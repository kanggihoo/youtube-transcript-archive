# Rails에서 하네스 엔지니어링을 활용하는 방법 — Joël Quenneville

## 한 줄 요약

Joël Quenneville의 Rails 컨퍼런스 발표(원문 영어). 에이전트를 프롬프트하고 기도하는 블랙박스가 아니라 루프로 보고, Rubocop, 훅, 제너레이터, 리뷰 스킬, 도메인 특화 스크립트로 AI 코드의 바닥선을 끌어올려야 이틀치 리뷰와 수정을 한 시간으로 줄일 수 있다고 말합니다.

## 이틀치 일을 이틀에 한 이야기

- 이틀치 기능을 에이전트로 한 시간 만에 동작하게 만들었지만, 내부 품질 문제를 다듬고 리뷰하느라 결국 이틀이 걸렸습니다. 한 시간 코딩 뒤 슬롭을 두더지 잡기 하듯 고친 셈입니다
- 첫 한 시간 뒤 바로 PR을 올려 부담을 동료에게 떠넘기는 것은 하지 말아야 한다고 합니다. 대신 AI가 내놓는 결과의 바닥선을 올려 리뷰를 한 시간으로 줄이는 것이 목표입니다
- agents.md에 규칙을 넣는 방식은 어느 정도 통하지만 천장이 있는 함정이라고 합니다

## 에이전트는 블랙박스가 아니라 루프

- 모델은 통 속의 뇌라 텍스트만 주고받습니다. 모델 호출을 감싸는 코드가 **하네스**이고, 파일 읽기와 쓰기 같은 무엇이든 붙일 수 있습니다
- 사람이 테스트를 돌려 결과를 프롬프트에 붙여 넣으면 **사람 배관공**이 됩니다. 이를 하네스에서 루프로 자동화한 것이 **에이전틱 루프**이고, Cursor, Claude Code, Codex의 핵심입니다
- 루프 덕에 에이전트가 실패에 대응해 스스로 고치므로 첫 생성이 완벽할 필요가 없습니다. 이런 루프와 신호를 활용해 코드 품질을 끌어올리는 일이 **하네스 엔지니어링**입니다

## agents.md는 스타일 가이드를 둘 곳이 아니다

- agents.md는 프롬프트 앞에 붙는 또 다른 프롬프트이고 확률적입니다. 컨텍스트가 찰수록 규칙을 어길 확률이 올라갑니다
- **Rubocop**: 판단을 결정론적 도구로 옮기고 agents.md에는 "Ruby 파일을 고치면 rubocop 실행" 한 줄만 둡니다. 이것도 확률적이므로 100%를 원하면 **stop 훅**으로 종료 시 rubocop을 돌리고 실패하면 종료를 막습니다
- **커스텀 cop**: 멀티 테넌트에서 finder 스코프를 빠뜨리는 버그처럼 cop 모양의 검증이 많습니다. LLM으로 2분이면 만들 수 있으니 야심 차게 접근하라고 합니다
- **제너레이터**: 마이그레이션 파일 이름은 에이전트가 자주 틀립니다. agents.md에 `rails generate migration`을 쓰라고 하면 약 90%, 파일 쓰기 훅으로 `db/migrate` 쓰기를 막고 거부 사유에 제너레이터 실행을 안내하면 100%에 가깝습니다. 에이전트는 쉬운 길을 택하므로 쉬운 길이 올바른 길이 되게 합니다. 컨트롤러 베이스 클래스나 policy 객체 같은 패턴도 제너레이터에 넣을 수 있습니다
- 지능이 덜 개입했는데도 시스템 전체가 더 똑똑하고 일관되어졌다고 합니다

## 결정론적으로 안 되는 것은 좁은 리뷰 스킬로

- 코드 휴리스틱을 agents.md에 넣은 결과는 특히 나빴다고 합니다. 대신 **LLM 리뷰 스킬**을 쓰되 범위를 좁히고 "좋은 코드란 무엇인가"의 한 가지 이론에 집중합니다
- 발표자는 자신의 PR 리뷰 방식대로 세 단계 스킬(넓은 구조 리뷰, 메서드별 리뷰, 가독성과 문서화 다듬기)을 만들었습니다. 편향을 줄이려고 서브에이전트에서 실행하고, 이를 호출하는 짧은 스킬로 흉내 낸 오케스트레이션을 자동화합니다. 진짜 오케스트레이션은 Claude Code의 dynamic workflow나 ultracode, 서드파티 도구가 있습니다
- agents.md와의 차이는 **조종 위치**입니다. 이미 생성된 구체적 프로그램에 휴리스틱을 거꾸로 적용하면, 가능한 모든 프로그램에 앞으로 적용하는 것(출발선 뒤에서 조종)보다 위반을 찾기 쉽습니다. 길 중간에서 조종하는 셈입니다

## 조종 메커니즘 2x2 사분면

Birgitta Böckeler의 멘탈 모델입니다. 시점(피드포워드 또는 피드백)과 성격(결정론적 계산 또는 LLM 추론)으로 나눕니다.

- **피드백 계산적**: Rubocop, reek, flog, Code Climate, 보안 스캐너, 테스트, 로그 확인, Playwright
- **피드포워드 계산적**: 제너레이터, 셋업 스크립트, 템플릿
- **피드백 추론적**: 에이전틱 리뷰와 분석
- **피드포워드 추론적**: 프롬프트, agents.md, 정적 문서, 근처 소스 코드
- 판단을 피드포워드 추론적 사분면에서 나머지 셋으로 옮기고, agents.md는 얇은 라우팅 레이어로 둡니다
- **굿하트의 법칙** 경고: 에이전트를 너무 빡빡하게 제약하거나 Code Climate 최대 점수를 요구하면 점수만 만족시키는 우회를 찾습니다. 여유를 주라고 합니다

## 도메인 특화 스크립트

- 문서를 가져와 처리하고 연결해 게시하는 프로젝트에서 자동화율이 약 5%였고, LLM에게 근본 원인을 물으면 큰 그림을 놓치고 모순된 답을 냈습니다
- 이 파이프라인을 새는 깔때기로 보고, 문서가 어느 단계에서 탈락했는지 분류하는 스크립트를 만들어 LLM에게 가리키자 결과가 크게 좋아졌습니다
  - 안정적인 정의로 집단을 서로 비교할 수 있습니다
  - 버킷, 단계, 종료 지점 같은 더 높은 수준의 언어로 추론합니다
  - 비슷한 이유로 실패한 버킷에서 조사를 시작할 수 있습니다
- 사람에게도 좋고 암묵지를 드러내며, 출력은 시각화 도구에 연결할 수 있습니다. Rails에서는 rake나 Rails shebang 스크립트로 쉽게 만듭니다

## 겪은 고통으로 개선하기

- 모든 메커니즘을 한꺼번에 들이지 말고, LLM을 바로잡을 때마다 "어떻게 하면 이번이 마지막일까"를 물어 **겪은 고통**으로 하네스를 키웁니다
- 점검 질문: 어디서 개입했나, 어떤 신호가 없었나, 수동으로 복사해 오간 것이 있나, agents.md 내용 중 결정론적으로 할 것이 있나, 대화가 퇴화했나(나눌 수 있었나), 반복된 실수가 있나
- 이를 묶은 **retro 스킬**(JoelQ/skills)이 긴 세션 뒤 이력을 분석해 자동화를 제안합니다. Matt Pocock도 최근 같은 이름의 스킬을 공개해, 그의 스킬을 쓴다면 이미 있을 수 있다고 합니다
- 결론: 에이전트는 루프라는 멘탈 모델로 바꾸고, 실수는 고치는 데 그치지 말고 다음에 반복되지 않도록 시스템을 고칩니다
