# 프롬프트 작성은 그만두세요. 이제 명세(Spec)를 작성할 때입니다.

## 한 줄 요약

휘발성 프롬프트 중심의 AI 코딩에서 벗어나 헌법(Constitution), 기능 명세(Spec), 기술 계획(Plan)을 메인 산출물로 삼는 '스펙 주도 개발(Spec-Driven Development)'을 적용해야 재현 가능하고 검증된 소프트웨어를 구축할 수 있다.

## 프롬프트 우선(Prompt-First) vs 스펙 우선(Spec-First)

- **프롬프트 우선의 한계**: 프롬프트는 개인 세션에 갇힌 임시 텍스트이며 리뷰와 버전 관리가 불가능함. 빌드는 되지만 원래 의도를 벗어난 엉뚱한 코드가 생성되어 사후 디버깅에 많은 시간을 낭비함
- **스펙 우선의 패러다임 전환**: 프롬프트가 아니라 '명세 문서' 자체를 핵심 산출물(Main Artifact)로 취급하고 Git 저장소의 영구적인 이력으로 관리

## 스펙 주도 개발(SDD)의 4단계 프레임워크

```
헌법 (Constitution) → 명세 (Spec) → 계획 (Plan) → 작업 분할 (Tasks) → 구현 (Implement)
```

| 단계 | 산출물 | 포함 내용 | 제외 내용 |
|---|---|---|---|
| **1. 헌법 (Constitution)** | 불변의 기본 규칙 | 설계 단계부터 테스트 가능성, 보안 표준, 엔터프라이즈 지침, 시간/데이터 정합성 원칙 | 개별 기능 세부 구현 |
| **2. 명세 (Spec)** | 기능 명세서 | 만들고자 하는 대상(What), 비즈니스 요구사항, 사용자 스토리, 도구 요구사항 | 기술 스택 및 구현 방식(How) |
| **3. 계획 (Plan)** | 기술 구현 계획서 | 프레임워크 버전, 프로그래밍 언어, 아키텍처 패턴, 배포 타깃, 인프라 설정 | 비즈니스 요구사항 재정의 |
| **4. 작업 (Tasks)** | 단계별 태스크 목록 | 의존성을 고려한 보일러플레이트, 설정, 기능별 구현 순서 및 테스트 작성 계획 | 모호한 포괄적 지시 |

## 성공적인 도입을 위한 3가지 실천 원칙

1. **프롬프트 전에 명세부터 작성**: '어떻게(How)'를 지시하기 전에 '무엇(What)'과 '왜(Why)'를 명확한 문서로 먼저 확정
2. **타협 불가능한 헌법 수립**: 프로젝트와 팀을 아우르는 3~5가지 핵심 규칙을 수립하고 살아있는 문서로 지속 진화
3. **AI 산출물의 철저한 전수 검토**: 코드를 짜기 전에 AI가 생성한 헌법, 명세, 계획 문서를 인간이 먼저 리뷰하고 팀의 합의를 이끌어낼 것
