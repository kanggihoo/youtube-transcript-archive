# 하네스 엔지니어링: 코딩 에이전트로 '소프트웨어 팩토리'를 만드는 방법

## 한 줄 요약

Tessl의 Drew Knox는 제품 코드를 전부 에이전트가 만들고 엔지니어는 그 팩토리를 만드는 소프트웨어 팩토리로 가는 길이 이너, 아우터, 메타 루프를 만드는 하네스 엔지니어링이라고 말하며, 컨트롤 플레인, 에이전트 레디 인프라, 개선 루프 세 레이어를 순서대로 쌓으라고 제안합니다.

## 소프트웨어 팩토리와 세 기둥

- 정의: 사용자에게 내보내는 최종 결과물을 전부 에이전트가 만들고, 엔지니어링 팀은 팩토리를 더 자율적이고 자동화되게 만들고 품질을 높이는 일을 하는 시스템입니다
- 자율성: 올바른 답까지 사람이 몇 번 바로잡아야 하는가입니다
- 자동화: 받아들이기 전에 얼마나 검토하고 신뢰를 쌓아야 하는가입니다. 자율성이 먼저 쌓여야 합니다
- 품질: 사용자에게 내놓는 제품의 수준입니다. 자율성과 자동화를 올리는 동안 일정하게 유지합니다

## 속도가 아니라 품질이 진짜 보상

- 발표자는 많은 사람이 팩토리를 빠른 출시 수단으로 보지만 그것은 단기 현상이라고 말합니다
- 백로그가 사라져 테스트 품질 개선과 아키텍처 리팩터링에 쓸 여력이 생기고, 결국 코드 품질이 오른다고 봅니다
- 비개발 직군도 아이디어를 내기 쉬워지고 엔지니어는 기반 시스템에 집중하게 됩니다

## 이너, 아우터, 메타 루프

- 이너 루프: PR을 올리기 전 에이전트가 계속 돌리는 빠르고 싼 반복입니다. 자율성을 높입니다
- 아우터 루프: PR이 올라간 뒤 한 번 돌리는 비싸고 포괄적인 검사입니다. 에이전틱 QA, 뮤테이션 테스트 등 사람 검토 시간을 덜어 주는 것들입니다
- 메타 루프: 개발 바깥에서 에이전트 로그, PR, 이슈, 사용자 피드백을 관찰해 새어 나간 실수를 찾고 이너와 아우터 루프에 되먹임합니다. 품질을 끌어올리는 곳입니다

## 하네스 엔지니어링이 어려운 세 가지 이유

- 분야가 너무 빨리 변해 따라가려면 사실상 AI 연구자가 돼야 하고, 모범 사례가 금방 안티패턴이 됩니다
- 본질적으로 계획에 없던 일이라 기능 출시와 경쟁하고, 안 하면 에이전트가 개선되지 않는 지역 최적점에 갇힙니다
- 필요한 정보가 로컬 에이전트 로그, 개인 컴퓨터, 사람 머릿속에 숨어 있어서 워크플로를 기록이 남는 곳으로 옮겨야 합니다

## 쌓아야 할 세 레이어

- 컨트롤 플레인: 이슈 트래커에서 작업을 시작해 샌드박스의 헤드리스 에이전트가 PR을 올리고 사람은 PR 댓글로 개입하게 해, 모든 접점을 읽을 수 있게 합니다. 이슈 추적, PR 리뷰, 스킬 레지스트리나 공유 저장소로 워크플로를 배포하는 세 가지가 필요합니다
- 에이전트 레디 인프라: CLI와 API 접근, 내부 서비스와 프로덕션 로그 접근, 코드 실행 환경, 회사의 일하는 방식 문서화입니다. 생각보다 훨씬 힘들고 한두 주를 쏟아야 합니다
- 개선 루프: 주기적 저장소 점검, 개발 플레이북, 반복 작업 자동화, 결과물 품질을 보고 스킬을 고쳐 같은 실수를 막는 되먹임입니다. 가장 많은 시간이 들어갑니다

## Tessl이 돕는 방식

- 스킬 레지스트리(게시, 버전 관리, 보안과 품질 리뷰, 권한 통제), Linear에서 GitHub로 가는 커넥터, 코드 리뷰 도구를 제공합니다
- Tessl Agent가 PR과 이슈에서 반복 작업을 찾아 스킬과 GitHub Action으로 자동화하고, 주간 유지보수 스캔을 원클릭으로 설치하게 합니다
- Tessl launch로 스킬을 골라 Codex, Claude Code, Gemini 등을 권한 있는 샌드박스에서 돌려 PR을 올리고 댓글에 응답하게 합니다
- 발표자는 위 내용이 모두 일반 기법이라 다른 도구로도 할 수 있다고 말합니다

## 추적할 지표

- 수동 개입과 사람이 다는 PR 댓글은 줄이고, 사람 입력 없이 시작되는 PR은 늘립니다. 품질은 먼저 유지하고 그다음 높입니다
