**12:08** · 컨트롤 플레인을 구축하려는 사람이 보통 갖추게 되는 것은 세 가지입니다. 이슈를 추적하고 거기서 에이전트 작업을 시작하는 방법이 있어야 합니다. 리뷰하는 방법도 있어야 하는데 GitHub PR 리뷰가 아마 가장 쉽습니다. 그리고 에이전트를 더 낫게 만드는 워크플로와 플레이북을 표준화하고 배포하는 방법이 있어야 합니다. 보통 스킬 레지스트리나, 에이전트 품질을 높이는 스킬을 푸시하는 공유 GitHub 저장소가 됩니다.

### 레이어 2: 에이전트 레디 인프라

**12:39** · 다음은 제가 "에이전트 레디"라고 부르는, 잡동사니가 엄청나게 많은 레이어입니다. 로컬 설정이 많은 프로젝트를 다른 사람이 세팅할 수 있게 옮겨 보려다가, 깔끔하게 분리돼 있다고 생각한 의존성이 사실은 그렇지 않다는 것을 알고 경악한 적이 있다면, 에이전트에게도 똑같은 일을 겪게 됩니다. 에이전트가 쉽게 접근할 수 있다고 생각했던 것들이 많을 겁니다. CLI, API 접근, 에이전트가 제품을 직접 클릭해 보며 만들 수 있게 하는 방법 같은 것들요.

**13:10** · 생각보다 더 힘들다고 약속드립니다.

**13:12** · "그래, 우리는 그렇게 어렵지 않을 거야" 하고 들어왔다가 끝에 가서 그렇게 말한 사람은 한 명도 없었습니다. 그만큼 거쳐야 할 조각이 많습니다. 이것이 아마 가장 계획하기 어려운 부분이고, 한두 주를 쏟아서 끝내 버려야 합니다. 회사의 두뇌에 일하는 방식과 워크플로 같은 것을 문서로 적어 두는 일로 이어집니다.

**13:37** · 모든 내부 서비스에 대한 접근을 줘야 하는데, 거버넌스와 API 접근 문제가 따릅니다.

**13:47** · 프로덕션 로그에 접근하는 방법도 줘야 하는데, 이것은 컴플라이언스 입장은 무엇인가 같은 별도의 문제가 있습니다. 그리고 에이전트가 자기가 짠 코드를 실행할 수 있는 환경도 필요합니다.

**13:59** · 끝없이 더 있지만 대체로 회사마다 다르고, 에이전트가 사람의 개입 없이 코드를 올리게 하려고 하다 보면 해결하게 됩니다. 어떤 문제가 있는지는 금방 알게 됩니다.

### 레이어 3: 개선 루프

**14:11** · 마지막으로, 가장 많은 시간을 쓰게 될 부분이 개선 루프입니다. 앞서 말한 이너, 아우터, 메타 루프에 해당하는 것들입니다. 메타 루프에 들어가는 구성요소들입니다. 먼저 저장소 유지보수입니다. 매일, 매일 밤, 매주 같은 주기로 코드베이스를 훑어 문제를 찾는 것이 필요합니다. 일반적인 개발 관행을 위한 플레이북도 필요합니다. 예를 들어 CLI에 기능을 추가하는 방법 같은 것입니다.

**14:38** · 반복되는 작업을 찾아내 자동화하는 방법도 필요하고, 가능한 한 빠르고 쉬워야 합니다. 그렇지 않으면 사람들이 하지 않을 테니까요. 그리고 결과물의 품질을 꾸준히 살펴 개선점과 배운 것을 나머지 코드베이스에 되돌려 주는 것도 필요합니다. 예를 들어 "에이전트가 이런 실수를 했네, CLI에 기능을 추가하는 플레이북 스킬을 업데이트해서 앞으로 이 실수를 하지 않게 하자" 하는 식입니다.

**15:09** · 이 세 가지 컨트롤 플레인을 해결하도록 돕기 위해 Tessl이 존재합니다. 앞서 말했듯 지금까지 한 이야기는 모두 기법일 뿐입니다.

**15:17** · 원하면 전부 직접 할 수도 있습니다. 그런 일을 하는 도구도 많습니다. 그래도 Tessl을 쓰고 싶으시다면 어떻게 도와드리는지 조금 말씀드리겠습니다.

### Tessl이 돕는 방법

**15:27** · 먼저, 왜 저희를 쓰고 싶으실까요?

**15:30** · 저희는 최첨단에 이르는 과정을 비교적 반복 가능하고 지속 가능하게 만드는 데 정말 집중합니다. 한 번에 거대한 것을 삼키는 것이 아니라 작은 도약 여러 번으로 만들려고 합니다.

**15:45** · 배터리가 포함돼 있습니다. 지식 격차는 저희가 따라가는 것으로 해결합니다. 하네스 엔지니어링의 모범 사례를 알고 있고 여러분 대신 최신 상태로 유지되는 에이전틱 경험을 쓰게 됩니다.

**15:58** · 모듈식이고 열려 있는 것에 진심입니다. 팩토리의 모든 구성요소가 한 회사의 최고 제품이어야 한다고 보지 않습니다.

**16:05** · 스택에서 가장 중요한 조각을 골라 쓸 수 있게 하고 싶습니다. 그리고 말씀드렸듯 쉽게 만드는 데 집중합니다. 설치해서 제안되는 변경에 반응하기만 하면 되는 자동화 루프가 있습니다. 6개월 뒤에 "와, 우리 소프트웨어 팩토리의 40%쯤 왔네" 하게 되도록, 멈추거나 출시를 미루는 일 없이 점진적인 단계로만 가게 하려 합니다.

**16:31** · 첫 번째로 Tessl이 돕는 곳은 컨트롤 플레인 구축입니다. 스킬 레지스트리가 있어서, 작업 중인 워크플로와 자동화를 게시하고 버전 관리할 수 있습니다. 보안 리뷰, 품질 리뷰, 누가 무엇을 게시하고 업데이트할 수 있는지에 대한 통제 같은 거버넌스가 내장돼 있습니다. 이슈 트래커를 GitHub에 연결하는 커넥터도 쉽게 쓸 수 있습니다. 지금은 Linear에서 GitHub로 연결하는 데 집중하고 있습니다. Linear 티켓을 만들면 GitHub 워크플로가 실행되게 할 수 있고, 커넥터는 곧 더 나옵니다.

**17:00** · 에이전틱 코드 리뷰의 기준을 세우고 더 표적화된 검사를 쉽게 설정하는 코드 리뷰 도구 모음도 있습니다.

**17:12** · 레지스트리에 게시된 워크플로가 보안과 품질 면에서 스캔되고, 실제로 에이전트의 출력을 얼마나 개선하는지 보여 주는 예시를 여기서 볼 수 있습니다.

### Tessl Agent

**17:25** · 이제 이야기하는 동안 영상을 하나 재생하겠습니다. 잘 나오는지 보겠습니다. 저희에게는 Tessl Agent라는 에이전틱 경험이 있어서, 개선 루프를 만들고 시간이 지나도 유지하도록 도와줍니다. 가장 먼저 하는 일은 변화 관리, 즉 반복되는 작업을 찾아 자동화로 만들 시간을 실제로 어떻게 낼 것인가를 돕는 것입니다. 에이전트가 PR과 이슈 등을 훑어서, 예컨대 매주 불안정한 테스트(flaky test)를 찾아 헤매고 있다는 것을 알아냅니다.

**17:57** · 그러면 그것을 워크플로용 스킬로 만들고 GitHub Action으로 자동화해 두자고 제안합니다. 그렇게 워크플로를 하나씩 자동화할 시간을 실제로 낼 수 있도록 돕습니다. 두 번째는 기본으로 유지보수 작업이 많이 들어 있다는 것입니다.

**18:14** · 앞서 아키텍처 품질, 코드 중복, 테스트 스위트의 수준, 보안 취약점이 있는지 같은 것을 주간으로 스캔하길 원할 거라고 말씀드렸습니다. Tessl을 쓰면 그런 것들을 원클릭으로 여러 개 설치해서, 별다른 수고 없이 매주 코드베이스가 개선되는 결과를 얻을 수 있습니다.

### Tessl Launch

**18:34** · 마지막으로, 어떤 스킬이든 자동화된 워크플로로 바꾸는 방법을 제공합니다. Tessl launch라는 명령인데, 워크플로를 코드화한 스킬을 가져와서 그것을 맡길 코딩 에이전트를 고를 수 있습니다. Tessl Agent도 선택지 중 하나지만 대부분의 코딩 작업에는 Codex, Claude Code, Gemini 같은 것을 쓰고 싶으실 겁니다. 모두 쓸 수 있고, 적절한 권한이 있는 샌드박스에서 실행합니다. 오래 걸리는 작업도 가능합니다.

**19:00** · PR을 올리고 남기신 댓글에 응답할 수 있도록 GitHub 토큰도 갖게 됩니다. 그래서 그런 워크플로를 자동화하기가 정말 쉬워집니다.

**19:12** · 이것들을 합치면 시작하기가 정말 쉽습니다. 하나씩 개선점을 찾고, 워크플로를 스킬로 만들고, 모두에게 배포하고, 그렇게 개선 루프를 돌리기 시작하면 됩니다.

### 추적해야 할 핵심 지표

**19:26** · 이 작업을 하면서 집중해야 할 것은 수동 개입(manual takeover)과 사람이 다는 PR 댓글을 줄이는 것입니다. 소프트웨어 팩토리까지 얼마나 왔는지 보기 위해 추적할 수 있는 지표입니다. 그리고 시간이 지나면서 사람의 입력 없이 시작되는 PR이 늘어나는 것을 보고 싶을 겁니다. 더 많이 자동화하고 있다는 신호입니다. 물론 먼저 품질을 일정하게 유지하고, 그 뒤에 끌어올리는 것을 목표로 하세요.
