# 팟캐스트 풀버전 - SpaceX에서 매달 수천 개의 PR을 반영하는 방법을 알아봅니다 | Cursor & Grok Bot 개발자 Lauren Tan(poteto)

## 한 줄 요약

Lauren Tan(poteto)이 지난달 PR 2,500개를 프로덕션에 반영한 방법을 설명합니다. 비결은 에이전트의 검증 능력과 실수를 불가능하게 만드는 코드베이스 환경을 먼저 갖추고, 외부 루프(Grok Bot)와 내부 루프(Cursor 프로젝트)를 연결해 사람이 병목이 되는 지점을 하나씩 없애는 것입니다.

## 신뢰의 사다리

- 에이전트 하나를 마이크로매니징하는 데 시간을 쓰다가, 자신이 병목이자 에이전트와 Chrome DevTools 사이의 사람 프록시라는 것을 깨달았다고 합니다
- 최전선 모델도 지름길을 택하므로, 쉬운 길이 곧 올바른 길이 되게 만드는 스킬을 만들어 왔다고 합니다
- 모델이 좋아질수록 병목은 의도를 명확히 표현하는 능력이 되기 때문에 도메인 전문성이 더 중요하다고 말합니다

## 소프트웨어 팩토리 대신 미쉐린 주방

- 팩토리는 품질과 장인정신을 연상시키지 않아서, 가정 요리사가 셰프가 되는 미쉐린 주방 비유를 선호합니다
- 셰프는 직접 요리하지 않아도 주방 전체를 조직하고 최종 결과에 책임을 지며, 엔지니어도 코드를 직접 쓰지 않지만 결과에 책임이 있습니다
- 주방, 스킬, 환경, 코드베이스를 어떻게 꾸리느냐가 새로운 재료입니다

## 검증이 가장 중요한 스킬

- 검증은 에이전트에게 손과 눈을 주어 코드를 실행하고 사람처럼 상호작용하고 디버깅하게 하는 것입니다
- 에이전트가 자기 작업 결과를 볼 수 있어야 루프가 성립하고, 사람이 방정식에서 빠질 수 있습니다
- 점수를 매기는 기준이 있으면 에이전트가 계속 개선하는 힐 클라이밍도 가능합니다
- 팀의 모든 앱에 자동으로 유지되는 검증 스킬이 있어 핵심 인프라가 됐다고 합니다

## 결정론적인 부분은 CLI로

- 스킬에서 결정론적인 부분은 스크립트나 CLI로 빼고 판단이 필요한 부분만 에이전트에게 남깁니다
- CLI가 없을 때는 에이전트마다 검증 도구를 매번 다시 만들어 비효율적이었다고 합니다
- 마이그레이션도 코드 모드처럼 기계적인 변환은 스크립트에 맡깁니다

## 실수를 막는 코드베이스

- 좋은 코드베이스는 변경하기 쉬운 코드베이스이고, 가드레일로 에이전트와 사람이 좁은 길만 가게 합니다
- TypeScript의 타입 내로잉처럼 가능한 공간을 좁힌다는 발상으로, 기능마다 디렉터리를 두는 관례와 엄격한 린트 규칙을 가진 사내 프레임워크 Dune을 만들었습니다
- 에이전트의 실패를 관찰해 실수를 볼 때마다 린트 규칙 등 환경으로 바꿉니다
- 엔지니어의 새로운 일은 환경에 시간을 쓰는 것이며, 이를 하지 않으면 마이크로매니징에 갇힙니다

## 내부 루프와 외부 루프

- 내부 루프는 에이전트가 의도를 향해 코드를 작업하는 것이고, 외부 루프는 Slack, Linear, X, 이메일 같은 외부 시스템에서 컨텍스트를 끌어오는 것입니다
- 두 루프를 연결하지 않으면 사람이 컨텍스트를 나르는 프록시가 됩니다
- Grok Bot이 외부 루프를 맡아 버그 리포트를 구독하고 재현해 Cursor 프로젝트로 보내며, 코디네이터 에이전트인 프로젝트가 서브에이전트에게 작업을 분배합니다
- 비슷한 이슈를 한 프로젝트로 묶으면 중복 작업을 줄이고 더 높은 수준의 원인을 볼 수 있습니다
- 2,500개의 PR은 기능만이 아니라 코드베이스 가꾸기(가드닝)가 많습니다. 나쁜 패턴을 찾는 에이전트는 바로 고치지 않고 문서에 쌓게 한 뒤 며칠마다 묶어서 봅니다

## 리뷰는 샘플링으로

- 모든 PR을 읽지 않고, 매일 PR 품질을 샘플링해서 여러 에이전트가 같은 지름길을 택하면 개별 에이전트가 아니라 환경을 고칩니다
- pstack의 풀 오토파일럿은 PR마다 검증 에이전트를 띄워 앱을 실제로 클릭하며 퍼징하고 스스로 고친 뒤 머지합니다. 토큰을 많이 쓰지만 조절할 수 있습니다
- 머지 후 아침에 커밋 히스토리를 보고 문제가 있으면 되돌리거나 수정하거나 린트 규칙을 추가합니다
- 이 지점에 이르는 것은 매우 어렵고 pstack만 쓴다고 쉽게 되지 않는다고 강조합니다

## 되돌릴 수 없는 변경은 어떻게 하나

- 일방향 문 같은 PR이 많은 분야는 해당 영역의 검증 가능성이 관건이며, 검증할 수 있다면 일방향 문도 양방향 문이 된다고 합니다
- 자신도 답을 갖고 있지 않다고 하면서, 프로그래밍과 증명을 결합한 Bend 같은 에이전트 지향 언어가 늘어나기를 기대합니다

## 자신만의 스킬 만들기

- 스킬은 말로 바뀐 프로세스일 뿐이며, 모두가 자기만의 칼 세트를 가져야 합니다
- 과거 채팅에서 개입했던 순간을 뽑아 린트 규칙이나 스킬로 바꾸라고 권합니다. pstack의 recall 스킬이 이 워크플로를 압축한 것입니다
- 최신 모델에서는 스킬에서 구현 세부 사항을 덜어내고 워크플로 중심으로 가며, 스킬은 점점 작아질 것이라고 봅니다
