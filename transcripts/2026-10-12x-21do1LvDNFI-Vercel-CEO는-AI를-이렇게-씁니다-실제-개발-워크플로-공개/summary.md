# Vercel CEO는 AI를 이렇게 씁니다 | 실제 개발 워크플로 공개

## 한 줄 요약

Vercel CEO 기예르모 라우치가 자사 코딩 CLI fx로 일하는 방식을 보여 주며, 코드를 한 줄씩 읽지 않더라도 에이전트가 한 일을 이해하려 하고(에이전틱 인콰이어리), 보안이 중요한 곳은 바이브 코딩과 반대로 철저히 하며, 에이전트 실행은 클라우드 샌드박스를 기본으로 하되 로컬 선택지도 열어 두라고 말합니다.

## fx와 리서치 폴더, 프로젝트 별칭

- fx는 셸처럼 빨리 부팅되도록 만든 작은 바이너리(다운로드 6MB, 디스크 11MB)입니다
- 리서치 폴더의 agents.md가 질문 처리 규칙을 정하고, 에이전트가 조사 결과를 그 폴더에 쌓습니다. 구글을 대체했다고 합니다. 별칭 r로 이 폴더에서 바로 실행합니다
- 별칭 p는 아이디어가 떠오를 때 프로젝트 폴더에 새 프로젝트를 만듭니다(토비의 try와 비슷). 맥 앱, Next.js, Zig, Rust 실험과 벤치마크에 씁니다
- 새 인프라는 에이전트의 방식으로 검증합니다. Drives를 발표할 때 에이전트에게 경쟁 상태 찾기, 지연 측정, 대안 비교를 시켰고, 써 본 뒤 "Vercel이 더 잘할 점"을 되돌아보게 합니다

## fx0 데모: 하네스는 기성품으로, 도구는 샌드박스로

- V0를 만들 때 엔지니어링 시간의 90%가 하네스에 들어갔지만, fx0 예제는 fx 에이전트 API 위에 코드 100줄쯤입니다. 오픈소스로 공개할 예정
- 권장 구조는 뇌(하네스)와 손(도구): 도구로 Vercel 샌드박스를 줘서 HTML만 내놓던 결과가 실제 Next.js 앱 실행으로 확장됩니다. 세 번째 예시는 프롬프트로 Eve 에이전트를 만드는 것
- 고객들이 자기 시스템 안에 앱 생성 기능이나 사내 소프트웨어 팩토리를 원한다고 합니다

## 에이전트가 한 일을 이해하기

- 에이전틱 인콰이어리: 모든 줄을 읽자는 게 아니라 일이 끝나면 무슨 일이 일어났는지 이해하려 하는 것. 한 줄씩 읽기와 무조건 맡기기라는 이분법을 비판합니다
- 에이전트로 파일이나 모듈을 이해하면 충분하고, 콜 스택을 그려 주는 스킬, 지연과 메모리 할당 측정, 새 API 모양 파악이 예입니다
- 공개 API가 바뀌면 Slack이나 Discord로 알리게 하는 식으로 자동화된 소프트웨어 팩토리를 짜는 것이 "실수하지 마, 자동 병합해"보다 낫다고 말합니다

## 보안

- 극단적 바이브 코딩은 기업 고객 앞에서 역효과가 날 수 있고, 바이브 코딩의 반대를 한다고 전달하는 것이 유리할 수 있습니다
- 새 소프트웨어를 들일 때 가장 큰 어려움은 떠안는 보안 파악이며, 공급망 공격으로 공격 표면이 커졌으니 철저히 할 영역은 철저히 하고 알려야 합니다

## 클라우드 vs 로컬

- 에이전트의 클라우드 이동은 필연이고 이미 진행 중: 대규모 코드베이스는 로컬에서 감당이 안 되고, 샌드박스는 공급망 공격의 피해 범위를 가두며(방화벽과 네트워크 감시로 데이터 유출을 막기 쉬움, 공급망 공격을 근절할 수도 있다는 대담한 주장), 병렬 실행과 자는 동안의 작업에 유리합니다
- 그래도 파일 시스템, 프로세스 모니터, 맥 앱과의 상호작용을 가까이서 봐야 할 때가 있어 로컬로 끌어올 선택지는 남겨야 합니다. 결론은 토글 스위치입니다
