# 에이전트 관리의 표준이 될 거라고 봅니다 | Manager Agent

## 결론부터

개발동생은 코딩 에이전트 세션을 5~10개 돌리면 병목이 사람의 승인이 된다며, 사람과 코딩 에이전트 사이에 에이전트를 관리하는 에이전트 계층을 두자고 주장합니다. 결론은 사람의 인지 부하를 줄이고 신뢰할 수 있는 검증 체계를 만드는 것이 핵심이며, 이 구조가 이미 표준이거나 곧 표준이 되리라는 것이 발표자의 견해입니다.

## 핵심 내용

- 발표자가 센 바로는 유휴 세션 약 28개 중 13개가 결정 대기였고, 이 중 사람의 판단이 필요한 것은 6개, 기준만 정해 두면 통과시킬 수 있는 것은 7개였습니다. 이 7개를 대신 처리하는 계층이 매니저 에이전트입니다.
- 구조는 3단입니다. 맨 위 매니저(Grok Bot, OpenAI dots, Claude Duet로 소개, Slack·Gmail·이슈 등에서 맥락을 모아 사람과 대화), 가운데 코디네이터(Cursor Projects, Claude Code Projects로 소개, 작업을 쪼개 위임), 아래 코딩 에이전트입니다. 위 두 층은 직접 코딩하지 않아야 하는데, 코딩 맥락이 매니저의 컨텍스트 창을 채워 관리 성능이 떨어지기 때문이라고 합니다.
- 사례로 Grok Bot 엔지니어 Lauren이 한 달에 PR 2,500개를 머지했다는 워크플로를 소개합니다(Slack 피드백 → Linear 티켓 → 클라우드 에이전트가 버그 재현·수정 → 여러 에이전트가 깨뜨려 보기 → 1시간 뒤 자동 머지). 발표자는 Cursor의 pstack `/correct` 스킬을 자기 영상 편집 앱에 돌려 커밋 1,054개와 리뷰 777개에서 실수 유형 약 13가지를 찾고 2가지를 CI 검사로 올렸으며, 16분 뒤 다른 세션에서 같은 실수가 CI에 걸렸다고 말합니다.

## 배울 점과 적용 조건

- **승인 설계:** 매니저가 알아서 처리할 것과 사람에게 승인 카드로 올릴 것을 미리 나눠야 합니다. 전부 맡기면 위험이 커진다고 발표자도 경고합니다. 이미 여러 에이전트 세션을 병렬로 쓰는 사람에게 해당하는 이야기입니다.
- **신뢰 역피라미드:** 코드 구조 → lint·테스트·CI 안전망 → AGENTS.md 등 프롬프트 지침 → 사람 리뷰 순으로 쌓고, 규칙으로 잡을 수 있는 것은 위 단계로 올립니다. 반복되는 에이전트 실수를 텍스트 규칙에서 CI 검사로 옮기는 것은 도구와 무관하게 적용할 수 있습니다.
- **보안:** 매니저·코디네이터는 사실상 관제실이라 뚫리면 전체가 뚫립니다. 발표자는 Paseo의 열린 relay를 닫고 비밀번호를 걸었으며 외부 접근은 Tailscale 연결 기기로만 허용했습니다.

## 근거와 한계

- **영상의 근거:** 발표자 본인의 세션 수 집계와 pstack `/correct` 실행 수치(커밋 1,054개, 리뷰 777개, 유형 13개, 검사 2개), Lauren의 발표와 X 게시물 인용, 자신의 보안 설정 변경 사례입니다. 자막만으로 화면 시연은 확인되지 않습니다.
- **평가:** 한 사람의 세션 집계(28개 중 13개)나 검사 2건은 일반화하기에는 표본이 작고, "표준이 될 것"은 발표자 스스로 개인 견해라고 말합니다. Lauren의 2,500 PR은 하루 약 83개이며, 머지된 PR의 품질·되돌림 비율은 영상에 없어 이 수치만으로 방식의 효과를 판단하기 어렵습니다. 매니저 에이전트의 오판(승인해서는 안 될 것을 통과시키는 경우)에 대한 사례나 대책은 약하게만 다룹니다.
- **확인 범위:** 자막 기반 평가이며 외부 확인은 하지 않았습니다. 제품 출시일(Grok Bot 8월 11일, dots 9월 29일, Duet 10월 21일), SpaceX의 Cursor 인수, Lauren의 수치와 팔로워 증가는 영상 내 주장, 외부 미검증입니다.
- **홍보성:** 협찬 고지는 자막에서 관찰되지 않습니다. 발표자가 Claude Code·Codex·Cursor를 모두 구독하고 Grok Bot과 Paseo를 쓰는 사용자로서 소개하는 구도입니다.
