**9:55** · 프레임워크는 다르게 동작합니다. 애플리케이션의 구조를 제공하고, 적절한 시점에 여러분의 코드를 호출하는 경우가 많습니다.

### Spring과 Spring Boot

**10:03** · 가장 잘 알려진 자바 프레임워크 중 하나가 Spring입니다. 핵심 기능은 애플리케이션 구성 요소를 만들고 그 의존성을 연결하는 일을 돕는 것으로, 이를 의존성 주입이라고 합니다.

**10:13** · 모든 구성 요소를 직접 만들고 연결하는 대신, 구성 요소가 무엇을 필요로 하는지 선언하면 Spring이 그것을 제공해 줍니다. Spring은 보안, 데이터베이스 접근, 웹 애플리케이션 등 애플리케이션 개발의 많은 영역을 지원합니다.

**10:28** · 하지만 예전에는 Spring 애플리케이션을 구성하는 데 상당한 설정이 필요했습니다. Spring Boot는 합리적인 기본값, 자동 구성, 애플리케이션을 패키징하고 실행하는 편리한 방법을 제공해 그 과정을 단순하게 만듭니다.

**10:42** · Spring Boot를 쓰면 개발자는 생성된 프로젝트에서 시작해 필요한 의존성을 고르고, 모든 세부 사항을 처음부터 설정하지 않고도 동작하는 웹 애플리케이션을 만들 수 있습니다.

**10:53** · 애노테이션으로 컨트롤러를 식별하고 메서드를 HTTP 엔드포인트에 매핑할 수 있으며, 요청 라우팅은 Spring이 처리합니다.

**11:00** · 그래서 Spring Boot는 현대 자바 백엔드 개발에서 아주 흔한 출발점이 되었습니다. Quarkus와 Micronaut 같은 대안도 시작 시간과 자원 사용량을 개선하는 기능으로 현대적인 배포 환경을 겨냥합니다.

### JDBC와 Hibernate로 다루는 데이터베이스

**11:14** · 애플리케이션은 보통 데이터를 저장하고 가져오기도 해야 합니다.

**11:18** · 자바는 관계형 데이터베이스와 통신하는 표준 API인 JDBC를 제공합니다.

**11:24** · 개발자는 이것으로 SQL 문을 보내고 결과를 처리할 수 있습니다.

**11:28** · Hibernate 같은 도구는 객체 관계 매핑을 제공해, 애플리케이션 코드가 데이터베이스 레코드에 대응하는 자바 객체로 작업할 수 있게 합니다.

**11:37** · Spring Data는 이런 기능 위에서 흔한 데이터 접근 작업을 단순하게 해 줍니다.

**11:42** · 그런데 라이브러리가 이렇게 유용한 기능을 많이 제공한다면, 그것들은 어떻게 자바 프로젝트에 들어올까요? 개발자가 파일을 하나하나 직접 내려받을 수도 있겠지만, 금세 유지하기 어려워집니다. 자바 라이브러리는 보통 JAR 파일로 배포되고, 많은 라이브러리가 소프트웨어 아티팩트의 공개 저장소인 Maven Central에 올라 있습니다.

### 빌드 도구: Maven과 Gradle

**12:03** · 빌드 도구는 이런 의존성을 관리하는 과정을 자동화합니다. 만나게 될 주요 선택지는 Maven과 Gradle 두 가지입니다. 이 도구들은 필요한 라이브러리를 내려받고, 전이 의존성을 해결하고, 소스 코드를 컴파일하고, 테스트를 실행하고, 완성된 애플리케이션을 패키징할 수 있습니다. Maven은 프로젝트 설정을 pom.xml이라는 파일에 기술하고, Gradle은 지원하는 설정 언어로 작성한 빌드 파일을 씁니다. 의존성이 또 다른 의존성에 의존할 수도 있어서, 애플리케이션이 필요로 하는 라이브러리의 연쇄가 생깁니다.

**12:34** · 빌드 도구가 이런 관계를 해결해 주지만, 개발자는 여전히 라이브러리 버전과 호환성에 신경 써야 합니다. 각 프로젝트는 자기 의존성을 따로 선언할 수 있으므로, 공유되는 하나의 설치본에 기대지 않고 애플리케이션마다 같은 라이브러리의 다른 버전을 쓸 수 있습니다. 이제 운영에서 중요한 문제인 보안으로 넘어갑니다.

### 의존성 보안과 Log4Shell

**12:56** · 라이브러리는 개발자의 시간을 엄청나게 아껴 주지만, 애플리케이션 팀이 직접 작성하지도 검토하지도 않았을 코드를 들여오기도 합니다. 2021년 12월, Log4Shell이라는 취약점이 널리 쓰이는 자바 로깅 라이브러리 Log4j의 영향받는 버전에서 심각한 약점을 드러냈습니다. 취약한 조건에서는 특수하게 조작된 입력이 위험한 룩업 동작을 일으켜 원격 코드 실행으로 이어질 수 있었습니다.

**13:22** · 이 사건은 전 세계 조직에 영향을 미쳤는데, 일부는 Log4j가 다른 의존성을 통해 간접적으로 포함되는 경우가 많았기 때문입니다. 팀이 Log4j를 직접 추가하지 않았더라도, 다른 라이브러리가 그것을 애플리케이션에 끌고 들어왔을 수 있습니다. 그래서 의존성 목록을 관리하고, 알려진 취약점을 스캔하고, 영향받는 패키지를 업데이트하는 것이 소프트웨어 개발의 중요한 일부입니다. 자바의 메모리 안전 기능은 애플리케이션이 쓰는 라이브러리의 모든 취약점으로부터 애플리케이션을 지켜 주지 못합니다.

**13:51** · 자바 생태계에는 흥미로운 측면이 하나 더 있습니다. JVM은 자바로 작성한 애플리케이션에만 국한되지 않습니다. 다른 언어도 JVM을 대상으로 할 수 있습니다.

### Kotlin과 안드로이드

**14:02** · Kotlin이 대표적인 예입니다. 다른 언어 설계를 제공하면서도 자바 코드와 많은 자바 라이브러리와 상호 운용됩니다. 구글은 새 안드로이드 개발에 Kotlin을 우선 언어로 권장했지만, 기존 애플리케이션에서는 자바가 여전히 의미가 있습니다. 다만 안드로이드에는 중요한 차이가 있습니다. 자바나 Kotlin으로 작성한 안드로이드 애플리케이션은 표준 데스크톱·서버용 JVM에서 실행되지 않습니다. 안드로이드 플랫폼을 위해 설계된 안드로이드 고유의 런타임 ART에서 실행됩니다.

**14:30** · 어떤 언어나 프레임워크를 고르든, 코드가 바뀌어도 계속 제대로 동작하는지 확인해야 합니다.

### 테스트와 개발자 도구

**14:39** · 여기서 자동화된 테스트가 등장합니다.

**14:41** · JUnit은 자바 테스트를 작성하는 데 널리 쓰이고, Mockito는 의존성을 통제된 테스트 대역으로 바꿔 줍니다. 예를 들어 결제 관련 테스트에서는 실제 카드를 결제하는 대신 모의 결제 서비스를 쓸 수 있습니다. 빌드 도구가 이런 테스트를 자동으로 실행해, 팀이 변경 사항이 운영에 나가기 전에 문제를 잡도록 도와줍니다.

**15:01** · 자바 코드를 작성하고 탐색할 도구도 필요합니다. JDK에 포함된 JShell을 쓰면 완전한 프로젝트를 만들지 않고도 자바 표현식을 실험해 볼 수 있습니다. 더 큰 애플리케이션에는 개발자들이 보통 IntelliJ IDEA와 Eclipse 같은 통합 개발 환경을 씁니다. 자바 확장을 설치한 Visual Studio Code도 한 가지 선택지입니다. 이런 도구들은 코드 탐색, 디버깅, 프로젝트 관리 등 개발을 편하게 해 주는 기능을 제공합니다.

### 자바 버전 고르기

**15:29** · 마지막으로 자바 버전 이야기를 해 보겠습니다. 튜토리얼이나 기존 프로젝트를 다루다 보면 서로 다른 번호를 만나기 때문입니다. 자바 10부터 기능 릴리스는 6개월 주기를 따릅니다. 일부 릴리스는 장기 지원 버전, 즉 LTS로 지정되어 해당 배포판의 정책에 따라 연장된 지원을 받습니다. 자바는 정기적으로 새 버전을 내놓아 언어, 성능, 개발 경험을 개선합니다. 하지만 모든 릴리스가 운영 환경에서 장기간 쓰이도록 만들어진 것은 아닙니다.

**15:59** · 초보자에게는 LTS 버전을 고르는 것이 보통 합리적인 출발점입니다. 학습에 안정적인 기반이 되기 때문입니다. 실무 환경에서 팀은 애플리케이션의 요구 사항, 라이브러리 호환성, 지원 정책에 따라 버전을 고릅니다. 그러니 자바 프로젝트를 시작할 때는 항상 그 프로젝트가 요구하는 자바 버전이 무엇인지, 그 버전이 아직 지원되는지 확인하세요. 오래된 많은 시스템에서는 여전히 자바 8을 볼 수 있습니다.

**16:25** · 낡은 접근법을 가르치거나 더 이상 현대 개발과 관련 없는 기술을 언급하는 오래된 튜토리얼도 만나게 됩니다. 그런 자료로 배울 때는 사용하는 자바 버전에 유의하세요. 일부 오래된 엔터프라이즈 자바 API는 javax 네임스페이스에서 Jakarta로 옮겨 갔습니다. 다만 javax를 쓰는 모든 패키지가 바뀐 것은 아닙니다. 그렇다면 자바가 가장 잘 맞는 곳은 어디일까요? 엔터프라이즈 애플리케이션, 금융 시스템, 백엔드 서비스, 데이터 인프라에서 여전히 널리 쓰입니다.

### 자바가 어울리는 곳

**16:53** · 성숙한 생태계, 폭넓은 도구 지원, 호환성, 큰 개발자 커뮤니티 덕분에 오래 유지되는 애플리케이션에 실용적인 선택입니다. 모든 상황에 최선은 아닙니다. 특히 극도로 낮은 메모리 사용량, 아주 작은 배포 크기, 매우 빠른 시작 시간이 가장 중요한 경우가 그렇습니다. 어떤 언어든 마찬가지로, 올바른 선택은 풀려는 문제에 달려 있습니다.

### 전체를 하나로 정리하면

**17:18** · 전체를 정리해 보겠습니다. 자바 소스 코드를 작성하면 컴파일러가 검사한 뒤 바이트코드를 만듭니다. JVM은 그 바이트코드를 로드해, 성능을 높이는 적시 컴파일 같은 기법을 써서 실행합니다. JDK는 애플리케이션을 개발할 도구를 주고, 표준 라이브러리는 공통 기능을 제공합니다.

**17:37** · 가비지 컬렉션은 객체 메모리를 관리하고, 가상 스레드는 특정 종류의 동시성 작업에 도움을 줍니다. 언어와 런타임 너머에서는 라이브러리가 재사용 가능한 기능을 제공하고, Spring Boot 같은 프레임워크는 애플리케이션의 구조를 잡도록 돕습니다. Maven과 Gradle은 의존성을 관리하고 빌드를 자동화합니다.

**17:55** · 테스트 도구는 동작을 검증하도록 돕고, 의존성 스캔은 보안 위험을 찾아내도록 돕습니다. 고른 IDE는 일상적인 개발 작업을 뒷받침하고, 쓰는 자바 버전은 어떤 언어 기능과 런타임 기능을 쓸 수 있는지를 결정합니다. 이 관계들이 이해되고 나면, 자바 생태계는 서로 무관한 이름들의 모음처럼 보이지 않게 됩니다. 각 구성 요소는 서로 다른 문제를 해결하고, 함께 모여 실제 애플리케이션을 만들고, 실행하고, 테스트하고, 유지하는 데 필요한 도구를 제공합니다. 오늘 모든 기술을 외울 필요는 없습니다.

**18:25** · 각 구성 요소가 맡은 역할을 이해하는 것부터 시작하세요. 새로운 자바 프로젝트를 만나면, 그 조각들이 어떻게 맞물리는지, 더 배워야 할 때 어디를 봐야 하는지가 훨씬 분명해질 것입니다. 이 영상이 자바와 그 주변 생태계를 더 선명하게 그려 주었다면, 개발자들이 매일 쓰는 기술을 실용적으로 설명하는 영상을 더 보시도록 구독을 고려해 주세요.
