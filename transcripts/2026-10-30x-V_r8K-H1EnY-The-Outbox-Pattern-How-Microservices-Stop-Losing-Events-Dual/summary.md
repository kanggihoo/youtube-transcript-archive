# The Outbox Pattern: How Microservices Stop Losing Events

## 결론부터

DB 저장과 브로커 발행을 따로 하면 어떤 순서로 해도 장애 시 데이터가 어긋나는데(이중 쓰기 문제), 발표자는 이벤트를 같은 DB의 outbox 테이블에 같은 로컬 트랜잭션으로 저장하고 별도 릴레이(폴링 또는 CDC)가 발행하게 하면 해결된다고 결론짓습니다. 대신 전달 보장은 최소 한 번이므로 소비자가 멱등해야 합니다.

## 핵심 내용

- **이중 쓰기 문제:** 저장 후 발행하면 이벤트가 사라지고, 발행 후 저장하면 유령 주문이 생깁니다. 프로세스가 죽으면 재시도 주체도 없어 순서 변경이나 재시도로는 못 풉니다. 2PC는 브로커 지원 부족, 잠금, 조정자 단일 장애점 때문에 현실적이지 않다고 합니다.
- **아웃박스:** 비즈니스 행과 outbox 행(ID, 이벤트 유형, 페이로드, 전송 플래그)을 한 트랜잭션에 씁니다. 릴레이는 폴링(미전송 행 조회 → 발행 → 표시) 또는 CDC(Debezium이 트랜잭션 로그를 읽음)로 발행합니다. 발표자는 폴링으로 시작하고 규모가 커지면 CDC로 옮기라고 권합니다.
- **운영 세부:** 발행 후 표시 전에 죽으면 중복 발행되므로 이벤트 ID로 소비자가 중복을 제거합니다. 순서는 Kafka에서 주문 ID를 파티션 키로 보장합니다. outbox 행은 삭제하거나 정리 작업으로 지우고, 결과적 일관성을 감수해야 합니다.

## 배울 점과 적용 조건

- DB 쓰기와 메시지 전송이 한 작업에 함께 있고 메시지 유실이 상태 오류로 이어질 때(주문 생성, 결제 승인, 재고 예약 등) 적용합니다. 캐시 무효화 힌트나 메트릭처럼 유실돼도 되는 메시지에는 과합니다.
- 소비자 쪽 멱등 처리(처리한 ID 테이블, 발표자는 인박스 패턴으로 언급)가 전제입니다. 변경과 이벤트를 같은 순간에 봐야 하는 경우에는 맞지 않습니다.
- 폴링 릴레이를 여러 워커로 확장할 때는 행 잠금으로 한 워커만 가져가게 해야 합니다.

## 근거와 한계

- **영상의 근거:** 주문 서비스–배송 서비스 시나리오와 장애 지점별 설명뿐입니다. 코드 시연, 벤치마크, 운영 사례는 없습니다.
- **평가:** 이중 쓰기 문제와 아웃박스의 원자성 논리는 널리 알려진 설명과 일치해 설득력이 있습니다. 다만 CDC가 "중복 없음"이라는 말은 단순화입니다(앞서 최소 한 번 전달을 말한 것과 긴장). 폴링 지연·부하 수치, DB별 구현 차이, CDC 운영 비용은 다루지 않습니다.
- **확인 범위:** 자막 기반 평가이며 외부 검증은 하지 않았습니다. 원문은 한국어 자동 번역 자막입니다.
- **홍보성:** 마지막에 구독 요청 외에 특별한 징후는 없습니다.
