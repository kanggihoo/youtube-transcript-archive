# Reverse Engineer Anything (REA) Explained: The Software Industry Will Never Be the Same

## 한 줄 요약

REA는 코딩 에이전트를 Ghidra 같은 전문 분석 도구와 MCP로 연결해 소스 없는 앱의 특정 기능을 조사하고 새로 구현하도록 돕는 오픈 소스 프로젝트이지만, 원본 소스를 복원하지는 못하고 샌드박스도 아니므로 증거 검증, 보안, 법적 허가는 사용자의 책임이라고 발표자는 설명합니다.

## REA가 무엇인가

- 그 자체가 디컴파일러가 아니라 코딩 에이전트와 분석 도구(Ghidra, Hopper, IDA Pro 등) 사이의 오케스트레이션 계층입니다
- 네이티브 바이너리, JavaScript와 Electron 앱, .NET 어셈블리, Android 앱, 웹사이트, 펌웨어 등을 대상으로 하며 MCP 서버와 명령줄 인터페이스를 제공합니다
- 2026년 10월 급상승하며 일주일 안에 GitHub 스타 4만 2천 개를 넘겼습니다
- 문서화된 카탈로그는 12개 계열의 MCP 도구 139개, 명령줄 명령 94개, 안내형 프롬프트 6개입니다

## 디컴파일, 이해, 재구성

- 디컴파일 단계에서는 의사 코드, 문자열과 심볼, 모듈, 메타데이터, 호출 관계 같은 증거를 모읍니다. 목표는 원본 복원이 아니라 유용한 증거 수집입니다
- 이해 단계에서는 실행 경로를 추적하고 앱의 각 부분이 어떻게 통신하는지 연결합니다. Electron이라면 UI에서 내부 통신 채널을 거쳐 메인 프로세스까지 따라갑니다
- 재구성 단계에서는 원본을 복사하지 않고, 이해한 동작을 내 프로젝트에 맞게 새로 구현합니다
- 세션 관리, 체크포인트, 구조화된 증거 기록으로 조사 컨텍스트를 이어 가며, 결론뿐 아니라 근거와 아직 모르는 것도 남깁니다

## 설정과 실제 사용 예

- Node.js 22.19 이상이 필요하고 `npx rea-agents setup`으로 설정합니다. 지원 에이전트를 감지하고, 변경 사항을 보여 주고, 기존 설정을 백업하며, 중요한 변경 전에 승인을 요청합니다
- 모든 분석 엔진이 자동 설치되지는 않습니다. 예를 들어 Ghidra 통합에는 호환 Ghidra와 64비트 JDK가 필요하고, JavaScript 분석은 네이티브 디컴파일러 없이 가능합니다
- 노트 앱의 내보내기 기능을 조사해 포매터를 새로 만든 테스트에서 14개 공개 테스트 케이스가 모두 기준 동작과 일치했습니다
- 다만 이 테스트는 JavaScript 예제와 특정 기능에 한정되었고 네이티브 바이너리나 앱 전체 재구성은 아니었으므로, 모든 앱에 통한다는 증거는 아니라고 발표자는 단서를 붙입니다
- 도구가 많다고 에이전트가 능숙해지는 것은 아니며, 올바른 질문, 도구 선택, 증거 해석, 정보 부족 인식은 여전히 에이전트의 몫입니다

## 원본 소스는 복원되지 않는다

- 컴파일 과정에서 변수 이름, 주석, 포맷, 소스 구조 일부가 사라지므로 디컴파일 결과의 의사 코드는 원본 소스와 다릅니다
- REA가 복원하는 것은 함수, 문자열, 심볼, 호출 경로, 모듈 관계, 런타임 관찰 같은 정보이며, 에이전트가 이를 바탕으로 동작을 추론합니다

## 보안: 프롬프트 인젝션과 샌드박스 부재

- 분석 대상의 문자열이나 디컴파일 출력에 지시문처럼 보이는 텍스트(프롬프트 인젝션)가 있을 수 있으므로, 에이전트는 이를 지시가 아닌 데이터로 다뤄야 합니다
- REA는 보호 장치가 있지만 샌드박스가 아니며, 런타임 조사 기능으로 대상을 실행하면 사용자 권한으로 돕니다
- 로컬에서 분석해도 문자열, 심볼, 디컴파일 출력은 코딩 에이전트를 통해 모델 제공자에게 전송될 수 있습니다
- 신뢰할 수 없는 앱은 격리 환경에서 조사하고, 승인 요청을 켜 두고, 에이전트에게 허용하는 작업을 검토하라고 권합니다

## 법적 고려

- 합법 여부는 관할권, 대상 소프트웨어, 조사 이유, 방법에 따라 다르며 REA가 판단해 주지 않습니다
- 상호운용성 목적은 허용될 수 있지만 서비스 약관, 디지털 저작권 관리나 기술적 보호 조치 관련 법률이 별도 문제가 될 수 있습니다
- 자신의 소프트웨어, 오픈 소스, 보안 챌린지, 테스트 권한이 있는 시스템이 더 분명한 출발점이며 경쟁사의 비공개 제품 복제는 법적·지식재산권 문제가 커질 수 있습니다

## 현실적인 한계와 핵심 교훈

- REA는 앱 전체를 자동 복제하지 않고, 디컴파일러마다 의사 코드가 다를 수 있으며, 플랫폼과 대상별 지원 차이와 추가 소프트웨어 요구가 있습니다
- 활발히 개발 중이라 기능이 빠르게 바뀌므로 특정 동작에 의존한다면 버전을 고정하라고 권합니다
- 요구 사항이 분명하고 테스트 가능한 작은 기능 단위의 조사가 앱 전체 재구성 요청보다 낫습니다
- 핵심은 증거 수집, 증거 추적, 새 구현 후 테스트라는 흐름이며, 낯선 의존성이나 프로토콜, 문서가 사라진 레거시 시스템에도 응용할 수 있습니다
- AI가 일을 더 해도 검증, 증거의 한계 이해, 민감 정보 보호, 조사의 허가 확인은 사람의 책임이며 엔지니어링 판단은 대체되지 않습니다
