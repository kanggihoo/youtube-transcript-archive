# 한국어 번역

Shopify는 메인 모바일 앱을 300개 화면 규모로 다시 만들면서 AI 코딩 에이전트를 사용했습니다. 전체 작업을 한 번에 에이전트에게 맡긴 것은 아닙니다. 구조화된 절차를 끝까지 적용해 품질 기준을 지켰습니다. Shopify는 방법을 이야기했지만 구현 과정을 공개하지 않아 발표자는 같은 워크플로를 다시 구성해 시연합니다.

Shopify의 내부 도구 Helix는 기존 앱의 화면 하나를 새 버전으로 옮기는 작업에서 화면을 읽고 체크포인트라는 작은 작업으로 나눕니다. 사람이 체크포인트를 먼저 검토하고 승인합니다. 각 체크포인트는 다음 작업으로 넘어가기 전에 네 가지 엄격한 검사를 통과해야 합니다. 대부분의 작업은 하위 에이전트가 맡습니다. 작업별로 별도 컨텍스트 창을 쓰기 때문에 긴 작업에서 중요한 정보를 잊는 일을 줄입니다.

이 워크플로의 중심은 체크포인트와 네 개의 게이트입니다. 게이트는 반드시 통과해야 하는 검토 단계입니다. 검사를 통과하지 못하면 다음 작업으로 넘어가지 않습니다. 앱 변환뿐 아니라 표준과 시각 품질을 지키면서 큰 기능을 만드는 데도 쓸 수 있습니다.

Helix는 내부 도구여서 발표자는 접근할 수 없습니다. 대신 데모 HR 프로젝트에서 재현 가능한 흐름을 만들었습니다. 오케스트레이터라는 단일 스킬에 요청하면 나머지 절차를 관리하며 사용자의 입력은 두 번만 필요합니다.

## 체크포인트로 큰 기능 나누기

체크포인트는 큰 기능을 작은 단위로 분해한 것입니다. 앞 작업이 끝나기 전에는 다음 작업을 시작하지 않고 난이도가 낮은 작업부터 순서대로 진행합니다. 각 단계가 앞 단계 위에 쌓이므로 초기 결정이 틀렸을 때 작고 저렴하게 발견할 수 있습니다.

Checkpoint Planner 에이전트는 큰 기능을 체크포인트로 나눠 JSON 파일에 씁니다. JSON은 에이전트가 이해하고 필요한 정보를 찾기 쉽지만 사람이 직접 읽기에는 불편하므로 계획을 보여주는 간단한 웹 뷰어도 만들었습니다. 오케스트레이터는 앱의 현재 상태와 실행 여부를 확인하는 에이전트, 체크포인트 계획 에이전트를 동시에 시작합니다. 계획 에이전트는 모르는 점을 사용자에게 묻고, 뷰어는 순서, 진행 상태, 완료 조건을 보여줍니다. 테스트 계획 에이전트는 각 체크포인트를 어떻게 검증할지 미리 문서화합니다.

사람은 계획을 자세히 읽고 누락된 기능이 없는지 확인해 수정 요청을 하거나 승인합니다. 구현에 에이전트 시간을 쓰기 전에 검토하는 단계가 중요합니다.

## 게이트 1: 동작 검증

프롬프트나 파일에 적힌 규칙은 조언일 뿐 에이전트가 잊을 수 있습니다. 게이트는 통과하기 전에는 다음 작업을 허용하지 않습니다. 발표자 팀은 에이전트가 멈추려 할 때마다 훅을 실행해 게이트 상태를 검사하고, 아직 통과하지 않았다면 종료 코드 2로 중단시키는 방식을 구현했습니다.

첫 게이트는 브라우저 없이 검증할 수 있는 동작을 테스트합니다. 예를 들어 관리자가 직원의 휴가를 승인할 수 있는지는 버튼을 누르지 않고 코드로 검사할 수 있습니다. 체크포인트를 승인한 뒤에는 먼저 테스트를 작성하는 하위 에이전트를 실행합니다. 기능 코드가 아직 없으므로 테스트는 처음에 실패합니다. 다음 에이전트가 구현하고, 또 다른 에이전트가 테스트를 실행해 전부 통과하는지 확인합니다. 모든 테스트가 통과하면 첫 게이트를 완료 처리합니다.

## 게이트 2: UI 검토

Shopify는 앱을 다른 형태로 바꾸면서 디자인 일치를 확인하기 위해 Gemini 모델을 꼼꼼한 디자인 리뷰어로 사용했습니다. 발표자는 Gemini가 화면의 위치와 크기를 잘 파악해 두 화면 사이의 작은 간격 차이도 찾을 수 있다고 말합니다.

기존 기준 화면이 없는 프로젝트나 고객 작업에서는 먼저 HTML 프로토타입을 만들어 시각 방향을 빠르게 시연하고 승인받을 수 있습니다. Prototype 스킬은 한 파일 안에서 열고 클릭해 볼 수 있는 전체 프로토타입을 만듭니다. 프로젝트 디자인 가이드(`design.md`)를 따릅니다.

별도 비교 스킬이 프로토타입과 실제 앱의 시각적 모양과 상호작용을 비교합니다. 먼저 두 화면이 같은 상태인지 확인합니다. 예를 들어 제출 전 양식과 제출 후 양식은 서로 다른 상태입니다. 비교에는 Gemini 대신 새 세션으로 실행한 Claude를 사용했습니다. 필요한 체크포인트에서 두 개의 Claude 하위 에이전트를 병렬 실행해 하나는 모양을, 하나는 동작을 검토하게 합니다. 둘은 프로젝트 지침을 보지 않고 프로토타입과 디자인 파일만 기준으로 평가합니다. 오케스트레이터가 결과를 합쳐 게이트 통과 여부를 결정합니다. 브라우저 없이 대부분 검사하는 첫 게이트로 충분한 체크포인트는 UI 게이트를 생략합니다.

## 게이트 3: 적대적 코드 검토

기능이 작동하고 프로토타입과 비슷해도 코드 품질은 나쁠 수 있습니다. 이를 위해 Shopify는 자체 표준에 맞춰 코드에 반대하는 두 적대적 검토 에이전트를 사용합니다. 두 에이전트가 모두 승인해야 통과합니다.

발표자 구현에서는 한 에이전트가 코드가 잘못됐다고 가정하고 문제를 찾으며, 다른 에이전트가 그 문제를 수정합니다. `adversarial loop` 스킬이 둘 사이의 소통을 관리합니다. 앞의 동작·UI 게이트를 통과하면 비판 에이전트가 검토하고, 문제가 있으면 수정 에이전트가 고칩니다. 다시 비판 에이전트가 확인하며 승인할 때까지 반복합니다.

## 게이트 4: 사람의 검토

에이전트는 사람의 관점에서 검토할 수 없으므로 마지막에는 사람이 실제로 기능을 써봐야 합니다. 모든 체크포인트가 끝나면 원하는 대로 작동하는지, 더 좋게 바꾸거나 보완할 부분이 있는지 확인합니다. 수정 의견은 새로운 체크포인트로 바뀌어 같은 게이트를 통과하고, 피드백은 모든 에이전트가 작업 전에 읽는 학습 파일에 기록됩니다.

전체 절차는 오케스트레이터 스킬 하나가 운영합니다. 사용자는 체크포인트 계획 승인 때 한 번, 완성된 앱을 검토할 때 한 번만 멈춰서 입력합니다. 에이전트는 중간에 실수해도 되지만 미완성 작업은 게이트를 통과해 배포되지 않습니다. Shopify의 표현대로 시도는 틀릴 수 있지만, 출시는 틀린 채로 하면 안 됩니다.
