# 한국어 번역

저는 Lauren입니다. Potato on X라는 이름으로 알려져 있고 SpaceX AI에서 Grokbot을 맡고 있습니다. 지난달 프로덕션에 PR 2,000개를 반영했습니다. 이 일을 가능하게 한 것은 신뢰입니다. 제가 자리에 없어도 에이전트가 좋은 품질의 일을 하리라 믿을 수 있어야 합니다. 에이전트에 맞게 환경을 잘 꾸리면 높은 품질의 코드를 더 빠르게 만드는 개인 또는 팀 작업 공간을 만들 수 있습니다.

저는 조립 라인의 소프트웨어 공장보다 미슐랭 주방 비유를 선호합니다. 제품 개발은 창의적인 일이고 어느 정도 예술입니다. 에이전트가 재료를 직접 다루더라도 최종 결과에 대한 책임은 사람에게 있습니다. 작업자와 부주방장, 장비, 훈련, 설거지 인력의 구성 모두 결과에 영향을 줍니다.

## 병목에서 신뢰 구축으로

Cursor에 합류했을 때 Cursor IDE의 에이전트 창을 대체하는 새 제품은 성능 문제가 많았습니다. React 팀 경험이 있어 성능 개선을 맡았지만, PR이 빠르게 쌓여 앱 성능이 후퇴하는지 확인하는 일이 버거웠습니다. 처음에는 Chrome DevTools, 성능 추적, 힙 스냅샷을 수동으로 살폈습니다.

그래서 에이전트가 앱을 직접 실행하고 추적을 수집·분석해 병목을 찾아 성능을 개선하도록 하는 검증 스킬을 생각했습니다. 지난 6개월 동안 제품 생산성이 크게 늘었습니다. PR 2,000개를 목표로 삼은 것은 아니지만, 스킬과 도구, 코드베이스 개선을 쌓은 결과 에이전트에 대한 신뢰가 높아졌습니다. 엔지니어인 제가 병목이 되지 않도록 지식을 에이전트 팀에 전달하는 것이 핵심이었습니다.

처음에는 에이전트 대화를 계속 지켜보며 방향을 고쳐야 합니다. 이 단계에서 벗어나기 어려운 이유는 신뢰가 부족하기 때문입니다. 신뢰 없이 에이전트 100개를 병렬로 띄우면 쓸모없는 PR, 회귀, 버그가 늘어날 뿐입니다.

## 검증 스킬과 기능 지도

검증에는 여러 단계가 있습니다. 가벼운 단계는 에이전트가 앱을 실행하고 Chrome DevTools Protocol 같은 도구로 성능 추적과 힙 스냅샷을 수집하고 디버깅하도록 가르치는 것입니다. 형식 검증이나 Lean, TLA+로 비즈니스 불변 조건을 검증하는 방식은 더 어렵고 여전히 열린 과제입니다. 형식 기법을 쓰지 못하더라도 검증 스킬만으로 많은 것을 할 수 있습니다.

Lauren이 Cursor 에이전트 창에서 처음 만든 `Control Glass` 스킬은 에이전트가 앱을 실행하고 Chrome DevTools Protocol로 추적을 남기게 합니다. 반복 가능하게 앱을 실행하고 경험적 증거를 수집하려면 매 세션마다 다른 스크립트를 만드는 대신 스킬 폴더에 CLI를 두는 것이 좋습니다. CLI가 다양한 사용 사례와 실행 방식을 처리하도록 투자해야 합니다.

다른 요소는 기능 지도(feature map)입니다. 내부 사용자가 UI 일부가 보이는 작은 스크린샷과 물음표만 보내면, 앱을 실행할 수 있는 에이전트도 사용자가 무엇을 뜻하는지 추측해야 합니다. 기능 지도는 앱이 어떻게 작동하는지, 어떤 기능이 있고 사용자가 키보드 단축키나 DOM 요소를 통해 어떻게 접근하는지 기록하는 일종의 물질화된 메모리입니다. 스킬 디렉터리 안 코드베이스에 저장하고 자동화로 유지합니다.

CLI와 기능 지도를 합치면 에이전트가 앱을 재현 가능하게 제어하고 추적을 수집하는 동시에 내·외부 사용자의 요청을 이해할 수 있습니다. 자체 작업을 검증하는 능력이 에이전트에 대한 신뢰를 높여 이 스킬은 팀의 핵심 인프라가 됐습니다.

## 정확성에서 코드 품질까지

검증은 기능이 원하는 동작을 하는지 경험적 증거로 확인합니다. 하지만 성능이나 코드 품질까지 알려주지는 않습니다. 이를 위해 에이전트가 숙련된 소프트웨어 엔지니어처럼 일하도록 하는 스킬이 필요합니다. Lauren이 만든 PAC 플러그인은 디버깅, 기능 개발, 프로토타이핑 등 다양한 작업에 자신이 사용한 절차를 스킬로 묶습니다. 경험 많은 엔지니어는 팀 공용 스킬 저장소에 작업 방법을 기여할 수 있습니다.

코딩 스킬과 검증 스킬을 결합하면 기능이 맞게 동작하는지뿐 아니라 품질이 좋은지도 확인할 수 있습니다. 실제 성능 수치, 통계, 텔레메트리도 얻을 수 있습니다.

## 에이전트 친화적 코드베이스

코드베이스와 아키텍처를 에이전트에 맞게 리팩터링하는 것도 중요합니다. 앞으로 에이전트가 대부분 코드를 쓸 것이라면 올바른 동작이 기본값이 되도록 코드베이스를 설계해야 합니다. 에이전트는 기존 패턴을 확장하는 경향이 있으므로 코드베이스 자체가 중요한 메모리입니다.

정적 분석, 린터, 컴파일러 진단, CI는 반복 오류를 제약으로 막습니다. 더 나아가 데이터 구조나 아키텍처를 바꿔 잘못된 패턴이 아예 불가능하게 만들 수 있습니다. 규칙, BugBot, 스킬은 가이드로 쓸 수 있지만 에이전트가 잊거나 사용자가 무시할 수 있어 강제 수준은 낮습니다. 스타일 가이드만으로 검토하면 사람이 모든 변경 줄을 읽어야 하므로 PR이 많아질수록 감당하기 어렵습니다.

Lauren은 코드베이스와 아키텍처로 나쁜 선택을 불가능하게 하고, 정적 분석을 적용한 뒤 규칙·BugBot·스킬을 보완적으로 두는 순서를 권합니다. 기존 안티패턴은 바이러스처럼 에이전트에 복제될 수 있습니다. 작은 우회가 코드에 있으면 에이전트가 이를 복사해 며칠 또는 몇 주 만에 사실상의 표준으로 만들 수 있습니다.

Grokbot 코드베이스의 `Dune` 프레임워크는 에이전트가 지름길을 좋아한다는 점에서 출발했습니다. 쉬운 경로가 올바른 경로가 되도록 프레임워크를 설계했습니다. 사람에게는 제약이 많고 다소 불편할 수 있지만, 컨텍스트가 적은 에이전트와 디자이너·PM·CEO 같은 비엔지니어 기여자가 기본적으로 잘 작업하도록 돕습니다.

## 자동화로 팀의 처리량 높이기

Grokbot 루틴을 통해 Slack 스레드와 Sentry 경보를 구독해 자동 작업을 시작할 수 있습니다. 코드베이스, 규칙, 스킬을 함께 사용하면 외부 이벤트에 반응해 클라우드 에이전트를 실행할 수 있습니다. Cursor 자동화와 SDK로 추가 봇을 만들고 이미 구축한 에이전트 인프라를 재사용할 수도 있습니다. 발표자의 팀은 버그 보고서를 자동 재현하고 PR을 여는 자동화를 운영합니다.

신뢰 그래프를 올라가려면 환경을 신뢰할 수 있도록 구성해야 합니다. 에이전트 작업을 병렬화하고 팀 전체가 인프라 위에 쌓아 생산성과 코드 품질을 높일 수 있습니다. 에이전트를 고칠 때마다 코드베이스·아키텍처·자료구조로 오류를 불가능하게 할지, 정적 분석으로 막을지, 규칙과 BugBot·스킬로 안내할지 순서대로 생각합니다. 이 구성은 많은 투자가 필요하지만, 환경을 신뢰하면 에이전트에 더 큰 자율성을 줄 수 있습니다.
