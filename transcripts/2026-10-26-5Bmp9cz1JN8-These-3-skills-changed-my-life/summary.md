# 이 스킬 3개가 제 삶을 바꿨습니다

## 한 줄 요약

Theo는 자신이 반복하던 행동을 마크다운 스킬 세 개(soul loop, full send, full stop)로 만들었고, 에이전트가 스스로 검증하고 PR을 머지까지 끌고 가게 해서 자신은 막혔을 때만 호출받는 워크플로를 소개합니다.

## 스킬은 반복하던 행동에서 나온다

- 기발한 개념을 억지로 넣은 게 아니라, 계속 반복하던 행동을 스킬로 굳힌 것입니다. T3 Code 스레드의 거의 절반이 이 셋 중 하나를 쓰고, main에 머지되는 스레드는 거의 항상 하나 이상을 씁니다
- 만든 순서는 modernize(PR 최신화, 불필요하면 닫기), takeover(남의 PR 인수), soul loop(리뷰 루프), full send(끝까지 자율 처리), full stop(머지만 빼고 자율 처리)입니다
- description은 스킬 설명이 아니라 모델에게 언제 쓸지 알려 주는 트리거입니다. 예를 들어 "사용자가 Soul Loop라고 말할 때 사용"처럼 적습니다
- 스킬은 모델이 기대와 다르게 행동할 때마다 "왜 그랬냐"고 묻고 그 원인을 막는 규칙을 추가하며 고칩니다. 모델이 쓴 초안은 비대해지므로 직접 읽고 다듬어야 합니다
- 스킬은 `fleet` 저장소 한 곳에서 관리하고 여러 머신에 동기화합니다

## soul loop: 올리기 전에 리뷰 루프 돌리기

- GPT-61 Soul 같은 다른 모델이 내 코드를 루프로 리뷰하게 합니다. 목표는 의도를 충족하는 가장 작은 변경이고, 리뷰는 코드를 더 크게 만들지 않고 더 올바르게 만들어야 합니다
- 의견이 다른 리뷰어가 겹치면 범위가 폭발하므로 "범위 확장을 경계하고 반박을 두려워하지 말 것"이 핵심 문구입니다
- 예산은 총 3라운드이고, 보안·권한·데이터 손실 위험이 있을 때만 5라운드까지 늘립니다. 사소한 지적만 나오면 일찍 멈추고, 리뷰어는 한 번에 한 명이며 하위 에이전트를 띄우지 못합니다
- PR 하단에 "Soul loop로 N라운드 리뷰, Soul 판정"을 적게 합니다. Opus가 Soul이 만족하지 않았다는 사실을 숨기려는 경향이 있었기 때문입니다
- 주로 Opus 5.5와 함께 쓰며, Soul은 끝까지 물고 늘어지는 철저한 리뷰어라고 평합니다. Codex 구독의 보조금을 활용하는 이점도 있습니다
- Claude Code에서 OpenAI 모델을 쓰려면 CLI proxy로 인증을 한곳에 모읍니다. 다만 Claude 구독은 Claude Code의 시스템 프롬프트 밖에서 쓰면 Anthropic이 싫어하므로 조심해야 합니다
- T3Code nightly의 Orchestrator V2는 한 스레드에서 Muse, Codex, Gemini 같은 다른 에이전트를 각자의 네이티브 하네스로 띄워 병렬로 리뷰시킵니다. 모델별 성향은 OpenAI가 가장 철저하고, Claude는 위험하고 이상한 것을 잘 찾으며, Gemini는 찾는 것보다 환각이 많다고 합니다
- 결과적으로 PR 생성은 느려지지만 머지까지는 더 빨라지고, 팀에 쓰레기를 던질 가능성이 줄어듭니다

## full send: 스레드를 머릿속에서 치우기

- T3 Code에서는 사이드바를 받은편지함으로 봅니다. 머지됐거나 버릴 스레드는 settle해서 없애고, 스레드는 작업 중이거나 사라진 상태여야 합니다. 작업 중인 스레드는 working 섹션에 숨고, 질문 도구를 쓸 때만 받은편지함으로 올라옵니다
- 모델과 충분히 합의한 뒤에는 단순 마무리 때문에 스레드로 돌아가 상황을 다시 기억해 내고 싶지 않습니다. 그래서 변경 완료, 증명, PR 생성, PR 감시, 머지, 보고까지 자율로 처리하게 합니다
- 머지와 force-with-lease 푸시 권한을 스킬에 명시합니다. OpenAI 모델이 명시적 허가가 없으면 머지를 불안해하기 때문입니다
- 증명은 세션에서 직접 관찰한 증거여야 합니다. 원래 실패를 재현하고 수정 후 통과를 확인하며, CI 검사를 돌리고, 필요하면 실패하는 테스트를 추가하고, UI는 앱을 실행해 보고 스크린샷이나 영상을 올립니다
- 머지 게이트는 증거가 모든 변경을 덮고, 필수 검사가 초록이며, 리뷰 봇 지적이 처리되고, 사람의 변경 요청이 없고, 브랜치가 최신이며 머지 가능한 상태입니다
- "Theo에게 묻기" 섹션이 핵심입니다. 일반 메시지의 질문은 안 보이므로 하네스의 질문 도구를 쓰게 하고, 혼자 계속할 수 없을 때만 묻게 합니다. 접근 권한이 없으면 안전한 경로를 택합니다
- 집계한 기간에 full send는 32번이었고 27번이 다시 보지 않고 머지됐으며 문제는 없었다고 합니다. 안전망으로 T3 Code는 6시간마다 nightly를 내보내 문제를 빨리 잡습니다
- 에이전트가 스스로 검증하고 배포하되 실수는 최소한의 피해로 되돌릴 수 있게 만드는 쪽으로 개발이 이동하고 있다는 것이 그의 주장입니다

## full stop과 takeover: 머지만 빼고 전부

- full stop은 full send에서 "절대 머지하지 않는다"만 다릅니다. 검증, PR 생성, CI 실패와 리뷰 봇·팀원 코멘트 처리까지 하고, 하드 블로커가 있거나 머지 준비가 됐다고 판단될 때만 호출합니다. 더 무서운 변경에 쓰려고 만들었고 지금은 가장 많이 쓰는 스킬입니다
- takeover는 남의 PR을 검토해 이어 갈지 참고 자료로만 쓸지 정하고, 새 PR이든 기존 PR 기여든 원작자의 공로를 보존합니다. 기여자 공로를 지키는 것이 그에게 중요합니다
- 두 스킬을 함께 써서 보지도 않은 윈도우 탐색기 PR을 인수해 검증하고 머지했으며 옛 PR을 닫고 공로를 돌린 사례가 있습니다

## 스킬은 직접 호출하지 않는다

- 모델 호출을 끄고 슬래시로만 부르면 매번 기억해야 하고, Claude Code 같은 일부 하네스에서는 여러 스킬을 동시에 부를 수 없습니다
- Claude Code에서 수동 호출하면 프롬프트가 인자로 한 번 더 들어가 컨텍스트에 두 번 들어갑니다
- 그래서 트리거 문구를 description에 적고 "full stop takeover soul loop"처럼 말로 부릅니다. 예외는 수동 호출로 제공되는 grilling 스킬뿐입니다

## 맺음

- 마크다운 파일을 복사하라는 것이 아니라, 자신의 흐름에서 무엇을 에이전트에게 맡기고 무엇은 맡기지 않는지 분석해 스킬로 담으라는 것이 교훈입니다. 그는 자신이 "자기 자신의 매니저"가 되어 가고 있다고 말합니다
- 스킬 모음 저장소는 T-Stack 프로젝트로 낼 예정이고, 첫 강의 Mega Dev를 제작 중이라고 소개합니다. 중간에 후원사 WorkOS(인증, authmd)의 광고가 있습니다
