# NVIDIA Just Built a Sandbox That Knows When to Say No (Openshell)

## 결론부터

Docker 컨테이너만으로는 AI 코딩 에이전트가 무엇을 할 수 있는지 충분히 제한하지 못한다고 보고, NVIDIA의 오픈소스 샌드박스 OpenShell을 소개합니다. 발표자는 파일·프로세스·네트워크 접근을 요청 단위로 허용하거나 막는 정책 계층이 에이전트 운영의 핵심이라고 결론짓습니다. 다만 단순한 격리가 필요하다면 기존 방식으로 충분하다고 덧붙입니다.

## 핵심 내용

- **정책 기반 검사:** 에이전트가 접근하는 파일, 시스템 호출, 네트워크 연결을 정책과 대조합니다. 게이트웨이, 샌드박스 안의 감독자(supervisor), 샌드박스 내부 에이전트의 세 부분으로 구성되며, 외부로 나가는 길은 감독자를 거칩니다.
- **요청 단위 규칙:** 같은 주소라도 어떤 프로세스(바이너리)가 어떤 엔드포인트에 무엇을 요청하는지 따로 판단합니다. 데모에서는 GitHub API 읽기는 규칙 추가 후 허용되고, 이슈 생성 요청은 같은 도구임에도 차단됐습니다.
- **자격 증명 주입:** 에이전트는 실제 키를 갖지 않고, 승인된 엔드포인트로 가는 요청에만 감독자가 키를 붙입니다. 프롬프트 인젝션으로 키를 유출하게 만들어도 가진 것이 없다는 논리입니다.

## 배울 점과 적용 조건

- **요청 단위로 권한 나누기:** "네트워크 허용 여부"가 아니라 "이 프로세스가 이 엔드포인트에 무엇을 할 수 있나"를 정책으로 쓰는 방식입니다. 에이전트에 토큰을 넘기는 구조라면 검토할 만합니다.
- **자격 증명을 에이전트 밖에 두기:** 키 주입을 프록시 계층에서 처리하는 설계입니다. 적용하려면 모든 외부 호출이 그 계층을 거치도록 구성해야 합니다.
- **전제와 비용:** 오픈소스(Apache 2.0, Rust)이며 Docker, Podman, Kubernetes, microVM 위에서 동작합니다. Mac에서는 Docker Desktop의 Linux VM이 landlock 커널 기능을 필요로 하고 호스트 네트워킹을 켜야 합니다. 영상은 이 설정의 상세 절차를 보여 주지 않습니다.

## 근거와 한계

- **영상의 근거:** 샌드박스 상태 확인, 권한 없는 실행 확인, 허용되지 않은 경로 쓰기 차단, 기본 차단 상태에서 curl 요청이 막히는 로그, 읽기 규칙 추가 후 GitHub API 조회 성공, 이슈 생성 요청 차단이 시연됩니다.
- **평가:** 시연은 기본 차단과 규칙 하나 추가에 그쳐 정책 문법, 여러 규칙의 상호작용, 실제 에이전트(Claude Code 등)를 감싸서 돌릴 때의 동작은 보여 주지 않습니다. 발표자가 인용한 수치(2주간 55만 개 샌드박스 생성, 에너지 행동 420만 건 거부, 생성 실패율 약 12%)는 NVIDIA 텔레메트리라는 주장이며 발표자도 감사된 수치가 아니라고 밝혔습니다. 다른 도구와의 비교(Docker, Anthropic 샌드박스 런타임, E2B, Daytona)도 발표자의 요약이며 측정 근거는 없습니다. Z3 기반 정책 검증 설명은 있으나 실제 검증 결과는 보여 주지 않습니다.
- **확인 범위:** 자막 기반 평가입니다. 프로젝트의 공개 시점, 스타(약 2만), 파트너 목록, 버전(0.1.5로 소개됨)은 외부에서 확인하지 않았습니다. 영상 내 주장은 모두 외부 미검증입니다. 보안 도구는 지원 범위와 기본 설정에 따라 결과가 달라지므로 도입 전 공식 문서와 릴리스 노트로 확인해야 합니다.
- **홍보성:** 특정 상업 제품 판매나 가입 유도는 보이지 않습니다. 다만 제품 비교 구도가 NVIDIA 공개 수치에 기대고 있다는 점은 감안할 필요가 있습니다.
