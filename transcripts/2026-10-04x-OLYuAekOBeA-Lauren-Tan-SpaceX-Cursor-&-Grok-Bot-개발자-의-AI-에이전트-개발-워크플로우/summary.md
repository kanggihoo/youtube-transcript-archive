# Lauren Tan(SpaceX - Cursor & Grok Bot 개발자)의 AI 에이전트 개발 워크플로우

## 한 줄 요약

에이전트에게 많은 일을 맡기는 힘은 프롬프트가 아니라 **직접 실행·검증할 수 있는 환경**에서 나옵니다. 앱 실행 도구, 코드로 굳힌 반복 절차, 나쁜 코드를 쓰기 어려운 구조, 버그 제보를 재현하는 외부 연결을 갖춘 뒤에야 표본 검토만으로 대량의 PR을 감당할 수 있다는 이야기입니다.

## 2,500 PR은 새 기능 수가 아니다

Laurent는 한 달에 PR 2,500개를 프로덕션에 머지했다고 밝혔지만, 이는 본인의 공개 실적일 뿐 새 기능의 수가 아닙니다. 처음부터 여러 에이전트에 나눠 맡긴 것도 아닙니다. 개인 프로젝트에서 계속 방향을 바로잡았고, 성능 로그와 메모리 상태를 직접 확인해 에이전트에 전달했습니다. 그래서 에이전트가 **직접 실행하고 관찰하는 도구**를 만드는 일부터 시작했습니다. 많은 일을 맡길 수 있다는 "신뢰의 사다리"는 자신 있는 답변이 아니라 결과를 검증하고 고칠 수 있는 환경에서 올라갑니다.

## 가장 중요한 스킬은 검증이다

에이전트에게 "손과 눈"을 주는 것입니다. 코드를 실행하고, 사용자처럼 앱과 상호작용하고, 트레이스와 스냅샷으로 디버깅하게 합니다. Cursor에 합류해 처음 만든 스킬이 이것이었습니다.

- 테스트 통과 보고로 끝내지 않고 실제 앱을 열어 버튼을 누르고 화면과 실행 로그를 확인
- **기능 지도**(기능 위치와 클릭 시 동작)를 실행 도구에 함께 제공. 작은 캡처만으로 문제를 찾으려면 필요하고, 앱이 바뀌면 지도도 갱신
- 검증마다 새 스크립트를 짜게 하면 실행 방식이 매번 달라지므로 반복 실행 도구를 미리 준비

## 반복 절차는 코드로, 판단은 에이전트에

에이전트와 스킬은 전적으로 판단이 필요한 일부터 기계적인 일까지 이어지는 스펙트럼입니다. 한 패턴을 다른 패턴으로 바꾸는 리팩터링 같은 결정적 부분은 에이전트가 매번 새로 궁리할 이유가 없습니다. 그래서 **결정적인 부분은 CLI 같은 코드로 빼내고 판단이 필요한 부분만 에이전트에 남깁니다.** 성능 문제는 측정, 가설, 수정, 재측정 순으로 돕니다.

## 나쁜 코드를 쓰기 어려운 구조

에이전트는 기존 코드를 읽고 따라 하므로, 예외와 임시 우회책이 흩어져 있으면 비슷한 패턴이 늘어납니다. 같은 실수를 채팅에서 반복 지적하는 대신 실수가 어렵도록 구조를 바꿉니다.

- 관례적 패턴과 린트 규칙으로 일을 하는 방법을 사실상 하나로 제한
- 기능마다 전용 디렉터리를 두고 레지스트리가 발견. 갓 파일에 덧붙이지 않음 (Grokbot 초기 버전이 100줄 넘는 갓 파일 여덟 개였던 데서 나온 방식)
- P-stack은 버그 조사·기능 구현·성능 개선 워크플로우를 담은 스킬 모음이지만, **설치만으로 검증 환경이 생기지는 않습니다**

## 안쪽 루프와 바깥쪽 루프

코드 안에서 수정하고 검증하는 흐름이 안쪽 루프, 외부 맥락을 받는 흐름이 바깥쪽 루프입니다. Slack MCP나 채널 구독을 붙이면 버그 제보가 올 때마다 에이전트가 앞서 만든 검증 스킬로 재현을 시도합니다. 버그가 main에도 있는지, 사용자 환경·데이터·의존성 미설치 탓은 아닌지까지 확인합니다. 두 루프를 연결하는 것이 스스로를 확장하는 핵심이라고 봅니다. 비슷한 제보에 에이전트를 각각 붙이면 같은 문제를 중복해서 고치므로 전체를 보는 **조정자 역할**도 생깁니다.

## 모두 읽지 않고 표본을 엄격하게 본다

나쁜 패턴을 발견해도 바로 고치지 않고 문서에 모읍니다. 기록이 쌓이면 공통 원인이 보입니다. 많은 변경은 공장의 품질 감독자처럼 **표본을 뽑아 매일 엄격하게** 봅니다. 문제 하나를 고치고 끝내지 않고, 같은 문제가 다시 생길 환경인지 돌아보며 스킬·타입·제약을 조정해 사람이 개입할 지점을 줄입니다.

## 쉽지 않다는 단서

본인이 직접 말합니다. 여기까지 오는 건 매우 어렵고 PAC 같은 도구로 쉽게 되는 게 아니며, 에이전트가 실패하는 지점을 보고 설정과 제약을 의도적으로 만드는 데 많은 시간이 듭니다.

- 검증을 여러 번 돌리면 토큰 비용이 든다
- 되돌리기 어려운 변경이나 프로그램으로 검증하기 힘든 분야에는 답이 없다고 인정
- 무엇을 만들지 전달하고 결과를 판단하는 도메인 전문성이 더 중요해졌다

진행자의 적용 팁은 내 작업에서 에이전트가 멈추는 지점(앱 실행, 기능 위치 설명, 같은 코드 패턴 반복 수정)을 찾고, 지점마다 필요한 도구와 구조가 다르다는 점을 보라는 것입니다.
