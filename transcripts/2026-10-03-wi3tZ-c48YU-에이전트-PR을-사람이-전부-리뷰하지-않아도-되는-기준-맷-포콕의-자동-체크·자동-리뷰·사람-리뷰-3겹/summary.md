# 에이전트 PR을 사람이 전부 리뷰하지 않아도 되는 기준 — 맷 포콕의 자동 체크·자동 리뷰·사람 리뷰 3겹

## 한 줄 요약

에이전트가 PR을 쏟아내는 시대에 리뷰가 막히는 이유는 사람이 느려서가 아니라 사람에게 닿는 PR의 품질이 낮아서입니다. 맷 포콕은 자동 체크, 자동 리뷰, 사람 리뷰의 3겹 브레이크로 앞단에서 걸러 내고, 사람의 시간은 되돌릴 수 없는 결정에만 쓰라고 말합니다.

## 소프트웨어 팩토리에는 브레이크가 필요하다

일을 시작시키는 주체가 사람이 아니라 시스템인 공장이 소프트웨어 팩토리입니다. 서버 오류나 느린 쿼리 리포트가 분류 에이전트를 거쳐 작업이 됩니다. 이 가속에 브레이크가 없으면 손댈 수 없는 PR이 쌓이는 슬롭 캐논이 됩니다. 코드는 에이전트가 일하는 환경이라 나쁜 코드가 더 나쁜 코드를 낳기 때문입니다. 브레이크는 세 겹입니다.

- **자동 체크**: 린트, 테스트, 타입 체크 등 매번 같게 동작하는 결정적 검사
- **자동 리뷰**: 테스트가 못 잡은 것과 코드베이스 구조를 보는 에이전트
- **사람 리뷰**: 마지막 층. 앞의 둘에 기대 빠르게 만드는 것이 목표

## 자동 체크는 싸지만 거짓말을 한다

체크는 토큰도 사람 노력도 안 들고 CPU만 쓰니 훨씬 많이 얹어도 됩니다. 그러나 초록불이 머지 가능을 뜻하지는 않습니다. 뒤의 두 층은 자동 체크의 거짓말을 찾는 탐지기입니다. 발표자가 자기 에이전트의 테스트에서 찾은 거짓말 유형은 세 가지입니다.

- **동어반복 테스트**: 구현을 그대로 다시 단언합니다(예: X 글자 수 제한 상수가 280인지 확인). 상수 값이나 이름만 바꿔도 깨집니다. 발표자는 Opus 5가 특히 즐겨 썼다고 합니다
- **소스 구조에 묶인 테스트**: 렌더링하지 않고 소스 파일을 읽어 요소 순서를 단언합니다. 소스 모양만 바꿔도 실패합니다
- **실패할 수 없는 테스트**: 모킹으로 Audio Context 같은 API를 가짜로 대체해 실제 오류 모드를 가립니다. 프로덕션에서야 이상한 오류가 드러납니다

AI가 나쁜 테스트를 쓰려는 게 아니라 지시를 받아 실행 가능한 테스트를 쓸 뿐이라고 짚습니다.

## 딥 모듈: 설계로 체크를 속이기 어렵게

해법은 테스트가 아니라 코드베이스 설계입니다. 존 오스터하우트의 딥 모듈은 단순한 인터페이스 뒤에 큰 구현을 숨깁니다. 인터페이스에서만 테스트하면 구현을 바꿔도 깨지지 않고, 에이전트가 구현 세부를 건드리는 테스트를 쓰기 어려워집니다. 발표자는 이를 위해 모듈을 깊게 만들 기회를 HTML로 보여 주는 스킬과, 팀이 공유할 용어(locality, leverage, seam)를 정의한 코드베이스 설계 스킬을 소개합니다.

## 코딩 표준은 구현이 아니라 리뷰 에이전트에게

사람들은 코딩 규칙을 `CLAUDE.md`나 `agents.md`에 넣지만, 구현 에이전트는 이미 탐색, 수정, 디버깅으로 컨텍스트가 과부하입니다. 표준까지 얹으면 성능이 떨어집니다. 대신 diff와 저장소의 coding standards 파일을 읽는 코드 리뷰를 서브에이전트로 따로 돌립니다. 리뷰는 부하가 적어 표준을 많이 얹어도 잘합니다.

- 구현은 동작하게 만들고, 리뷰는 좋게 만드는 두 단계입니다. 발표자는 이를 컨텍스트 윈도우를 둘로 나눈 레드-그린-리팩터에 비깁니다
- 코딩 표준을 전역 범위에 두면 구현을 뒤덮어 잘 안 됩니다

## 자동 리뷰는 외주 말고 직접, 코멘트 말고 커밋

Cursor Bugbot, CodeRabbit 같은 서비스는 범용이라 너무 일반적이면 오탐이, 너무 구체적이면 특정 언어에만 묶인다고 합니다. 직접 만들어 코딩 표준을 팀이 쌓고 공유하라는 것이 조언입니다. 리뷰 에이전트가 코멘트만 달면 사람 리뷰어에게 읽을 거리만 늘립니다. 기본값은 직접 고쳐 커밋하는 것이고, 의문이 있을 때만 코멘트를 남깁니다.

## 사람 리뷰: 일방통행 문에만 시간을 쓴다

아마존의 일방통행 문과 양방통행 문 비유를 가져옵니다. 대부분의 PR은 되돌릴 수 있는 양방통행 문이라 가볍게 보면 됩니다. 단, 실수로 6만 명에게 이메일이 나가는 변경이나 비용이 큰 마이그레이션, 데이터 손실이 따르는 변경은 일방통행 문입니다. 맷이 만들고 있는 PR 스킬(발표 시점에 개발 중)은 다음을 PR 본문에 넣습니다.

- **병합 위험 요약**: 되돌릴 수 있는지, 영향 범위가 얼마나 제한적인지, 잘못되면 얼마나 심각한지
- **변경 내용을 글 대신 그림으로**: Human Layer의 덱스가 만든 "show me" 스킬에서 빌려 온 아이디어로, 의사 코드와 머메이드·UML 다이어그램, 새 명령과 플래그 같은 짧은 요약으로 보여 줍니다

## 같은 지적을 두 번 하지 않는다: retro 스킬

사람이 리뷰할 때는 코드만이 아니라 그 코드를 만든 시스템을 봐야 한다는 세 번째 원칙입니다. 같은 코멘트를 두 번 쓰지 않는 것이 목표입니다. 새 스킬 retro는 세션, PR, 혹은 지난주 PR과 리뷰 전체를 받아 회고하고 다음을 제안합니다.

- 자동 체크와 coding standards 파일의 갱신
- 탐색 포인터: 에이전트가 정보를 얼마나 쉽게 찾았는지, `agents.md`에 포인터를 둘 수 있는지
- 도구 경제성: 토큰 효율을 높일 수 있는 도구
- 비대한 조종 파일과 스킬

사람 리뷰가 다음 리뷰의 품질을 높이는 복리 효과를 낸다는 것이 요점입니다. 맷의 스킬 모음은 이번 주 버전 1.3으로 공개될 예정이라고 합니다.
