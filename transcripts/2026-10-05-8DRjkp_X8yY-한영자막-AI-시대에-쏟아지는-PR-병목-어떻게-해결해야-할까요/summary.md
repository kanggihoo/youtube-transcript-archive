# AI 시대에 쏟아지는 PR 병목, 어떻게 해결해야 할까요?

## 한 줄 요약

Matt Pocock의 PR 병목 발표(원문 영어). 에이전트가 코드를 쏟아내는 소프트웨어 팩토리에는 속도를 늦춰 품질을 올리는 브레이크 세 겹(자동 체크, 자동 리뷰, 사람 리뷰)이 필요하며, 이렇게 앞단에서 걸러야 사람이 모든 PR을 읽지 않고 되돌릴 수 없는 한쪽 문 PR에만 집중할 수 있다고 말합니다.

## 소프트웨어 팩토리와 슬롭 캐논

- 소프트웨어 팩토리는 일의 시작을 사람이 아닌 에이전트와 결정론적 코드(오류 알림, PlanetScale 느린 쿼리 리포트 등)가 맡는 구조입니다. 중간에 Jev 같은 분류기가 "수정 작업으로 바꿀지, 재현 작업으로 바꿀지" 가릴 수 있다고 합니다
- 가속만 하면 건드릴 수도 없는 쓰레기 PR이 쌓이는 **슬롭 캐논**이 됩니다. 코드는 에이전트가 활동하는 환경이라 나쁜 코드가 더 나쁜 코드를 낳습니다
- 브레이크 세 겹: **자동 체크**(린트, 타입, 테스트) → **자동 리뷰**(에이전트) → **사람 리뷰**. 앞의 두 층에 기대어 사람 리뷰를 줄이는 것이 목표이고, 출시 코드의 품질이 오르면 개입 자체가 줄어듭니다

## 자동 체크는 저렴하지만 거짓말한다

- CPU 사이클만 들어서 얼마든지 쌓을 수 있는데 대부분 충분히 쓰지 않습니다. 하지만 초록색 CI가 머지 준비 완료를 뜻하지는 않습니다. 사람과 자동 리뷰는 **자동 체크의 거짓말을 찾는 탐지기**입니다
- 에이전트가 쓴 테스트의 거짓말 세 가지 (발표자가 실제 코드에서 발견)
  - **동어반복 테스트**: `expect(X_POST_CHARACTER_LIMIT).toBe(280)`처럼 구현을 그대로 다시 단언. 상수 이름만 바꿔도 깨질 만큼 구조에 민감합니다. Opus 5가 특히 중독된 듯하다고 합니다
  - **소스 파일을 읽어 순서를 확인하는 테스트**: 화면을 렌더링하지 않고 모듈 소스에서 요소 순서를 검사합니다. 소스 모양만 바꿔도 실패합니다
  - **절대 실패할 수 없는 테스트**: `useAudioBoost`의 AudioContext를 가짜 메서드로 대체해, 실제 오류 모드가 프로덕션에서 터져도 테스트는 못 잡습니다
- AI가 일부러 속이는 게 아니라 지시를 받아 구조에 묶인 테스트를 쓸 뿐입니다. 해법은 체크를 속이기 어렵게 만드는 것입니다

## 딥 모듈로 설계해서 가짜 테스트를 줄인다

- **딥 모듈**(Ousterhout, 『소프트웨어 설계의 철학』)은 큰 구현을 작은 인터페이스 뒤에 숨깁니다. 구현이 숨겨질수록 구조에 민감한 테스트가 줄고, 에이전트가 인터페이스로만 테스트하게 강제할 수 있습니다
- 형편없는 코드베이스에도 돌릴 수 있는 스킬이 있어 모듈을 깊게 만들 기회를 변경 전과 후가 담긴 HTML 문서로 보여 줍니다
- 팀이 같은 언어로 말하도록 **지역성**(관련 코드가 모여 있는 정도), **레버리지**(단순한 호출로 큰 가치를 얻는 것), **심**을 정의한 코드베이스 설계 스킬도 있습니다

## 코딩 표준은 구현 에이전트가 아니라 리뷰 에이전트에게

- 구현 에이전트는 탐색, 수정, 디버깅(체크 실행과 검증)만으로 이미 **과부하**입니다. 표준까지 얹으면 성능이 떨어집니다
- 표준은 전역 `agents.md`가 아니라 **`coding standards.md`**에 두고, **서브에이전트로 도는 코드 리뷰 스킬**이 diff와 그 파일을 읽어 검사하게 합니다. 리뷰는 구현과 디버깅이 없어 여유가 있어서 표준을 많이 넣어도 잘합니다
- 구현에서 동작하게 만들고 리뷰에서 좋게 만든다는 점에서 **레드-그린-리팩터**와 같고, 컨텍스트 윈도우를 나눠 씁니다. 한 번에 좋은 코드를 얻으려는 시도를 멈추라고 합니다

## 자동 리뷰는 직접 만들고, 코멘트 대신 커밋한다

- Cursor Bugbot이나 CodeRabbit 같은 서드파티에 맡기지 말고 직접 만드세요. 범용 리뷰는 너무 일반적이면 오탐, 너무 구체적이면 쓸 수 있는 범위가 좁습니다. 아무도 읽지 않는 문서가 있다면 코딩 표준으로 옮겨 넣을 기회입니다
- 리뷰 에이전트가 PR에 코멘트만 달면 사람 리뷰어의 일이 늘어납니다. **리뷰어는 직접 수정해 커밋**하고, 의문이 있는 부분에만 코멘트를 답니다

## 사람 리뷰: 한쪽 문, 양쪽 문

- 아직 공개 전인 **PR 스킬**의 원칙: 모든 리뷰가 똑같이 중요하지 않습니다. AWS 용어로 PR이 **한쪽 문**(되돌릴 수 없음)인지 **양쪽 문**(되돌릴 수 있음)인지 분류합니다
- 대부분의 PR은 양쪽 문입니다. 하지만 단순한 변경이 실수로 6만 명에게 이메일을 뿌리거나, 비싼 마이그레이션이나 데이터 손실이 따르면 한쪽 문이라 철저히 봐야 합니다
- 모든 PR 맨 아래에 **머지 위험**(문의 종류와 영향 범위)을 요약해 둡니다. 양쪽 문에 영향 범위가 국소적이면 가볍게만 봅니다
- 변경 내용은 텍스트 대신 **의사 코드와 다이어그램**(mermaid, UML)으로 보여 줍니다. Dex Holley의 Human Layer 저장소 `show me` 스킬을 참고했습니다

## 같은 코멘트를 두 번 쓰지 않기: retro

- 사람이 리뷰할 때는 코드뿐 아니라 **코드를 만드는 시스템**을 리뷰하는 것입니다. 같은 지적을 두 PR에 걸쳐 반복하면 안 됩니다
- 새 스킬 **retro**는 세션, PR과 세션, 혹은 지난주 PR과 리뷰 전체를 불러와 회고하고 자동 체크와 `coding standards.md` 개선안을 제안합니다. 사람 리뷰가 다음 리뷰의 품질을 올리는 복리 효과입니다
- 그 밖에 탐색 포인터(`agents.md`에 길 안내를 넣을 수 있는가), 도구 경제성(토큰 효율), 조향 파일과 스킬의 비대화를 봅니다. 밖에서는 디버깅하기 어려운 것들을 많이 잡는다고 합니다
- 결론: 자동 체크와 자동 리뷰를 겹겹이 쌓고 사람 리뷰는 필요한 만큼만 수월하게. **모든 양쪽 문을 리뷰할 필요는 없고, 모든 한쪽 문은 리뷰한다.** 스킬은 aihero.dev/skills에 있고 v1.3은 이번 주에 출시 예정이라고 합니다
