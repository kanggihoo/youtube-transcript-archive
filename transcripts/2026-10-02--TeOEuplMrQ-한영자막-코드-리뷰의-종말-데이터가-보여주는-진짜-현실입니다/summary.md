# 코드 리뷰의 종말: 데이터가 보여주는 진짜 현실입니다

## 한 줄 요약

Arize AI의 Laurie Voss(npm 공동 창업자)는 코드 리뷰가 죽은 것이 아니라 **사람이 줄 단위로 읽는 일에서, 리뷰 시스템(하네스·규칙·평가)을 설계하는 일로 올라가고 있다**고 결론짓습니다. 결론적 조언은 PR을 읽는 데 시간을 쓰지 말고 신뢰할 수 있는 리뷰 하네스를 만드는 데 쓰라는 것입니다.

## 코드는 8배 빨라졌는데 출시는 30%만 늘었다

경제학자 세 명이 GitHub 개발자 10만 명 이상을 추적한 결과, 자율 에이전트를 켠 개발자는 코드를 741% 더 썼지만 출시된 소프트웨어는 30% 늘었을 뿐입니다. 저자들은 병목이 리뷰라고 단언합니다. 코드를 만드는 비용은 싸졌지만 믿어도 되는지 아는 비용은 여전히 비쌉니다. Stripe의 5천만 줄 Ruby 마이그레이션(하루), Bun의 100만 줄 Zig→Rust 포팅(6일)처럼 생성은 더 이상 병목이 아닙니다.

## 더 열심히 읽는 것은 답이 아니다

Cisco의 20년 전 연구(리뷰 2,500건, 코드 320만 줄)에 따르면 리뷰어는 한 번에 400줄, 시간당 450줄을 넘기면 결함 탐지 효과가 급락합니다. 이 속도면 에이전트 PR 하나(1만 줄)에 사나흘이 걸리고, 개발자는 에이전트를 열두 개씩 돌립니다.

## 테스트 통과는 머지 가능이 아니다

- **METR**: SWE-bench 채점기를 통과한 PR을 현역 메인테이너가 보니 머지할 만한 것은 약 절반. 실패 이유는 코드 품질과 테스트 바깥 코드를 조용히 깨는 변경
- **FrontierCode(Cognition)**: 메인테이너 20명 이상이 150개 과제로 "머지하겠는가"를 채점. Fable 5는 SWE-bench Pro 88%인데 가장 어려운 구간은 29%(51포인트 차). GPT 5.5는 6% 미만
- Sarah Guo의 논지: 컴파일러와 테스트는 공짜 검증기라서 모델이 코드 생성에서 빨리 좋아졌고, 머지 가능성 벤치마크가 생기면 곧바로 **프론티어 모델의 학습 신호**가 됩니다. 오늘의 리뷰 기준이 내년의 기본 모델 행동이 된다는 뜻입니다 (선례: 2024년 CriticGPT)

## 자동 리뷰는 이미 주류다

- **GitHub Copilot 리뷰어**: 6천만 건, GitHub 전체 리뷰의 5건 중 1건 넘게
- **Cursor**: 초기에는 diff마다 리뷰 패스 8번에 순서를 섞어 오탐을 걸렀음. 베이징대 연구도 다중 패스로 품질 최대 44% 향상. 재구축 때는 모델에게 "코드를 기본적으로 믿지 말고 문제가 있다고 가정하라"고 지시해야 했음. 리뷰어가 수정 에이전트를 띄워 패치까지 내는 방향으로 리뷰와 수리가 융합 중
- **CodeRabbit**(1,300만 PR 이상), **Graphite**(저장소 그래프, 개발자 수락·거절로 평가 세트 구성)
- 이들 모두 성공 지표가 **사람의 수락**이고, Cursor의 해결률은 52%에서 70% 이상으로 올랐음

## 사람을 완전히 뺀 실험들의 실상

- **Carlini의 C 컴파일러**: 에이전트 16개, 약 2,000 세션으로 리눅스 커널 컴파일. 루프에 사람은 없었지만 테스트 하네스와 피드백 시스템은 사람이 썼음(사람은 루프 "위에" 있었음)
- **Bun의 Zig→Rust 포팅**: 테스트 99.8% 통과. 그러나 unsafe 블록이 13,044개로, 비슷한 규모의 사람이 쓴 Rust 코드의 약 74개와 세 자릿수 배 차이. 테스트는 공개 인터페이스 동작만 보증
- **OpenAI**: 사람이 직접 쓴 코드 없이 5개월 만에 약 100만 줄, 머지 PR 약 1,500개, 엔지니어 3명. 리뷰를 없앤 게 아니라 에이전트 간 리뷰 루프, 앱을 부팅해 UI 확인, 로깅 스택 노출 같은 **시스템으로 옮김**. 금요일마다 AI 쓰레기를 손으로 치우다 이를 찾는 에이전트를 학습시킴
- **Dexter Horthy**: 6개월간 코드를 읽지 말라고 했다가 올해 3월 "틀렸다, 제발 코드를 읽으세요"라고 철회. 시스템의 큰 부분을 뜯어내야 했음

## 사람의 검증이 남는 자리

테스트는 이 모듈에 외부 사용자 세 곳이 있다거나 아무도 인정 않는 크론 잡이 의존한다는 맥락을 알려주지 못합니다. 그래서 사람의 체크포인트는 세 곳에 남습니다.

- 정확성을 싸게 확인할 수 없는 곳
- 영향 범위가 큰 곳 (보안 민감 환경 등)
- 결과에 누군가 이름을 걸어야 하는 곳

## 리뷰어를 누가 리뷰하나

자동 리뷰어는 속습니다. Anthropic의 자동 보안 리뷰어 README는 프롬프트 인젝션에 대비돼 있지 않다고 밝힙니다. 취약한 코드를 무해한 커밋 메시지로 포장하면 자율 리뷰 에이전트는 88% 속았고 사람 리뷰어는 35%만 통과시켰습니다. 채점기를 어떻게 채점할지에 대한 합의도 없습니다. 머지 전 리뷰가 전부 기계가 되면 남는 마지막 리뷰어는 **프로덕션**, 즉 코드가 실제로 한 일의 궤적입니다 (발표자는 Arize 홍보는 하지 않겠다고 밝힘).

## 오늘 당장 할 일

PR 리뷰는 2026년에 맞지 않는 추상화 수준입니다. "좋음"의 정의, 회사 맥락, 도메인 지식을 코드로 정리해 리뷰어·규칙·평가 계층에 투자하면 3분의 1 빨라지는 수준을 훨씬 넘을 수 있습니다. 이기는 팀은 코드를 가장 많이 만드는 팀이 아니라 출시한 것을 왜 믿는지 증거로 말할 수 있는 팀입니다.
