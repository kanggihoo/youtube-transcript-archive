# "좌석 잡아 두기"는 어떻게 구현할까? | 티켓 예매 좌석 선점, 실제로 어떻게 만들까

## 한 줄 요약

티켓 예매 시스템의 좌석 선점은 단순한 동시성 락을 넘어 원자적 조건부 갱신, 지연 만료(Lazy Expiration), 그리고 결제 중 타임아웃과 콜백 지연에 대응하는 `PAYMENT_PENDING` 중간 상태 설계를 통해 중복 판매(Double Booking)를 원천 차단해야 한다.

## 3단계 좌석 상태와 동시성 제어

- **2단계 상태(AVAILABLE, SOLD)의 한계**: 결제 진행 중인 수 분 동안 좌석을 'AVAILABLE'로 두면 중복 선점이 발생하고, 'SOLD'로 두면 결제 이탈 시 판매 기회를 영구 상실함
- **임시 점유 상태(HELD)**: 일정 시간 동안 특정 사용자에게 임시 점유권을 부여하는 리스(Lease) 구조 도입
- **원자적 조건부 업데이트(Atomic Conditional Update)**:
  - 비관적 락(Pessimistic Lock)의 대기 병목이나 분산 락의 인프라 복잡도 대신, 단일 SQL 쿼리로 조회·판단·쓰기를 원자적으로 실행
  - `UPDATE seats SET status = 'HELD', held_until = NOW() + INTERVAL 7 MINUTE, held_by = :userId WHERE seat_id = :id AND status = 'AVAILABLE';`
  - 갱신된 행이 1이면 선점 성공, 0이면 이미 다른 사용자가 선점한 것으로 판정

## 만료(Expiration) 처리의 2가지 전략

| 전략 | 동작 방식 | 장단점 및 실무 권장 |
|---|---|---|
| **지연 만료 (Lazy Expiration)** | 만료 시점에 DB를 직접 수정하지 않고, 다른 사용자가 해당 좌석을 조회하거나 선점 시도할 때 만료 시각(`held_until < NOW()`)을 체크해 판매 가능으로 간주 | DB 부하가 없고 즉시성이 높음. 단, 인기가 없어 조회가 없는 좌석은 헬드 상태로 유지되므로 통계/집계 시 만료 시각 필터링 필요 |
| **능동 만료 (Active Expiration)** | 백그라운드 스케줄러(Worker)가 주기적으로 만료된 좌석을 감지해 `AVAILABLE`로 일괄 업데이트 | 스케줄러 주기만큼 시간차가 발생할 수 있으나 유휴 좌석 정리에 유용 |
| **실무 권장** | **지연 만료를 기본 축으로 삼고, 보조 스케줄러로 잔여 유휴 좌석을 정리하는 하이브리드 조합** |

## 결제 완료와 만료가 겹칠 때: 중복 판매 방지 (`PAYMENT_PENDING`)

- **문제 상황 (콜백 지연 및 타임아웃)**:
  - 18시 6분 59초에 PG사 결제 승인이 났으나, 네트워크 지연으로 18시 7분 05초에 콜백이 도착
  - 시스템은 18시 7분 00초에 7분 만료로 판단하고 좌석을 회수하여 사용자 B에게 판매
  - 사용자 A와 B 모두에게 결제·판매되는 치명적인 **중복 판매(Double Booking)** 사고 발생
- **해결책: `PAYMENT_PENDING` 상태 도입**:
  - 결제 창 진입 및 PG사 호출 직전, 상태를 `HELD`에서 `PAYMENT_PENDING`으로 전이
  - `HELD` 상태에서 만료된 좌석만 즉시 회수하고, `PAYMENT_PENDING` 상태의 좌석은 만료 시각이 지나도 자동 회수하지 않고 보류
  - PG사 결제 결과가 타임아웃되거나 모호한 경우, PG 상태 조회 API를 능동 호출해 성공/실패 여부를 최종 확인할 때까지 좌석을 보수적으로 유지

## 아키텍처 의사결정 기준

예매 시스템에서 가장 위험한 리스크는 결제 미완료 좌석이 잠시 묶이는 것(회사 손실)이 아니라, 한 좌석이 두 명에게 팔려 고객 분쟁과 CS 대란이 터지는 것(신뢰 붕괴)입니다. 따라서 불명확한 결제 상태에서는 회전율보다 보수적인 안전 판매를 우선하는 상태 머신 설계가 필수적입니다.
