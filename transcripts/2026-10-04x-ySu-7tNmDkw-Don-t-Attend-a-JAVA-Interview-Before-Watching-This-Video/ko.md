**7:38** · 이것이 실제로 무슨 뜻인지 이해해 봅시다. 애플리케이션이 사용자를 관계형 데이터베이스에 저장해야 한다고 해 보죠.

**7:44** · 애플리케이션의 모든 서비스가 JDBC 코드를 직접 작성하길 원하지는 않을 것입니다.

**7:49** · 여기서 JPA가 등장합니다. JPA는 명세입니다. 객체-관계 영속성을 위한 표준 API와 규칙을 정의합니다. Hibernate는 그 명세의 구현체이고, Spring Data JPA는 JPA 위에 리포지토리 추상화를 제공합니다. 예를 들어 JPA 리포지토리를 상속해 사용자 리포지토리를 정의하면, 데이터베이스 접근 코드를 전부 직접 구현하지 않아도 흔한 리포지토리 연산을 얻게 됩니다.

**9:15** · @Transactional은 Spring의 트랜잭션 인프라가 트랜잭션 동작을 적용하는 데 사용하는 메타데이터이며, 흔히 프록시를 통해 적용됩니다. 즉 메서드를 어떻게 호출하느냐가 중요합니다. 예를 들어 기본인 프록시 기반 모드에서는 같은 클래스 안의 한 메서드가 다른 메서드를 직접 호출하면, 그 내부 호출은 Spring 프록시를 거치지 않습니다.

**9:36** · 따라서 두 번째 메서드에 @Transactional을 붙여도 자기 호출(self-invocation)에서는 트랜잭션 어드바이스가 자동으로 실행되지 않습니다. 그러니 "@Transactional은 롤백을 제공한다"고만 답하지 마세요. 트랜잭션 경계를 정의하며, Spring이 트랜잭션 인프라를 통해 그 동작을 적용한다고 설명하세요. 다음 질문에도 함정이 있는데, 특히 "우리는 인증에 JWT를 씁니다"라고 가볍게 말하는 경우입니다. 9번, Spring Security는 인증과 인가를 어떻게 처리하나요? 주문 API를 만들었고 모든 사용자가 모든 작업을 할 수 있어서는 안 된다고 해 보겠습니다.

### Q9. Spring Security는 인증과 인가를 어떻게 처리하나요?

**10:10** · 먼저 구분해야 할 것은 인증과 인가입니다.

**10:14** · 인증은 사용자가 누구인지 확인하는 것이고, 인가는 그 사용자가 무엇에 접근할 수 있는지 결정하는 것입니다. Spring Security는 이런 관심사를 처리하는 인프라를 제공하며, 현대적인 설정에서는 보통 보안 필터 체인을 다룹니다. 예를 들어 어떤 엔드포인트는 공개하고 어떤 엔드포인트는 인증을 요구하도록 정의할 수 있습니다. 여기서는 /public 아래 요청은 인증이 필요 없고 나머지는 모두 필요하다고 설정한 것입니다. 이제 중요한 구분입니다. OAuth 2.0과 JWT는 같은 것이 아닙니다.

**10:43** · OAuth 2.0은 인가 프레임워크이고 JWT는 토큰 형식입니다. 애플리케이션이 OAuth 2.0 리소스 서버로 구성되면 Spring Security는 JWT 베어러 토큰을 사용할 수 있습니다. OpenID Connect라는 말을 듣는다면, 이는 OAuth 2.0 위에 인증용 아이덴티티 계층을 더하는 관련 개념입니다. 그러니 보안을 설명할 때 그냥 "JWT를 씁니다"라고만 하지 마세요.

**11:10** · 사용자가 어떻게 인증되는지, 토큰이나 자격 증명이 어떻게 검증되는지, 인가 결정이 어떻게 내려지는지 설명하세요. 지금까지 애플리케이션이 어떻게 시작되고, 요청이 어떻게 처리되고, 데이터가 어떻게 저장되고, 접근이 어떻게 통제되는지 다뤘습니다.

**11:26** · 하지만 하나 더 다뤄야 할 것이 있습니다. 운영 환경에서 애플리케이션을 실행하는 일입니다. 10번, 운영 중인 Spring Boot 애플리케이션을 어떻게 모니터링하나요? 노트북에서는 완벽히 동작하던 애플리케이션을 운영에 배포했는데 문제가 생겼다고 해 보겠습니다. 그 시점에는 애플리케이션의 상태, 메트릭, 가용성에 대한 유용한 정보가 필요합니다. 여기서 Spring Boot Actuator가 등장합니다. Actuator는 운영 환경을 위한 관리·모니터링 엔드포인트를 제공합니다.

### Q10. 운영 중인 Spring Boot 애플리케이션을 어떻게 모니터링하나요?

**11:50** · 예를 들어 health 엔드포인트는 보통 /actuator/health로 노출됩니다. 어떤 관리 엔드포인트를 노출하고 보호할지도 설정할 수 있습니다.

**12:01** · 컨테이너 환경에서는 readiness와 liveness도 신경 쓰게 됩니다. liveness는 애플리케이션이 살아 있는지, 아니라면 재시작해야 하는지를 플랫폼에 알려줍니다. readiness는 애플리케이션이 트래픽을 받을 준비가 되었는지를 알려줍니다. 하지만 Actuator는 운영 관측성의 일부일 뿐입니다. 실제 시스템에서는 보통 로그, 메트릭, 트레이스도 함께 생각하며, Spring Boot는 메트릭과 관측을 위해 Micrometer와 통합됩니다.

**12:24** · 즉 Actuator는 애플리케이션에 유용한 운영 정보를 주고, 더 큰 관측성 구성은 시스템 전체에서 무슨 일이 일어나는지 이해하게 해줍니다. 그리고 이것이 이 10개 질문의 요점입니다. Spring 어노테이션을 따로따로 외우지 마세요. 생애 주기를 이해하세요.

### 마무리: 전체가 어떻게 맞물리는가

**12:42** · Spring 컨테이너가 객체를 만듭니다. Spring Boot가 애플리케이션을 구성합니다. Spring MVC가 요청을 처리합니다. 비즈니스 로직이 실행됩니다.

**12:51** · 영속성 계층이 데이터를 다룹니다.

**12:53** · 트랜잭션이 작업을 보호합니다.

**12:55** · 보안이 접근을 통제합니다. Actuator가 애플리케이션 모니터링을 돕습니다. 이 흐름을 이해하면 Spring Boot는 어노테이션 모음이 아니라 하나의 시스템으로 보이기 시작합니다. 그리고 그것이 바로 면접관이 원하는 것입니다.
