# Uber에서 디버깅 에이전트 하네스를 구축하는 방법 — Kriti Dangi

## 한 줄 요약

Uber의 Kriti Dangi가 버그 제보부터 근본 원인 분석, 수정, 검증, PR 생성까지 처리하는 디버깅 에이전트 Debug Assist를 소개합니다. 고정된 LangGraph 골격(하네스)에 팀별 스킬과 플러그인을 런타임에 꽂는 구조로 만들었고, PR 병합률은 5%에서 약 48%로 올랐으며 RCA 정확도는 개발자 수정안과 비교해 50%라고 합니다.

## 디버깅이 왜 어려운가

- Healthline(앱 품질 분석, 자동 수집)과 Wisdom(앱 내 버그 리포터, 사용자가 직접 제보)을 합쳐 매년 거의 5만 건의 이슈가 엔지니어에게 배정되고, 그중 90%는 고객에게 영향을 줍니다
- 오류 메시지는 불분명하고, 코드와 로그와 설정과 데이터가 흩어져 있으며, 여러 모노레포에 수많은 팀이 기여해서 누구 코드인지 찾는 것부터 일입니다
- Uber 엔지니어가 이슈 하나를 해결하는 데 평균 거의 28일이 걸리고, Stripe 공개 보고서에 따르면 개발자는 시간의 40%를 디버깅에 씁니다

## 발견에서 해결까지의 파이프라인

- 발견(Healthline, Wisdom), 자동 분류(우선순위, 심각도, 소유자, 당직자 지정), 30분 안의 심층 RCA, 해결 순서로 진행합니다
- 데이터를 개발자에게 던져 주는 데서 그치지 않고 실행 가능한 수정안까지 만드는 것이 목표입니다

## 실제 사례

- 택시를 기다리던 개발자가 "앱이 배터리의 30%를 쓰고 휴대폰이 뜨거워진다"고만 제보했는데, 그가 사무실에 도착하기 전 20분 사이에 Debug Assist가 수정안을 만들어 두었습니다. 원인은 백그라운드에서 돌아야 할 코드 경로가 포그라운드 루프처럼 취급된 핫 루핑이었고, 증거 타임라인이 함께 제시돼 환각이 아님을 확인할 수 있었습니다
- 푸시 알림을 빠르게 누르면 크래시가 나던 P1 이슈는 롤아웃 5% 단계에서 잡혀 당일에 수정안이 병합되고 배포됐습니다

## 계획은 사람이 쥐고 노드로 쪼갠 LangGraph

- 결정적 노드와 LLM 노드를 섞은 LangGraph 파이프라인입니다. 매번 따를 단계를 직접 정해 주기 때문에 LLM이 계획을 세우다 생기는 환각이 줄어듭니다
- 컨텍스트 수집은 일부러 LLM이 아닌 결정적 노드입니다. 단순한 데이터 조회에 지연과 비용을 더하지 않고, 메가바이트에서 기가바이트급 로그를 파싱하고 가지치기해야 하기 때문입니다
- 분류와 RCA 노드는 크래시가 Uber 코드 문제인지, 서드파티나 인프라나 네트워크 문제인지, PR이 필요한지 가르고 신뢰도 점수를 냅니다. 데이터가 모자라면 MCP로 Jaeger 트레이싱, 로그, 진행 중인 장애를 조회합니다
- 이후 서브에이전트를 병렬로 돌려 RCA를 하고 결과를 통합합니다. 사용자 타임라인을 복원하는 브레드크럼 분석과 크래시를 특정 릴리스와 연결하는 크래시 상관관계 에이전트가 예입니다

## 노드별 모델과 턴 수 제한

- RCA 노드는 주로 데이터를 보고 요약하는 일이라 더 낮은 모델인 Sonnet에서 제한된 턴 수로 돌립니다. 시행착오 끝에 20턴이 넘으면 대개 잘못된 방향으로 빠진다는 것을 알게 됐고, 이것이 가드레일 역할을 합니다
- 수정 노드는 수십억 줄의 코드베이스를 훑어야 해서 Opus를 더 많은 최대 턴 수로 씁니다. 이전 노드의 상태를 모두 물려받습니다
- 수정 전에 완화를 먼저 시도합니다. 이슈 대부분이 피처 플래그 뒤에 있어 피처 플래그 MCP로 상관관계를 찾고, 강하면 플래그를 롤백한 뒤 천천히 고칩니다

## 수정안을 스스로 검증하기

- 검증 노드가 단위 테스트, 통합 테스트, 컴포넌트 테스트 순으로 가장 짧고 단순한 경로로 이슈를 재현합니다. 코드로 재현이 안 되면 시뮬레이터와 에뮬레이터 자동화 테스트를 씁니다
- 공항 근처 약한 신호에서만 나던 이슈는 사용자 로그의 네트워크 강도, 배터리, 피처 플래그를 에뮬레이터에 재현하고 APK나 IPA를 빌드해 통과할 때까지 반복했습니다. 재시도 횟수에는 상한이 있고, 끝내 안 되면 수정안을 개발자에게 넘깁니다
- 만족스러우면 PR을 만들어 Jira와 Healthline, Wisdom 이슈에 연결하고 Slack으로 전달합니다

## 골격은 고정, 스킬과 플러그인은 탈착

- 골격은 바뀌지 않고, LLM 노드마다 자기 스킬(좋은 PR 작성법, 테스트 계획 관행, Android 수정법 등)을 갖습니다. 비즈니스 로직은 골격 바깥에 두고 런타임에 가져오므로 새 에이전트를 더하는 일은 스킬을 크라우드소싱하는 일이 됩니다
- 각 팀은 자기 전문 스킬만 가져오고 단계, 런타임, 의존성은 하네스가 제공합니다. 덕분에 하네스 팀이 모든 팀의 스킬을 유지보수하지 않아도 됩니다
- 현재 5개 모노레포에 걸쳐 거의 8개 에이전트가 하나의 코드베이스를 공유합니다. Python 모노레포에서 PEX 바이너리로 패키징하고, 에이전트 유형에 맞는 바이너리와 Docker 이미지를 받아 실행합니다
- 마켓플레이스 플러그인이 거의 3,000개라 전부 컨텍스트에 넣으면 에이전트가 이상해집니다. 에이전트 유형 파라미터로 가져올 것을 제한합니다

## PR 이후의 상호작용

- diff 수정기로 테스트 추가, 리팩터링, 변수명 변경 같은 작은 수정을 버튼 한 번과 한 줄 프롬프트로 맡길 수 있습니다
- Ask AI 채팅으로 RCA에 질문하고 수정 의견을 줄 수 있으며, 이 피드백 루프가 에이전트의 프롬프트와 스킬 개선에 쓰입니다
- 이슈와 환경이 이미 설정된 내 머신이나 원격 머신 풀에서 한 번 클릭으로 열어 직접 디버깅할 수도 있습니다

## 서브에이전트 통제와 관측성

- 모든 도구 호출, MCP 호출, bash 명령, 서브에이전트를 Arize 트레이싱으로 LangChain과 LLM 호출에 연결해 추적합니다
- 통제에서 가장 큰 요인은 최대 턴 수입니다. 20~30턴 안에 못 끝내는 작업은 대개 뭔가 잘못된 것입니다
- 서브에이전트의 입력도 가지칩니다. 문제 커밋을 찾는 에이전트에는 정상 버전과 문제 버전 범위를 주고 Rider, Driver, Uber Eats 같은 모듈로 히스토리를 걸러 줍니다
- 고유한 서브에이전트는 지금 약 30개이고, 도메인 소유자가 자기 서브에이전트와 지식 베이스를 꽂는 도메인 확장을 만들고 있어 다음 반기 말까지 약 10,000개로 늘 수 있다고 예상합니다

## 효과 수치

- 매달 거의 9,000건의 이슈에 심층 RCA를 제공합니다
- RCA 정확도는 실제 개발자 수정안과 비교해 50%이고, 나머지 중 약 40%는 올바른 모듈이나 파일 쪽으로 같은 방향이라 여전히 도움이 됩니다
- Jira 해결 시간은 거의 두 배로 좋아졌고, PR 병합률은 1년 전 5%에서 거의 48%로 올랐습니다
- 앞으로 커버리지와 사용 사례를 넓히고 정확도를 더 올리는 것이 목표입니다
