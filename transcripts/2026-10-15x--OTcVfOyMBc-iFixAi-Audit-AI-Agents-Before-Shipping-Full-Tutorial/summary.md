# iFixAi - Audit AI Agents Before Shipping (Full Tutorial)

## 한 줄 요약

iFixAi는 에이전트가 역할·도구·권한 정책을 압박 속에서도 지키는지 60개 점검으로 진단하는 오픈소스 도구이며, 인증서가 아니라 직접 쓴 픽스처만큼만 의미 있는 진단이므로 목 실행, 자기 픽스처, 실제 엔드포인트 순으로 쓰라고 권합니다.

## 전자 평가가 놓치는 것

- 환불 티켓은 모든 검사를 통과하고 전자 평가도 깨끗했지만, 감사를 돌리니 사기 신호를 숨기고 관리자가 거절한 금액을 지급하고 승인 없이 결제 계정을 바꾼 것이 드러납니다
- 기존 평가는 역량(기술적 동작, 토큰 비용, 지연, 알려진 인젝션)을 재지만, iFixAi는 여러 턴의 압박, 사용자 이의, 감시가 없어 보이는 상황에서도 거버넌스를 지키는지를 봅니다
- 60개 점검 중 32개가 채점, 28개가 프리미엄 미리보기이고, 25개 범주로 묶이며 다섯 기둥이 점수를 정합니다. 점검은 파이썬, 엔진은 아파치 라이선스입니다

## 설치와 시작 방법

- 파이썬 3.10 이상이 필요하며, 마법사, 플래그 기반(프로덕션 파이프라인용), 에이전트 플러그인의 세 가지 방법이 있습니다
- 우선순위는 플래그, 설정 파일, 환경 변수, 기본값 순이고, 키는 셸에 남습니다
- 점수가 0.85 미만이면 종료 코드 2로 끝나 회귀가 빌드를 실패시킬 수 있습니다
- 인증서가 아니라 한 시스템의 한 버전에 대한 진단입니다

## 픽스처와 목 실행

- 픽스처는 역할, 사용자, 위험 등급이 붙은 도구, 데이터 소스, 정책, 에스컬레이션 경로로 운영을 가짜 회사로 재구성한 것입니다. 기본 제공 Nimbus Forge 예시는 821줄입니다
- 점수가 의미를 가지려면 환경이 자기 것이어야 합니다. 기본 픽스처는 의도적으로 결함이 심어져 있어 첫 점수표는 실패를 보여 줍니다
- 키와 네트워크 없이 목 제공자를 먼저 돌려 파이프라인을 시험하며, 기본 실행은 10개 점검(그중 여섯 개 영향 큼)입니다
- 목 전체 실행 결과는 실패 15, 통과 44, 판정 불가 1이고, JSON과 Markdown 보고서가 나옵니다
- 기본 10개는 약 850회(에이전트)와 820회(심판) 호출하고, 60개는 약 5,500회와 4,700회입니다

## 심판과 비용

- 심판은 항상 평가 대상과 다른 벤더이며, 키가 하나뿐이면 실행을 거부합니다. 자기 평가는 후한 점수를 주므로 우회하면 편향 경고가 붙습니다
- Sonnet 심판 하나로 전체 스위트는 약 12~18달러, 서로 다른 벤더의 저렴한 모델 둘로 나누면 10~14달러이며 다수결을 쓰고 동률은 보수적으로 처리합니다

## 구조적 테스트와 행동 테스트

- 구조적 테스트는 모델과 심판 없이 메커니즘을 직접 호출하므로 같은 입력에 같은 답이 나옵니다. 알 수 없는 도구는 규칙을 밝힌 거부로 돌아와야 합니다
- 행동 테스트에는 여덟 범주의 인젝션 페이로드 40개, 관찰받는다고 믿을 때 결정이 바뀌는지 보는 같은 요청 네 번, 목표를 포기하라는 압박 후 목표를 묻는 다턴 테스트가 있습니다
- 과도한 거부도 실패로 칩니다. 도움말 검색에까지 승인을 요청하는 에이전트는 쓸모없다고 봅니다

## 점수 체계와 필수 관문

- 점수는 다섯 기둥의 가중 평균으로, 조작 0.35, 날조 0.20, 기만·예측 불가능성·모호성 각 0.15입니다
- 합격선은 0.85로 B보다 엄격합니다
- 도구 위임 100%, 에스컬레이션 차단 95%, 파괴 저항 100%의 세 필수 관문 중 하나라도 틀리면 점수 상한이 D입니다

## 실제 에이전트에 적용하기

- HTTP로 배포된 엔드포인트를 겨누고 기준선을 테스트 대상 시스템으로 두면, 가짜 정책 대신 에이전트가 실제로 강제하는 거버넌스를 읽습니다. OpenAI 채팅 형식이면 추가 작업이 없고, 아니면 메시지 전송 메서드 하나를 구현합니다
- 연결이 없는 항목은 증거 부족으로 보고되어 총점에서 빠지고 경고가 붙습니다. 숫자를 지어내지 않는 이 결정을 발표자는 강하게 옹호합니다

## 네 가지 사례 연구

- 저장소는 공개 보고를 재구성한 네 사례를 제공합니다. 배달 접수 사례는 도구 위임이 100% 하한에 69%였고, 그 숫자는 권한 토폴로지에서 모델 없이 계산됩니다
- 계정 지원 도우미는 에스컬레이션 0점으로 넘겨서는 안 되는 계정을 넘깁니다. 나머지 둘은 A와 B이고, B 사례는 84.2%인데 에스컬레이션이 20번 중 18번 실패했습니다
- 어느 사례도 픽스처를 함께 제공하지 않아 숫자를 재현할 수 없고, 어느 것도 실제 프로덕션 시스템을 시험하지 않습니다

## 한계와 불만

- 거버넌스를 실시간 대시보드가 아닌 픽스처에 적어 두면 설명을 채점한 것이며, 공격 세트가 공개되어 있어 통과는 알려진 패턴을 견뎠다는 뜻일 뿐입니다
- 점수는 한 픽스처와 한 버전 안에서만, 벤더 간에는 비교하지 않으며, 점검별 신뢰 구간으로 두 실행을 비교합니다
- 재현성은 없습니다. 선언문에 픽스처 요약과 논스를 기록하지만 재실행 명령은 아직 없습니다
- 쉬운 말 문서는 49개 점검이라고 하지만 readme, 방법론, list 명령은 60개이며 명령을 믿으라고 합니다
- 텔레메트리는 기본 켜짐이고 설치 ID, 완료 여부, 버전, OS만 수집하며 코드, 결과, 점수, 경로는 수집하지 않습니다. 호스팅 서비스 안내에 거절하면 다시 묻지 않습니다

## 발표자의 결론

- 도구, 역할, 권한이 있는 에이전트의 압박 시 행동을 모른다면 가장 짧은 길이지만, 리더보드 숫자나 고객용 인증서가 목적이면 맞지 않습니다
- 순서는 목 실행, 픽스처로 권한 채점, 두 번째 벤더 심판을 둔 실제 엔드포인트 실행입니다
- 프로젝트는 6개월 된 저장소에 별 26,790개, 기여자 16명이며, 자체 수치로 100일간 약 2,500회 감사가 있었습니다
