# Pocock vs Pstack vs Osmani: Which Skill Pack Wins?

## 한 줄 요약

Rob Shocks가 Addy Osmani의 agent-skills를 Matt Pocock의 스킬, Lauren Tan의 pstack과 비교합니다. 세 팩은 같은 기술을 다른 각도에서 본 것이고 모든 프로젝트에 다 필요하지 않으니, 읽고 쓸 만한 것만 골라 자기만의 스킬을 만들라는 결론입니다.

## Addy Osmani의 여섯 단계 라이프사이클

- Addy는 Google에서 Chrome 개발자 경험과 웹 성능을 이끌었고 최근 Anthropic으로 옮겼으며, agent-skills 저장소는 GitHub 스타 10만 개를 넘겼습니다
- 접근은 Define, Plan, Build, Verify, Review, Ship의 여섯 단계이고 단계마다 슬래시 커맨드가 있습니다. 은유 없이 SDLC를 에이전트와 제대로 수행하는 방식이라 기존 개발팀이나 기업에 잘 맞는다고 봅니다
- spec은 코드 전에 PRD를 쓰고, plan은 인수 기준이 붙은 원자적 작업으로 쪼개며, build는 얇은 수직 슬라이스를 하나씩 구현합니다
- /build auto는 계획을 한 번 승인하면 작업을 독립적으로 돌립니다. 작업마다 테스트 기반이고 단독 커밋되며 실패하면 멈추므로 자율성을 다루는 올바른 방식이라고 합니다
- 25개 스킬에 스태프 엔지니어, 테스트 엔지니어, 보안 감사자, 웹 성능 감사자 리뷰 페르소나 넷이 있습니다

## 스킬 파일 안의 반합리화 표와 의심 주도 개발

- 각 스킬에는 에이전트가 단계를 건너뛰며 댈 변명과 그에 대한 반박을 나란히 적은 반합리화 표가 있습니다. 변명을 미리 적어 두는 것이 영리하다고 평가합니다
- 의심 주도 개발은 자명하지 않거나 중요한 결정마다 새 컨텍스트의 리뷰어가 그 주장을 의심하게 하는 것으로, 끝이 아니라 구축 도중에 하는 적대적 리뷰입니다
- 하이럼의 법칙(API 설계), 비욘세 규칙(테스트), 체스터턴의 울타리(코드 단순화), 트렁크 기반 개발, 작은 원자적 커밋, 코드는 부채라는 관점이 들어 있어 스킬을 읽는 것만으로도 좋은 소프트웨어 엔지니어링 강의가 된다고 합니다

## 세 팩은 무엇을 묻는가

- Matt Pocock: 우리가 무엇을 만드는지 합의했는가. 에이전트가 먼저 몰아붙여 질문하는 "Grill me", 공유 언어 용어집, 결정 기록, 스펙과 티켓이 중심이고, 프레임워크가 통제권을 빼앗는다고 보아 스킬을 작고 조합 가능하게 둡니다
- Lauren Tan의 pstack: 동작함을 증명할 수 있는가. 일부러 계획 스킬이 없고 최고의 스펙은 코드 자체라는 입장이며, 조사, 검증, 사후 멀티모달 리뷰에 무게를 둡니다. 빌드 통과는 증거로 치지 않습니다
- Addy Osmani: 전체 프로세스를 따랐는가. 셋 중 유일하게 CI/CD, 모니터링, 기능 중단, 배포까지 SDLC 전체를 다루고, 약 70개 에이전트에 설치할 수 있어 팀에 가장 맞고 이식성이 높을 것이라고 합니다

## 언제 무엇을 쓸까

- Pocock: 문제가 모호하거나 원하는 바가 불확실할 때, 수년간 가져갈 코드베이스의 설계를 신경 쓸 때. "Grill me"가 가장 먼저 설치할 단일 스킬입니다
- Addy: 프로덕션으로 배포하는 팀에서 모두가 아는 예측 가능한 프로세스와 품질 게이트를 원할 때
- pstack: 재현 안 되는 버그, 마이그레이션, 밤새 도는 장기 에이전트처럼 복잡한 상황에서 스웜과 아레나를 쓰고 싶을 때, 그리고 Cursor를 쓸 때
- 세 팩이 서로 겹치는 건 소프트웨어 엔지니어들이 같은 구축 방식으로 수렴하기 때문이며, 소프트웨어 엔지니어링은 의견의 영역이니 가장 좋은 의견을 골라 쓰면 됩니다

## 전부 설치하지 마세요

- 에이전트가 이미 매우 똑똑하니 agents.md나 기존 스킬을 줄이고 다듬는 편이 낫습니다. 스킬은 새로운 것을 가르치기보다 선호하는 작업 방식에 관한 것입니다
- 스킬이 길거나 많으면 컨텍스트 윈도우가 부풀고 혼란스러워지며, 원치 않을 때 자동 발동될 수도 있습니다. 스킬이 많다고 에이전트가 더 똑똑해지지 않습니다
- 프로세스는 작업의 규모와 중요도에 맞춥니다. 버튼 색 변경은 고치고 눈으로 보면 되고, 시각적이거나 프로토타입 성격이면 직접 하고 반복하며, 작은 기능은 빠른 그릴링 후 TDD, 크거나 불분명한 기능은 스펙과 단계별 계획에 단계마다 검증, 프로덕션이나 보안이나 되돌릴 수 없는 일에는 전체 리뷰와 의심 주도 개발을 씁니다
- Addy 본인의 도입 가이드도 기존 코드베이스에서 검증부터 시작하는 점진적 롤아웃입니다

## 스킬은 좋은 관행의 코드화

- 스킬을 배운다는 것은 TDD, 작은 수직 슬라이스, 만들기 전에 요구사항 합의, 결정 이유 기록, 이유를 알기 전에 울타리를 치우지 않기, 실제 대상으로 동작 증명 같은 좋은 개발 관행을 배우는 것입니다. 테스트가 초록이라고 앱이 동작하는 것은 아닙니다
- 이 아이디어들은 세 사람이 발명한 것이 아닙니다. Matt는 『실용주의 프로그래머』와 도메인 주도 설계, Addy는 Google의 엔지니어링 책, Lauren은 React와 Meta 경험에 기댑니다
- 팩을 교리가 아니라 O'Reilly 교과서처럼 대하고, 통하는 것을 가져와 자기만의 스킬을 쌓으라고 합니다. 에이전트가 망칠 때마다 배운 교훈으로 스킬을 업데이트하면 되고, 세 팩도 그렇게 만들어졌다고 합니다
