# 버그 리포트에서 배포까지: '소프트웨어 팩토리'가 바꿀 개발의 미래

## 한 줄 요약

Factory의 Davis Palmy는 버그 리포트 같은 입력 신호를 프로덕션 코드까지 이어 주는 에이전트 시스템인 소프트웨어 팩토리를 인시던트 분류처럼 좁고 검증 가능한 영역부터 점진적으로 구축하고, 토큰이 아닌 성과를 측정하며 사람은 방향과 판단을 맡아야 한다고 말합니다.

## 엔지니어링의 세 시대와 역할 변화

- AI 엔지니어링은 탭 자동 완성, 파일 단위 생성, 코드와 결합된 에이전트를 거쳐 시스템 단위로 추상화 사다리를 오르고 있으며, 단계마다 엔지니어의 가치는 오히려 커졌다고 봅니다
- 엔지니어는 코드를 타이핑하는 사람에서 에이전트를 통제하고 시스템으로 조직하는 사람이 되어 가드레일 유지, 코드 드리프트 포착, 우선순위와 방향 설정을 맡습니다
- 제품과 엔지니어링의 경계, 팀 사이의 경계가 흐려지고 컨텍스트가 경계를 넘어 흘러야 하며, 사일로는 특히 에이전트에게 치명적입니다

## 코딩은 병목이 아니었다

- 병목은 PR 리뷰 시간, 버그 재현과 디버깅, 문서와 테스트 스위트 관리, 팀 간 소통에 있고 코드 작성부터 프로덕션까지의 시간(DORA 지표)이 실제 변경 시간을 훨씬 넘는다고 주장합니다
- 지금 필요한 것은 여러 접점에 걸친 응집력이며, 에이전트가 모든 서비스를 이어 조직의 맥락을 이해하게 만드는 것이 팩토리 구축의 과제입니다

## 소프트웨어 팩토리와 시작 방법

- 소프트웨어 팩토리는 입력 신호에서 프로덕션 배포까지 이어 주는 에이전트 시스템이며, 고객 지원, 제품, 엔지니어링, 배포 운영 역할을 맡아 분류, 계획, 문서, 실행, 리뷰, 테스트, 롤아웃, 모니터링을 수행합니다
- 한꺼번에 하면 너무 무겁고 팀이 신뢰를 쌓을 시간이 없으므로 Sentry 알림을 읽고 트레이스를 모아 Slack에 올리는 인시던트 분류처럼 좁고 검증 가능한 것부터 시작하고, 사람이 검토하게 둡니다
- 각 단계를 충분히 관리한 뒤 출력을 입력 신호에 다시 연결하면 조직의 자기 개선이 열리며, 개별 기둥을 먼저 자동화하고 나서 루프로 돌려야 합니다

## 세 가지 원칙

- **모델 애그노스틱**: 코드 리뷰에서 GPT 5.2가 최신 Opus와 같은 성능을 절반 가격에 낸다고 하며, 오픈 소스 대안은 10~30배 저렴합니다. 한 연구소에 묶이지 않으면 속도, 효능, 비용의 파레토 프런티어 전체를 쓸 수 있습니다
- **주권적 배포**: 보안 아키텍처와 정책을 타협하지 않도록 완전 관리형, 내 머신 사용, 완전 망 분리까지 선택할 수 있어야 합니다
- **SDLC 전반의 통합**: 문서, 코드, 계획 목표, 테스트가 서로를 반영해야 하며 한 기둥이 약하면 시스템 전체가 약해집니다

## AI 네이티브 조직의 실전 패턴과 O(N)에서 O(1)로

- 흔한 패턴은 Sentry 알림 분류와 사전 진단, 비밀 값과 취약점 스캔, 테스트 생성과 유지, 문서와 코드와 회의 내용의 동기화, 코드 리뷰, 롤아웃, 릴리스 모니터링입니다. 사람은 판단을 내리고 AI가 배우도록 바로잡습니다
- 거버넌스를 한 번 정의해 조직 전체에 표준화하면 팀 관리의 선형적 고통을 O(N)에서 O(1)로 줄이고, 모두를 최저 공통분모가 아니라 가장 높은 기준으로 끌어올릴 수 있다고 봅니다
- 에이전트는 원격 머신, CLI, Slack 등 어느 접점에서든 같은 하네스와 컨텍스트를 공유해야 하며, 컨텍스트가 한곳에 모이면 경영진이 SDLC 전체를 볼 수 있습니다

## 에이전트 준비도 8대 기둥과 거버넌스

- 팩토리를 만들면 암묵지, 수작업 프로세스, 낡은 정보가 드러나며 이를 푸는 일은 에이전트와 엔지니어링 팀 모두에게 도움이 됩니다
- 언급된 평가 항목은 검증(린터, 포매터), 빌드 시스템과 CI 문서화, 피드백 루프(단위·통합 테스트, README, agents.md), 재현 가능한 개발 환경, 경계가 분명한 모듈화, 관측 가능성, 선제적 보안 스캔입니다
- 볼 수 없는 것은 통제할 수 없으므로 에이전트 성능을 모니터링하고 행동을 통제해야 합니다. Factory는 모든 행동을 감사 가능하게 하고 역할 기반 접근 제어와 최소 권한을 적용하며 점진적으로 롤아웃하라고 권합니다

## 사람의 역할과 성과 지표

- 정밀한 실행이 나쁜 설계를 막아 주지는 않으므로 아키텍처, 전략, 방향 설정에는 사람이 필요합니다. 엔지니어는 대체되지 않지만 기계적 구현 기술보다 판단과 우선순위가 중요해지고, 사람은 팩토리의 검증 게이트 역할을 합니다
- 코드 라인 수와 토큰 생성량은 조작 가능한 지표이며 토큰 리더보드는 낭비성 지출을 부추깁니다(굿하트의 법칙). 토큰이 아니라 성과를 측정해야 합니다
- Factory가 선호하는 지표는 신호에서 프로덕션까지의 시간, 사람 개입 횟수, 중앙값 복구 시간, 코드의 수명, PR당 비용입니다
- 에이전트에게도 엔지니어와 같은 수준의 거버넌스(도구, 접근 수준, 리뷰 체계)가 필요하며 코드베이스에 그냥 풀어놓지 말라고 당부합니다
