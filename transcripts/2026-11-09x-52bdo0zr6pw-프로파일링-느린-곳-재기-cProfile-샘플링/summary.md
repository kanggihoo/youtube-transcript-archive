# 프로파일링 — 느린 곳 재기 cProfile, 샘플링

## 결론부터

파이낸스코더는 파이썬 프로그램이 느릴 때 짐작으로 고치지 말고 cProfile로 재서 가장 큰 곳부터 고치라고 말한다. 예시로 체결 4만 건 리포트의 2초 넘는 시간이 `list`의 멤버십 검사 한 줄 때문이었고 `set`으로 바꾸자 0.01초 안팎으로 줄었다고 한다.

## 핵심 내용

- **재야 하는 이유:** 시간은 보통 한두 곳에 몰려 있고, 효과는 그곳이 전체에서 차지하는 비율만큼만 난다. 전체의 10%를 두 배 빠르게 해도 전체는 5%만 준다.
- **도구와 표 읽기:** `perf_counter`는 구간 시간, `timeit`은 짧은 코드를 반복 측정, cProfile은 함수별 호출 횟수와 시간을 기록한다. 표에서는 `ncalls`(호출 횟수), `tottime`(함수 안에서만 쓴 시간, 병목 판단 기준), `cumtime`(하위 호출 포함)을 본다. 예시에서는 중복 확인 함수가 3만 번 불려 2.5초 중 약 2.4초를 썼고, 의심했던 수익률 계산은 상위에 없었다.
- **원인과 해법:** 리스트의 멤버십 검사는 앞에서부터 비교(O(n))이고 set은 해시로 거의 한 번에 찾는다. 반복문 안에서 쓰면 데이터가 두 배일 때 시간은 네 배가 된다. 3.6만 개 리스트의 맨 끝 값 검색이 약 200μs, set은 0.01μs로 만 배 넘게 차이 났다고 한다. 수정은 두 줄.

## 배울 점과 적용 조건

- 고치는 순서: 측정 → 알고리즘·자료구조 → 표준 라이브러리/내장 함수 → 마지막에 NumPy·C 확장. 처음부터 마지막 단계로 가면 이유도 모른 채 복잡해진다.
- 전후 비교는 같은 데이터, 다른 무거운 작업 중지, 여러 번 측정으로 조건을 맞춘다.
- 샘플링 프로파일러는 기록 부담이 적어 돌고 있는 서버에 붙일 수 있다고 하지만, 도구 이름이나 사용법은 영상에서 다루지 않는다.

## 근거와 한계

- **영상의 근거:** 연습용으로 만든 합성 데이터 4만 건 예시와 수치(2.5초→0.01초, 200μs vs 0.01μs). 코드 시연은 화면으로만 보인다.
- **평가:** 수치는 합성 예시 한 건의 값이고 하드웨어·파이썬 버전은 밝히지 않았다. 원리(리스트 O(n) vs set 평균 O(1), 암달의 법칙)는 표준적이라 결론은 일반적으로 성립한다(작성자 보충).
- **확인 범위:** 자막 기반이며 자동 생성 자막이 군데군데 깨져 있다(`timeit`, `cProfile` 설명 일부). 수치는 외부 미검증.
- **홍보성:** 특별한 징후는 없다.
