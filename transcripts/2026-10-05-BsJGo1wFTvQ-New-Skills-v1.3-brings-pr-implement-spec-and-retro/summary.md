# New Skills! v1.3 brings /pr, /implement-spec, and /retro

## 한 줄 요약

Matt Pocock의 스킬 저장소 v1.3은 스펙 전체를 서브에이전트로 구현하는 `implement spec`, 리뷰하기 쉬운 PR 본문을 쓰는 `pr`, 에이전트 세션을 돌아보고 저장소 개선안을 내놓는 `retro`를 추가합니다. 발표자는 이 중 `retro`가 가장 반응이 컸다고 하면서도, 사람이 판단하며 쓰고 자동화하지 말라고 당부합니다.

## 스펙과 티켓: 큰 작업을 쪼개는 세 가지 루프

- 큰 작업은 **스펙**(가려는 곳)과 그것을 구현하는 **티켓**(에이전트 하나가 한 세션에 끝낼 단위)으로 나눕니다. 스펙 전체를 에이전트 하나에 맡기면 "멍청한 구간"이나 자동 컴팩트에 걸립니다
- **수동 루프**: 사람이 티켓마다 "구현해 → 컨텍스트 비우기"를 반복합니다. 사람이 for 루프 노릇을 하는 셈이라 쓸 만하지 않습니다
- **결정론적 루프**: 스크립트가 티켓을 읽어 구현을 돌립니다. 매번 똑같이 돌고 믿을 만하고 싸서 대부분에게 추천하지만, 설정이 복잡하고 다듬을 인내가 필요해 초보자에게는 어렵습니다
- **`implement spec`**: 에이전트가 감독을 맡고 서브에이전트가 티켓을 구현하는 중간 지점입니다. 서브에이전트가 서브에이전트를 만들 수 있게 된 덕분에 가능해졌습니다. 결정론적 루프보다는 못하지만 자리를 비우는(AFK) 워크플로의 입문용입니다

## implement spec의 9단계

- 티켓은 순서 목록이 아니라 서로 막는 관계가 있는 **작업 그래프**라서, 바로 집을 수 있는 티켓은 병렬로 처리합니다
- 흐름: 스펙과 티켓 읽기 → 서브에이전트로 탐색 → **통합 브랜치** 생성 → 티켓마다 구현 서브에이전트가 TDD와 작업 트리로 구현 → 서브에이전트가 통합 브랜치에 병합 → 전부 끝나면 통합 브랜치에 코드 리뷰 → 정리 후 **거대한 스펙 하나에서 PR 하나**
- 발표자는 소프트웨어 팩토리가 아직 다듬어지지 않은 시스템에서 예상보다 자주 쓴다고 합니다. 기본 버전일 뿐이니 스택형 PR 등으로 바꿔도 됩니다

## PR 스킬: 본문 템플릿 하나가 전부

- Dex Hies의 `Show Me`(다이어그램과 의사 코드로 설명하는 스킬)에서 영감을 받아, **사람의 리뷰를 최대한 쉽게** 만드는 PR 본문 템플릿을 제공합니다
- 본문 구성: **요약**(Show Me 템플릿) → **증거**(변경 전과 후) → **머지 위험**(한쪽 문인가 양쪽 문인가, 영향 범위)
- 증거를 요구하면 에이전트가 테스트를 한 번 더 돌리거나 스크린샷을 찍습니다. "코드를 읽어 보니 아마 될 겁니다"로 넘어가지 못하게 하는 장치이고, 발표자는 요즘 "검증 없음"에 집착한다고 합니다
- 한쪽 문 = 데이터 삭제나 되돌리는 데 비용이 드는 변경. 양쪽 문이면서 영향 범위가 작으면 가볍게 봐도 됩니다. 이 항목을 맨 아래에 두어 리뷰어가 가장 먼저 보게 합니다
- 모델이 스스로 가장 일관되게 호출하는 스킬이어서, 적어도 Opus 5.5에서는 설치만 해도 PR 본문이 좋아진다고 합니다

## context.md가 glossary.md로 바뀜

- domain modeling 스킬(grill with docs)이 `context.md` 대신 **`glossary.md`**에 씁니다. DDD의 바운디드 컨텍스트에서 딴 이름이 너무 모호했고, 에이전트가 적절한 때 불러오지 않았으며, 사용자도 헷갈렸기 때문입니다
- 내용을 줄이다 보니 사실상 용어집만 남았습니다. 다른 동작 변경은 없고 파일 이름만 바뀌었지만, 여러 스킬이 `glossary.md`가 보이는 것을 전제로 동작하므로 **반드시 갱신해야** 합니다

## retro 스킬: 에이전트 세션을 돌아보고 저장소를 고친다

- 배경: 발표자의 스킬 세트는 사용자에게 `agents.md`와 스킬 관리, 토큰 효율, 린트 규칙, 탐색 구조 개선을 직접 하라고 요구해 왔는데, 자신이 하던 일을 스킬로 묶은 것이 `retro`입니다
- 현재 세션이나 이전 세션을 읽어 **다음번을 위한 개선안**을 냅니다. 에이전트는 불평하지 않고 끈질기게 기능을 만들어 내기 때문에, 세션을 되짚는 다른 에이전트가 숨은 비효율을 찾아야 한다는 논리입니다
- 발표자 세션에서 찾아낸 것: 수정안을 고르기 전에 **되돌릴 수 없는 릴리스를 묻지 않고 실행**(그래서 1.3.0 없이 1.3.1만 존재), 체크 스크립트는 있는데 실행하는 CI가 없음, 컴팩션 때 컨텍스트 손실이 생기니 반복 지시를 스킬로 옮길 것, 커스텀 CLI가 토큰을 낭비
- 보는 범주: 코드베이스 탐색 용이성, 추가할 자동 체크, 자동 리뷰어용 코딩 표준, 전역 `agents.md`의 상태, 도구 경제성, 지침 파일의 효과 없는 항목, 에이전트가 필요한 정보에 접근 가능한지

## retro는 자동화하지 않는다

- **사람이 개입하는(human in the loop) 설계**입니다. 발표자 본인 결과에서도 가장 심각하다고 나온 항목은 실제로는 별 문제가 아니었습니다
- 자동화하면 에이전트가 오탐을 계속 찾아 고치려는 루프에 빠져 저장소와 에이전트를 엉뚱한 곳으로 끌고 갑니다
- 권장 사용법: 한가할 때, 특히 에이전트가 이상한 짓을 한 세션을 **표본으로 골라** 돌립니다. 정기적으로 돌린 뒤 토큰 효율과 결과 품질이 크게 올랐다고 합니다
