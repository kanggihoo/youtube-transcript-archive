# I’ve been using Redis wrong this whole time...

## 결론부터

발표자는 Redis를 단순 캐시로만 쓰는 것은 낭비이며, 영속성(RDB·AOF), 고가용성(Sentinel), 샤딩(Cluster), 풍부한 자료구조와 모듈을 갖춘 만큼 주 데이터베이스로도 쓸 수 있다고 주장합니다. 다만 비용 때문에 오래된 콜드 데이터는 SQL DB에 두라고 덧붙입니다.

## 핵심 내용

- **"휘발성"과 "단순 key-value"는 오해라는 주장:** RDB는 fork와 copy-on-write로 스냅샷을 만들고, AOF는 쓰기 명령을 로그로 남겨 재시작 시 재생합니다(매초 또는 매 쓰기마다 fsync 설정 가능). Sentinel은 쿼럼 투표로 자동 장애 조치를 하고, Cluster는 16,384개 해시 슬롯(CRC16)으로 데이터를 나눕니다.
- **자료구조 서버:** 문자열(최대 512MB, INCR, 비트맵), 리스트(활동 스트림), 셋(공통 친구), 해시, 정렬 셋(리더보드, 해시 테이블+스킵 리스트)을 사례로 듭니다. Redis JSON, Search, 벡터 검색 모듈로 문서·전문 검색·RAG 용도까지 확장된다고 설명합니다.
- **운영 측면:** 단일 스레드 이벤트 루프(epoll/kqueue)가 속도의 근원이라고 설명합니다. 주 DB로 쓸 때는 `noeviction`, 캐시로 쓸 때는 LRU 계열을 권합니다. Lua 스크립트는 읽기-수정-쓰기 경쟁 상태를 없애지만 CPU 무거운 스크립트가 전체를 막고 롤백이 없다고 짚습니다. Pub/Sub과 Streams(컨슈머 그룹, 펜딩 목록, ack)도 소개합니다.

## 배울 점과 적용 조건

- 캐시 외 용도를 검토할 때 RDB/AOF, 퇴출 정책(`noeviction`), Sentinel/Cluster의 역할 구분을 한 번에 정리하는 체크리스트로 쓸 수 있습니다.
- 읽기-수정-쓰기 경쟁 상태는 분산 락 대신 Lua 스크립트로 푸는 방법이 있습니다. 클러스터에서는 같은 해시 슬롯 안의 키에만 해당하고, 스크립트는 짧고 결정적이어야 하며 중간 실패 시 부분 적용을 직접 처리해야 합니다.
- 작업 큐나 이벤트 처리에는 Pub/Sub(유실 허용)과 Streams(영속, ack)를 구분해 선택합니다. 전체 데이터가 RAM에 올라가므로 비용과 용량이 전제 조건입니다.

## 근거와 한계

- **영상의 근거:** 코드 시연, 벤치마크, 운영 사례, 수치 비교는 없습니다. 개념과 메커니즘 설명이 전부입니다.
- **평가:** 설명 자체는 일반적인 Redis 지식과 맞아 보이지만, "주 DB로 충분하다"는 결론을 지지하는 근거(장애 시 데이터 손실 범위, `fsync always`의 성능 비용, 복제의 비동기성, 실제 도입 사례)는 빠져 있습니다. AOF를 매초 동기화하면 최대 약 1초 분량을 잃을 수 있다는 점 같은 한계도 다루지 않습니다. 제목의 "wrong"에 비해 새로운 통찰은 적습니다.
- **확인 범위:** 자막 기반 평가이며 공식 문서 등 외부 검증은 하지 않았습니다. 영상 내 주장, 외부 미검증입니다.
- **홍보성:** 중간에 Neon(서버리스 Postgres) 스폰서 구간이 있고, 말미에 CodeCrafters 40% 할인과 발표자의 뉴스레터를 안내합니다. 영상 설명란에는 시스템 설계 강의 링크도 있습니다. 스폰서 구간은 Redis 설명과 분리되어 있어 기술 내용에는 큰 영향이 없어 보입니다.
