**17:09** · 그리고 이 경우에는 그 때문에 리눅스 연결 추적 테이블에 항목이 남아 있게 되어, Rust 구현에서 만난 것과 같은 서버의 연결 한도에 부딪혔습니다. 같은 개발자가 거의 같은 한도를 가진 C++ 구현 두 개를 제출했고, 세 개 모두 61,000명에서 끝났습니다. 그러니 그 설정을 바꿨다면 Zig도 64,000명 한계에 도달할 수 있었을 거라고 생각합니다. 숫자가 이를 뒷받침합니다. 62,000명에서 지연 시간은 훌륭했고 P99는 겨우 268밀리초였습니다. 강제 재연결로 인한 1.02%의 오류 때문에 순전히 그 이유로 실패했습니다.

**17:37** · 그리고 CPU 사용률은 69%였는데, Rust보다 상당히 높지만 우리가 달성할 수 있었을 범위의 안전 한도에는 여전히 한참 못 미칩니다. 그리고 공동 1위는 64,000명의 C++입니다. 이 구현은 스레드 하나, 이벤트 루프 하나를 쓰고 SQLite와 직접 통신합니다. 워커 풀도, 락도, 리버스 프록시도 없습니다. 꽤 흥미로운 최적화가 여기서 SQLite 안에 있었습니다.

### C++

**17:56** · 애플리케이션을 프로파일링해 보니 SQLite가 트랜잭션을 커밋할 때 자기 페이지 캐시를 스캔하는 데 애플리케이션 CPU 시간의 13%를 쓰고 있었습니다. 그래서 SQLite가 캐싱을 처리하는 방식을 조정했는데, 규칙을 생각하면 저는 좀 회의적이었습니다. 하지만 실제로는 SQLite의 내부 캐시를 거의 없는 수준으로 줄이고 데이터베이스를 메모리에 매핑해서, 읽기가 운영체제의 페이지 캐시를 쓰게 했고, 그러면 SQLite가 할 일이 줄어듭니다. 또 SQLite가 체크포인트 작업을 실행하는 시점도 바꿨는데, 체크포인트는 SQLite가 선행 기록 로그를 관리하는 방식의 일부입니다.

**18:23** · 그래서 유지보수 작업이 진행되는 동안 요청을 실행하는 대신, 응답 경로에서 체크포인트를 뺐습니다. 여기서 언급할 만한 세부 사항이 하나 있습니다. 이 구현은 SQLite의 선행 기록 로깅 모드에 synchronous를 normal로 설정해서 씁니다. 유효하고 챌린지 규칙도 지키지만, 내구성 면에서 상당한 대가가 따릅니다. 'normal'은 모든 트랜잭션의 선행 기록 로그 데이터를 즉시 영구 저장소로 동기화하도록 강제하지 않기 때문에, 트랜잭션이 커밋되어도 갑작스러운 정전에서 살아남는다는 보장은 없을 수 있습니다. 이 구현들이 응답 전에 커밋해야 한다고 말할 때, 그것이 자동으로 확인된 모든 쓰기가 머신이 전원을 잃어도 보존된다는 뜻은 아닙니다.

**18:53** · 이런 최적화를 실제 애플리케이션에 쓰고 싶다면 고려해야 할 점입니다. 이 측면 때문에 여기에는 별표를 하나 붙이겠습니다. 그리고 제 캐싱 규칙으로 돌아가면, 데이터베이스를 자체 인메모리 구조에 저장하는 것은 규칙 위반이었지만 여기서는 실제로 그러지 않았습니다. 운영체제의 파일 캐시를 데웠는데, 이것은 데이터베이스가 동작하는 방식의 정상적인 일부이고 허용되었습니다. 그래서 이 구현은 사실상 유효했습니다. 그리고 Rust처럼, 리눅스가 부과하는 연결 추적 한도에 닿기 전에 64,000명에 도달했습니다. 64,000명에서 C++의 P99 지연 시간은 910밀리초, Rust의 P99는 겨우 224밀리초였습니다.

**19:24** · 즉 가장 느린 1%의 요청은 C++에서 훨씬 높은 지연 시간 임계값에 이르렀습니다. 이번에도 그 한도 때문에 두 애플리케이션이 같은 수의 가상 사용자를 지원했는데도 말입니다. 그리고 C++는 Rust에 비해 서버 CPU도 약 68% 썼습니다.

**19:40** · 그러니 규칙상으로는 무승부로 끝났지만 Rust는 이 수준에서 훨씬 더 여유가 있었고, 그래서 이것이 커뮤니티 벤치마크에서 가장 빠른 언어입니다. 그럼 이 구현들을 그렇게 빠르게 만든 것은 실제로 무엇이었을까요? 영상 내내 몇 가지를 언급했지만, 계속 반복해서 나온 점들을 짚고 싶었습니다. 첫째, 가장 빠른 구현은 거의 모두 Nginx를 빼고 HTTP 트래픽을 직접 처리했습니다. Nginx는 프로덕션 환경에서 엄청나게 유용합니다. TLS 종료, 로드 밸런싱, 버퍼링, 라우팅 등 훨씬 많은 것을 처리할 수 있습니다. 하지만 이 실험에서는 CPU 하나짜리 작은 머신 한 대에서 모든 것을 돌립니다.

### 핵심 정리

**20:08** · 그래서 애플리케이션 앞에 Nginx를 두면 모든 요청이 여러분의 코드에 닿기 전에 프로세스 하나를 더 거쳐야 합니다. 이는 작업이 더 많고, 데이터 이동이 더 많고, CPU 시간이 더 든다는 뜻입니다. 이 작은 CPU에서 마지막 한 방울까지 짜내려 할 때는 그 오버헤드가 정말 중요합니다. 모든 출품작이 Nginx를 뺀 것은 아닙니다.

**20:23** · Rust Axum이나 Rails 출품작 하나처럼 Nginx를 유지한 구현도 있었습니다. 하지만 가장 빠른 출품작들은 트래픽을 직접 처리했습니다. 둘째, 거의 모든 상위 출품작이 SQLite 쿼리를 한 번만 준비해서 재사용하고 데이터베이스 연결도 하나를 재사용했습니다.

**20:34** · 이렇게 하면 같은 SQL 문을 반복해서 파싱하는 일을 피하고 데이터베이스 접근을 더 예측 가능하게 만듭니다. 셋째, 많은 구현이 SQLite로 JSON 응답을 생성했습니다. 데이터베이스 행을 애플리케이션 객체로 바꾸고 직렬화하는 대신 SQLite가 응답을 직접 만들게 했습니다. 이것이 엄청난 시간을 절약했습니다. 그리고 넷째, 가장 빠른 출품작 대부분이 그룹 커밋을 썼습니다. 즉 쓰기를 하나하나 커밋하는 대신 여러 쓰기를 트랜잭션으로 묶어 한꺼번에 커밋했습니다. 쓰기가 있는 워크로드에서는, 특히 쓰기가 더 많을수록 이것이 아주 큰 차이를 만들 수 있습니다. 마지막으로, 가장 빠른 구현들은 프레임워크 너머로 나아가 프레임워크를 아예 대체했습니다.

**21:03** · 사람들은 자체 서버, 메모리 관리, 이벤트 루프를 구현했는데, 이것이 이 실험에서 더 중요한 부분 중 하나로 이어집니다. 바로 사람들이 감수한 트레이드오프입니다. 이 숫자들은 매우 인상적이었지만, 저는 이 구현들 대부분을 직장의 대규모 애플리케이션에 배포하거나 이 PR들을 승인하지는 않을 겁니다. 예를 들어 우승한 C++ 출품작은 자체 HTTP 파서와 JSON 파서를 포함해 파일 하나에 코드가 1,300줄이 넘습니다. 가장 빠른 Rust 구현은 코드가 약 2,400줄이고 'unsafe' Rust를 많이 씁니다. 꽤 최신의 리눅스 기능에 의존하며, Bun 출품작은 이 특정 API가 실제로 필요로 하는 HTTP 부분만 구현합니다. 그러니 확장성이 가능한 만큼 좋지는 않습니다.
