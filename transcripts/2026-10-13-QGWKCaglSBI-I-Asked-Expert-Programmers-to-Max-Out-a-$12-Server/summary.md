# I Asked Expert Programmers to Max Out a $12 Server

## 한 줄 요약

Arjay McCandless가 12달러짜리 1 vCPU / 2GB 서버를 최대한 쥐어짜 보라는 커뮤니티 챌린지를 열었고, 최고 구현(Rust + IO uring)이 동시 사용자 64,000명에 도달해 지난번 최고 14,000명의 4배를 넘겼습니다. 다만 대부분은 프로덕션에 쓰기 어려운 극단적 최적화이고, 64,000은 서버가 아니라 리눅스 연결 추적 테이블 한도에서 멈춘 수치입니다.

## 챌린지 조건

- 트위터 같은 소셜 API(엔드포인트 5개, 42개 검사 통과)를 SQLite를 같은 프로세스에서 써서 구현합니다. 별도 DB 서버, Redis 등 외부 캐시는 금지입니다
- 쓰기는 트랜잭션이 커밋된 뒤에야 응답해야 합니다
- K6로 사용자 부하를 5분간 유지하면서 P95 0.5초 이내, P99 1초 이내, 오류율 1% 미만이어야 한 단계를 통과합니다
- 일부 구현이 너무 빨라 부하 생성기가 먼저 병목이 되어 가상 머신 네 대로 부하를 만들었습니다
- 13개 언어로 28개가 들어왔고 26개를 벤치마크했습니다. Java와 Node 출품작은 없었습니다

## 언어별 결과

- Ruby 14,000명(Rails는 3,000~3,500명): Iodine 서버, YJIT, SQLite가 JSON을 직접 생성
- Erlang 15,000명: 스케줄러 하나, 프로세스 하나가 SQLite 연결 관리
- Python 22,000명(원래 약 2,150명): FastAPI에서 의존성 주입, 미들웨어 등을 걷어내 11,000에서 두 배로
- Go 22,000명: 그룹 커밋을 쓰지만 연결 16,000개 초과 시 재연결 요청이 비싸 연결 부족으로 실패
- C# 32,000명: Kestrel 저수준 인터페이스 직접 사용, 풀링 버퍼와 스택 메모리로 GC 회피
- Fortran 38,000명: libmicrohttpd, SQLite JSON 기능, 토큰 검증도 SQL로 처리
- PHP 40,000명(Laravel은 750명): Swoole로 상주 서버화, JIT 켬, 코드 250줄
- C 46,000명: IO uring, 프로파일 기반으로 컴파일한 SQLite, 피드 쿼리 재작성. CPU 36%에서 실패해 락과 배치 대기가 의심됨
- Bun 47,000명(원래 4,200명): 원시 TCP와 최소 HTTP 파싱, SQLite가 JSON을 원시 바이트로 반환
- Rust 두 가지: Axum 구현 43,000명, IO uring 구현 64,000명(P99 224ms, CPU 절반, RAM 100MB 미만)
- Zig 61,000명, C++ 64,000명: 둘 다 연결 한도 때문에 정점이 결정됨

## 64,000에서 멈춘 이유

- K6 가상 사용자마다 연결이 열려 있고 리눅스 연결 추적 테이블이 65,000명용이라, 64,000명을 넘으면 커널이 패킷을 버립니다
- 규칙상 커널 튜닝은 금지라 64,000이 실질적 최고 점수가 되었고, Rust는 CPU가 절반 남은 상태였습니다
- Zig는 개발자가 persistent 연결 상한을 60,000으로 둬서 61,000명에서 멈췄고, 재연결이 추적 테이블에 항목을 남겨 같은 한도에 걸렸습니다
- 64,000명에서 C++의 P99는 910ms, Rust는 224ms였습니다. 규칙상 공동 1위지만 Rust가 여유가 훨씬 컸고 그래서 가장 빠른 언어로 꼽힙니다

## C++ 우승작의 SQLite 튜닝과 내구성 대가

- 스레드 하나, 이벤트 루프 하나, 워커 풀·락·리버스 프록시 없음
- 프로파일링 결과 SQLite가 커밋 때 페이지 캐시 스캔에 CPU 13%를 썼고, 내부 캐시를 거의 없애고 DB를 메모리에 매핑해 OS 페이지 캐시를 쓰게 했습니다. 영상은 이것이 인메모리 DB 금지 규칙은 어기지 않았다고 봅니다
- 체크포인트를 응답 경로에서 뺐습니다
- WAL 모드에 synchronous=normal이라 정전 시 커밋된 트랜잭션이 보존된다는 보장이 없어서, 발표자는 별표를 붙입니다

## 빠른 구현들의 공통점

- Nginx를 빼고 HTTP를 직접 처리했습니다. 단일 CPU에서는 프록시 한 단계의 오버헤드가 큽니다
- SQLite 쿼리를 한 번만 준비하고 DB 연결 하나를 재사용했습니다
- SQLite가 JSON 응답을 직접 만들어 객체 생성과 직렬화를 건너뛰었습니다
- 그룹 커밋으로 여러 쓰기를 한 트랜잭션에 묶었습니다
- 프레임워크를 쓰지 않고 자체 서버, 메모리 관리, 이벤트 루프를 구현했습니다

## 프로덕션에 쓰기 어려운 이유

- 우승 C++는 파일 하나에 1,300줄 이상이고 자체 HTTP·JSON 파서를 담고 있으며, 가장 빠른 Rust는 약 2,400줄에 unsafe를 많이 쓰고 최신 리눅스 기능에 의존하며, Bun 구현은 이 API에 필요한 HTTP만 구현합니다
- 발표자는 직장의 대규모 애플리케이션이라면 대부분 승인하지 않을 것이고, 유지보수성·보안·이식성·온보딩이 중요한 환경에는 지난 영상의 벤치마크가 더 현실적이라고 말합니다
- 그룹 커밋은 트랜잭션이 실패하면 기다리던 요청이 모두 실패할 수 있고, DB 연결 하나로 처리할 때는 느린 작업 하나가 모두를 막지 않게 스케줄링에 신경 써야 합니다
