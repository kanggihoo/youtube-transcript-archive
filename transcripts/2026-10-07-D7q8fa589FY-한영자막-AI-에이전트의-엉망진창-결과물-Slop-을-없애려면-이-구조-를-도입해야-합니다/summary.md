# AI 에이전트의 엉망진창 결과물(Slop)을 없애려면 '이 구조'를 도입해야 합니다

## 한 줄 요약

XState 제작자 David Khourshid는 슬롭이 구조 없는 위임에서 나온다고 보고, 에이전트의 흐름을 명시적인 상태 머신으로 모델링하면 규칙을 구조로 강제하고 트레이스와 평가를 바탕으로 에이전트가 스스로 워크플로우를 개선하게 할 수 있다고 주장합니다.

## 슬롭은 구조 없는 위임에서 옵니다

- 판단, 구조 전체, 구현과 취향까지 에이전트에게 넘기면 모델이 아무리 똑똑해져도 슬롭의 위험이 남습니다. 잘 돌아가다 안 돌아가기 시작할 때 고치라고 말할 근거가 없기 때문입니다
- 해법의 핵심은 결정론입니다. 같은 입력이면 매번 같은 예측 가능한 출력이 나오는 성질이고, 상태와 이벤트가 주어지면 다음 상태가 정해지는 상태 머신이 그 모델입니다
- 발표자는 루프와 그래프가 같은 그림이라고 하며, 에이전트 엔지니어링이 루프 이야기에서 그래프 이야기로 옮겨 왔다고 말합니다

## 메가 프롬프트의 한계

예시는 이메일 작성 에이전트입니다. 초안을 먼저 쓰고, 사용자가 승인한 이메일만 보내고, 수신자를 지어내지 않는다는 규칙은 결정적이어야 합니다. 이메일 내용, 명확화 질문, 초안은 비결정적으로 남깁니다.

메가 프롬프트에 규칙과 send email 툴을 넣는 방식은 동작은 하지만 다음 문제가 있습니다.

- 제어 흐름이 프롬프트와 툴 설명 안에 글로 인코딩됩니다
- 단계를 나누지 못해 단일 모델, 단일 시스템 프롬프트, 단일 설정에 묶이고 단계마다 다른 전략을 쓸 수 없습니다
- 블랙박스라 규칙이 지켜진다는 증명도 매번 보장도 못 합니다. 추론을 켜도 속을 볼 수 없습니다
- 규칙도 나머지 컨텍스트와 같은 텍스트라, 컨텍스트가 쌓일수록 중요도가 희석됩니다

## 상태 머신으로 규칙을 구조에 새기기

- 요청, drafting, reviewing, sending 같은 상태로 모델링하면 수신자가 없으면 sending으로 갈 수 없고, drafting이나 reviewing에서 이메일을 보내는 전이는 아예 존재하지 않아 불가능합니다
- 라이브 데모에서는 모호한 요청에 수신자 주소와 제목을 되묻고, 초안을 쓴 뒤 reviewing을 거쳐 시뮬레이션 발신함으로 전송했습니다. 상태 머신은 자동으로 시각화됩니다
- 이것이 형식적 절차가 아니냐는 물음에, 발표자는 혼란을 대체하는 모델링은 절차가 아니며 사람과 에이전트가 동작 방식을 공통으로 이해하게 해 준다고 답합니다. 모든 에이전트를 이렇게 하라는 것은 아니고, 맞는 곳에서 유용하다는 입장입니다
- 어떤 상태에 있었고 어떤 이벤트가 있었는지 구조화된 로그가 남아 관측 가능성도 얻습니다

## 구조가 보이면 평가할 수 있습니다

- 문단에는 화살표를 그릴 수 없어 프롬프트의 어디서 실패했는지 짚을 수 없지만, 상태 머신은 가능합니다
- 단계별 평가와 워크플로우 전체 평가(LLM 심사자 포함)를 할 수 있고, 빠져 있던 것은 엣지(전이) 평가입니다. 데모는 최종 상태에 도달해도 사용자에게는 짜증스러운 과정이었습니다

## 에이전트가 자기 상태 머신을 개선하게 하기

- 상태 머신, 샘플 트레이스(실제 또는 시뮬레이션 사용자), 단계별과 전체 평가 결과를 지속 가능한 산출물로 에이전트에게 넘기고 변경안을 제안하게 합니다. Stately의 소프트웨어 팩토리와 상태 머신 생성 및 편집 파이프라인에서 해 보니 잘 동작했다고 합니다
- 결과물인 V2는 사소한 수정에 여러 단계를 거치던 것을 보고, 먼저 초안을 쓰고 필요한 정보는 reviewing에서 채우도록 바꿨습니다. 훨씬 빠른 워크플로우이며, 첫 머신도 평가는 통과하지만 직접 써 보고 스스로 개선하는 반복이 없으면 최적에 이르지 못한다고 말합니다

## 필요한 건 루프 하나뿐입니다

- 특별한 라이브러리나 도구는 필요 없습니다. 초기 상태에서 시작해 상태가 활성인 동안 LLM 호출, 툴 호출, 비동기 프로세스를 실행하고, 현재 상태와 이벤트로 다음 상태와 이펙트를 정하는 루프면 됩니다
- 로직은 XState, switch 문, reducer 함수, LangGraph 중 무엇이든 되며, 코딩 에이전트는 어느 쪽이든 업데이트를 잘합니다
- 순서는 모델(상태 머신) 생성, 전이 관찰, 다른 에이전트의 개선 제안, 버전 1과 2를 같은 시나리오로 비교하는 것입니다
- 선행 연구로 Agent Spec, AIFlow, 그리고 이벤트 트레이스를 형식 모델로 정제해 최적화 지점을 찾는 약 20년 된 프로세스 마이닝을 듭니다. 에이전트가 항상 이렇게 돌아야 한다는 주장이 아니라, 상태 머신이 에이전트가 스스로 개선하는 방법이라는 주장입니다

## 안전장치에서 자기 개선으로

2023년 Agent Conf에서는 그래프가 가드레일과 작업 경계로 에이전트를 정직하게 지켜 준다고 했고, 2026년에는 그 그래프적 사고가 에이전트의 자기 행동 개선을 가능하게 한다고 정리합니다.

마지막 데모는 상태 머신으로 만든 에스프레소 머신을 Jev에 맡긴 것입니다. 정확한 상태 머신과 가상 바리스타의 모든 이벤트를 받은 Jev가 오타가 섞인 주문(카푸치노, 샷, 코르타도)을 미리 짠 순서 없이 실시간으로 단계별 수행하고, 일부러 고장 낸 그라인더도 스스로 고치기로 판단하는 모습을 보여 줍니다.
