# Anthropic Engineers Just 10x'd Everyone's Claude Code

## 한 줄 요약

Nate Herk는 Anthropic이 Claude Code 시스템 프롬프트의 80% 이상을 덜어내고도 평가에 큰 영향이 없었다는 글을 근거로, 모델이 좋아진 만큼 우리의 CLAUDE.md와 스킬도 줄여야 한다고 말합니다. `/doctor`로 설정을 감사하고 정기적으로 점검하라고 권합니다.

## 지침을 줄여야 하는 이유

- Anthropic 엔지니어의 글에 따르면 팀은 Opus 3.5, Sonnet 3.5, 3.7 같은 모델에서 시스템 프롬프트의 80% 이상을 걷어냈고, 모델 평가에는 큰 영향이 없었습니다
- 모델이 발전할수록 옛 모델용 규칙은 오히려 발목을 잡습니다. 코드 주석 글자 수 제한을 "주변 코드 스타일을 따르라"로 바꾼 것이 예시입니다
- 실수를 막으려고 하나씩 추가한 규칙이 CLAUDE.md나 스킬에 남아 있는데, 모델이 좋아져 이제 필요 없을 수 있습니다. Claude Code 제작자 Boris Cherny도 6개월마다 스킬을 전부 지우라고 했다고 합니다
- Anthropic Applied AI 팀의 원칙은 원하는 결과를 얻는 데 가장 적은 맥락을 쓰는 것입니다. 다만 최소가 항상 작다는 뜻은 아니고, 모델이 일하는 데 필요한 세부 정보는 넣어야 합니다

## 입력이 길수록 나빠진다는 근거

- 2025년 논문은 모델 다섯 개를 수학, 질의응답, 코딩으로 테스트했고, 입력이 길수록 성능이 13.9%에서 85%까지 떨어졌습니다. 관련 정보를 찾을 수 있을 때도 그랬습니다. 다만 이전 세대 모델의 통제 실험이라 지금 설정에 그대로 적용되지는 않습니다
- Anthropic이 MCP 도구 정의를 필요할 때만 불러오게 한 테스트에서는 토큰 사용량이 85% 줄었고, MCP 평가 점수는 Opus 4에서 49%에서 74%로, Opus 4.5에서 79.5%에서 88.1%로 올랐습니다

## 지침을 줄여 본 실험

- 발표자는 자기 AIOS를 복제해 CLAUDE.md와 스킬을 뺀 채 같은 작업을 시켜 봤습니다. Boris Cherny 인터뷰를 학생용 리소스 가이드로 바꾸는 작업이었습니다
- 평소 설정은 브랜딩과 링크가 들어간 예쁜 문서를 냈고, 줄인 설정은 덜 예쁘지만 세부 내용, 개념별 구성, 타임스탬프가 더 좋은 가이드를 냈습니다
- 그래서 브랜딩(헤더, 폰트, 푸터, 로고)만 새 스킬로 고정하고 내용 구성은 Claude에게 맡기기로 했습니다. 규칙이 너무 많으면 모델을 제한해 최고의 결과를 막는다는 판단입니다. 숙련된 디자이너에게 초보용 체크리스트를 주는 것과 같다고 비유합니다

## 남길 맥락과 뺄 맥락

- 남길 것은 Claude가 스스로 알 수 없는 것입니다. 말투, 목표, 시청자, 사업의 업무 프로세스, 그리고 왜 그 일을 하는지에 대한 목적입니다
- 뺄 것은 Claude가 스스로 찾을 수 있는 것(긴 폴더 목록)과 여러 곳에 중복된 지침입니다. 특정 작업에만 쓰는 상세 절차는 그 작업을 할 때 불러오게 합니다
- CLAUDE.md는 프로젝트가 무엇을 위한 것인지, 주의할 위험, 상세 지침이 어디 있는지를 알려 주는 출발점으로 유지합니다

## /doctor로 설정 감사하기

- 새 세션에서 `/doctor`를 실행하면 스킬, 메모리, 플러그인, 설정, 설치 상태를 점검합니다
- 스킬별 설치 위치, 설치 후 사용 횟수, 차지하는 토큰(YAML 프론트매터 기준)을 표로 보여 줍니다. 사용 기록이 없는 오래된 스킬 18개를 짚었고, 최근 만든 스킬은 나이를 고려해 남겼습니다. 최근 세션 50개를 분석했고 252번의 시작 카운터와 223개의 트랜스크립트를 살폈습니다. 삭제 전에는 다른 도구에서 쓰는 스킬이 아닌지 직접 확인하라고 합니다
- 중복도 찾았습니다. 프로젝트 맵이 라우팅 맵과 겹쳤고, 약 2,250자(약 563토큰)를 덜어낼 수 있었습니다
- 메모리 출처(프로젝트 CLAUDE.md, 사용자 전역 지침, 자동 메모리 인덱스, 로컬 CLAUDE.local.md)를 구분해 보여 줍니다. 데스크톱의 다른 영상 프로젝트에서 로드되는 약 2,000토큰짜리 파일도 찾아냈습니다. 프로젝트 안을 정리해도 다른 곳의 지침에 토큰을 내고 있을 수 있습니다
- 파일 이름이 틀린 스킬과 프론트매터 형식이 깨진 스킬 두 개를 찾았고, 감사 끝에 "전부 고쳐 줄까요?"라고 묻는 대로 고쳤습니다. 설치, 자동 업데이트, 자동 모드, 권한, 훅 설정도 점검합니다

## 유튜브 워크플로를 고친 사례

- 프롬프트는 "이 레포를 감사하고, 아이디어에서 촬영용 스크립트까지 가는 길을 빠르게 할 작은 변경을 보여 줘. 기존 시스템을 쓰고, 재사용할 파일을 밝히고, 지금은 아무것도 바꾸지 마"였습니다
- Claude는 아이디어, 리서치, 아웃라인, 스크립트, 텔레프롬프터 파일의 단계와 인계를 정리했습니다
- 핵심 발견은 아웃라인 스킬이 모은 증거를 스크립트 스킬이 확인할 파일에 저장하지 않는다는 점이었습니다. 감사한 영상 폴더 25개 중 `sources.md`가 있는 것은 세 개뿐이었습니다. 스크립트 스킬의 엄격한 재검증 규칙도, 1차 출처를 이미 확인했다면 그 결과를 이어받게 하자는 방향이었습니다
- 기존 스킬 두 개에 걸친 세 가지 변경이 제안됐고 발표자는 승인했습니다

## 감사를 정례화하기

- 스킬을 자주 추가하면 월 1회, 설정이 안정적이면 분기 1회, 그리고 새 모델로 바꿀 때마다 감사를 권합니다. 모델마다 설정과 스킬과 지침을 다르게 해석하기 때문입니다
- 감사 프롬프트나 doctor를 믿게 되면 Claude 데스크톱 앱의 로컬 예약 작업으로 `/doctor`를 돌리고, 제안만 승인하거나 거절하면 됩니다
- 사람은 업데이트를 잊고, 같은 정보를 두 번 입력하고, 삭제를 잊습니다. AIOS가 이런 반복 작업과 정리를 자동화하면 스스로 개선되는 깔끔한 시스템이 되고, 이후 팀이 각자 같은 일을 하지 않도록 동기화하는 것도 생각할 수 있다고 말합니다
