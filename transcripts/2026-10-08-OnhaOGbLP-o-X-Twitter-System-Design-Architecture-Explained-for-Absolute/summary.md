# X (Twitter) System Design Architecture Explained for Absolute Beginners

## 한 줄 요약

Cloud X Berry가 X(트위터)의 시스템 설계를 사용자 행동 순서대로 설명합니다. 큰 시스템이 빠른 비결은 사용자 요청 중의 작업을 줄이고 백그라운드 작업을 늘리는 것이며, 그 핵심 수단이 캐싱, 이벤트 스트리밍(Kafka), 비동기 처리라는 결론입니다. 서비스 이름은 설명용이고 실제 회사의 이름과 다를 수 있다고 밝힙니다.

## 읽기 중심 서비스라서 타임라인을 미리 준비한다

- X는 읽기 작업 비중이 매우 높습니다. 둘러보는 사용자가 많고 글을 올리는 사용자는 적습니다
- 앱을 열 때마다 팔로우 대상 확인, 최근 게시물 조회, 정렬, 순위 매기기를 처음부터 하면 이 규모에서는 너무 비쌉니다
- 요청은 API 게이트웨이나 로드 밸런서를 거쳐 타임라인 서비스로 가고, 먼저 Redis 같은 캐시를 확인합니다. 있으면 바로 반환하고, 없으면 팔로우 데이터와 트윗으로 타임라인을 만들어 캐시에 저장한 뒤 반환합니다
- 팔로우는 팔로우 서비스가 맡고, 이 관계를 소셜 그래프라고 부릅니다. 팔로우는 일방향이며, 읽기가 잦아서 많이 쓰는 팔로우 목록은 캐시에 둘 수 있습니다

## 트윗 게시와 저장

- 게시 요청은 트윗 수집(ingestion) 서비스로 갑니다. 새 트윗 데이터가 백엔드로 들어오는 진입점이라 이렇게 부릅니다
- 이미지와 동영상은 에셋 서비스가 S3, Azure Blob Storage, Google Cloud Storage 같은 오브젝트 스토리지에 저장하고, CDN이 사용자와 가까운 곳에서 전달해 더 빨리 로드되게 합니다
- 트윗 레코드는 Cassandra 같은 분산 데이터베이스에 저장할 수 있습니다. 대량의 쓰기를 처리하고 데이터를 여러 머신에 분산하기 때문입니다

## Kafka로 나머지 일을 뒤로 미룬다

- 트윗이 저장되면 같은 요청 안에서 모든 것을 갱신하지 않고 Kafka에 이벤트를 발행합니다. 게시가 느려지는 것을 피하기 위해서입니다
- 한 서비스가 발행한 이벤트를 여러 백엔드 서비스가 나중에 소비합니다. 이것이 비동기 처리이며, 사용자는 백그라운드 작업이 끝나기를 기다리지 않습니다
- 타임라인, 검색, 트렌드, 알림이 모두 이 이벤트 흐름으로 갱신됩니다

## 팬아웃: 하이브리드 설계

- 트윗은 한 번 쓰이지만 많은 팔로워의 타임라인에 나타나야 합니다. 트윗 프로세서가 Kafka 이벤트를 읽고 어떤 타임라인이 받을지 정하는 것이 팬아웃입니다
- 쓰기 시 팬아웃: 트윗이 쓰인 뒤 팔로워의 캐시된 타임라인을 갱신합니다. 일반 사용자에게 잘 맞습니다
- 읽기 시 팬아웃: 팔로워가 수백만인 유명 사용자의 트윗은 한꺼번에 밀어 넣으면 시스템에 과부하가 오므로, 타임라인을 열 때 끌어와 캐시된 타임라인과 합칩니다
- 실용적인 설계는 하이브리드입니다. 일반 사용자는 쓰기 시 팬아웃, 유명 사용자는 읽기 시 팬아웃을 씁니다. 활성 사용자는 캐시에 준비된 타임라인을 받고, 비활성 사용자는 돌아올 때 타임라인을 만들며, 실시간 사용자는 웹소켓으로 즉각 업데이트를 받습니다

## 검색은 Elasticsearch가 맡는다

- 트윗 저장과 텍스트 검색은 다른 문제라서 메인 트윗 데이터베이스에서 직접 검색하지 않습니다
- Kafka의 또 다른 컨슈머가 트윗을 Elasticsearch에 색인하고, 검색 서비스가 거기에 질의해 일치하는 트윗을 반환합니다. 인기 검색 결과는 잠시 캐시할 수 있습니다

## 트렌드는 증가 폭을 본다

- 같은 트윗 이벤트 스트림을 스트리밍 시스템이 읽어 해시태그와 중요한 단어를 살피고 흔한 단어를 제거한 뒤, 일정 시간 창 안에서 세어 봅니다
- 단순히 가장 많이 쓰인 단어가 아니라 평소 활동량에 비해 갑자기 늘어나는 주제를 찾습니다. 결과는 캐시에 저장해 트렌드 서비스로 보여줍니다
