# Kafka 제대로 이해하기 | 멤버십 영상

## 한 줄 요약

카프카는 단순한 메시지 큐가 아니라 $O(N^2)$의 복잡한 파이프라인을 $O(N)$으로 통합하고 분산 시스템의 순서·일관성을 보장하기 위해 설계된 '분산 커밋 로그(Log as a Service)'이며, 모든 분산 아키텍처는 로그 레이어와 서빙 레이어로 환원된다.

## 분산 시스템에서 '로그(Log)'의 본질과 역할

- **로그의 정의**: 추가 전용(Append-only)이자 시간 순서로 정렬된 레코드 배열
- **물리적 시계의 한계와 논리적 타임스탬프**: 분산 환경의 각 노드는 NTP 동기화 오차나 네트워크 지연으로 물리 시계가 일치하지 않음. 반면 로그의 순번(Offset)은 어떤 환경에서도 불변하는 절대적 순서를 제공하여 분산 일관성의 근간이 됨
- **상태 기계 복제 원칙 (State Machine Replication)**: 동일하고 결정론적인 프로세스가 같은 초기 상태에서 동일한 순서의 입력을 받으면 항상 동일한 최종 상태에 도달함. 결국 분산 합의(Paxos, Raft, ZAB)의 본질은 분산 로그의 순서를 합의하는 것

## 테이블과 로그의 이중성 (Duality)

- **로그는 원본, 테이블은 파생물**: 로그의 변경 사항을 처음부터 순서대로 재생(Replay)하면 현재 상태의 테이블이 되고, 테이블의 변경분을 방출하면 변경 로그(Change Data Capture)가 됨
- **현대 아키텍처 패턴의 뿌리**:
  - **이벤트 소싱 (Event Sourcing)**: 상태 자체가 아닌 상태를 변경시킨 모든 이벤트 로그를 단일 진실 공급원으로 저장하여 완벽한 감사 추적과 과거 시점 복원 보장
  - **CQRS**: 쓰기는 이벤트 로그에 집중하고, 읽기는 로그를 구독해 목적에 맞게 사전 계산된 파생 뷰(테이블)에서 처리
  - **Kafka Streams (KStream & KTable)**: KStream(로그)을 실시간 집계한 뷰가 KTable(테이블)

## $O(N^2)$ 파이프라인에서 $O(N)$ 중앙 로그 허브로

- **점대점(Point-to-Point) 통합의 붕괴**: $N$개의 특화 시스템(검색 엔진, 캐시, DW, 하둡 등)이 서로 직접 데이터를 주고받으면 최대 $N(N-1)$개의 커스텀 파이프라인이 필요해 거미줄 복잡도 발생
- **중앙 로그 허브 도입**: 모든 생산자는 중앙 로그에 한 번만 발행하고, 각 컨슈머는 자신의 처리 속도에 맞춰 독립적으로 구독($O(N)$으로 단순화). 컨슈머가 다운되어도 마지막 읽은 오프셋부터 재개 가능
- **생산자 정제 책임 (Producer Cleaning)**: 중앙 DW 팀이 수많은 시스템의 데이터를 일일이 정제하느라 조직 전체의 병목이 되던 구조를 타파하고, 데이터를 가장 잘 아는 생산자가 정제 후 로그에 발행하도록 책임을 분산

## 카프카 vs 전통적 메시지 큐 (RabbitMQ)

| 비교 항목 | 전통적 메시지 큐 (RabbitMQ) | 분산 커밋 로그 (Kafka) |
|---|---|---|
| **설계 목적** | 일회성 태스크 전달 (소비 시 삭제) | 데이터의 영구 기록 및 장기 보존 |
| **재생 (Replay)** | 불가능 (메시지 소비 후 소멸) | 오프셋 재설정을 통해 과거 시점 언제든 재소비 가능 |
| **로그 압착 (Log Compaction)** | 미지원 | 같은 키(Key)에 대해 최신 상태만 남기고 과거 데이터를 압착하여 '키-값 상태 저장소'로 활용 가능 |
| **확장성** | 브로커 큐 단위 처리 | 토픽을 여러 파티션으로 분할하여 병렬 처리량 선형 확장 |

## 분산 시스템의 2대 레이어와 시스템 언번들링

모든 분산 시스템은 다음 두 레이어의 조합으로 분해(Unbundling)할 수 있습니다:
1. **로그 레이어 (Log Layer)**: 순서 보장, 복제, 내구성, 장애 복구 담당 (예: Kafka)
2. **서빙 레이어 (Serving Layer)**: 빠른 쿼리 응답을 위한 인덱싱 및 조회 전용 파생 뷰 (예: Redis의 키-값 캐시, Elasticsearch의 역색인, RDBMS의 B-Tree, OLAP의 컬럼 스토어)

> "배치 처리는 윈도우 크기가 하루인 스트림 처리일 뿐이다." 데이터는 연속적으로 발생하므로 실시간 스트림 처리가 본질이며, 로그가 모든 실시간 데이터 흐름의 척추가 됩니다.
