# 한국어 번역

## 에이전트 자율성의 미래

에이전트가 어떤 작업을 자율적으로 수행하도록 하려면 모호성을 얼마나 걷어내야 할까요? 명시적으로 프롬프트에 쓴 내용보다 현재 맥락과 환경에서 더 많은 단서를 얻도록 할 수 있습니다.

저는 프롬프트를 최대한 적게 쓰는 사람이 되고 싶습니다. 모델이 판단에 필요한 도구와 맥락을 갖도록 일을 해 두면 프롬프트에 모든 것을 미리 넣을 필요가 없습니다. 우리가 가진 도구로 무엇이 가능한지 계속 새롭게 생각해야 합니다.

## 에이전트 하네스란 무엇인가

AI 에이전트는 간단히 말해 대규모 언어 모델과 에이전트 하네스로 이뤄집니다. 하네스는 LLM을 제외한 에이전트의 나머지 부분입니다. 예를 들어 Gemini Flash가 모델이라면 Google Antigravity는 하네스입니다.

“하늘은 왜 파란가요?”나 “농담을 해 주세요” 같은 질문은 모델이 이미 알고 있는 답을 말하면 됩니다. 하지만 “비옷을 입어야 할까요?”라는 질문에는 현재 날씨 정보가 필요합니다. 모델은 날씨를 알아보라는 요청을 내고 하네스는 실제 날씨를 확인합니다. 하네스가 “맑고 화창하다”는 정보를 원래 질문과 함께 모델에 돌려주면 모델은 비옷이 필요 없다고 답할 수 있습니다. 하네스는 입력된 텍스트를 출력하는 능력을 넘어 에이전트에 힘을 보태는 모든 부분입니다.

이 개념을 자세히 살펴보기 위해 진행자가 용어를 만든 Google 엔지니어 Ryan Leopo와 인터뷰합니다.

## 하네스 엔지니어링의 배경

Ryan은 코딩 에이전트가 완전히 자율적으로 일하게 만들 방법을 연구했고, 관련 작업을 올해 2월에 공개한 뒤 업계에서 큰 관심을 얻었다고 설명합니다. 그는 지난해 5월경부터 코드 편집기를 거의 열지 않고 자연어 명세로 일을 해 왔다고 합니다.

모델이 점점 좋아지더라도 사용자가 원하는 바를 저절로 더 잘 알게 되는 것은 아닙니다. 하네스 엔지니어링은 모델 주변의 맥락과 환경을 다듬어 모델이 매번 시작할 때 원하는 결과가 무엇인지 더 잘 이해하도록 하는 일입니다. 좋은 결과의 기준을 환경에 반영할수록 모델은 더 복잡한 작업을 수행할 수 있습니다.

Ryan은 린터와 분명한 코딩 규칙 등 소프트웨어 엔지니어링의 좋은 관행을 모두 에이전트 우선 작업 흐름에 적용해 왔다고 합니다. 같은 프롬프트를 바꾸지 않고 다시 시도하는 것은 가장 단순한 개입이지만 동료나 시간이 달라지면 확장되지 않습니다.

## 시프트 레프트와 맥락 자동화

그는 개입을 소프트웨어 개발 과정에서 더 왼쪽으로 옮긴다고 말합니다. 문서, 그 문서로 안내하는 `agents.md`, 정적 검증기와 테스트를 추가할 수 있습니다. 더 나아가 정적 검증기 자체가 에이전트에 프롬프트를 제공하거나 평가를 통해 모델 개선에 기여할 수도 있습니다.

여기서 “왼쪽으로 옮긴다”는 말은 모델 환경과 도구에 적용하는 개입을 가능한 한 저렴하게 만들고, 텍스트로 작동하는 에이전트가 더 정교하고 자동화된 방식으로 필요한 텍스트를 얻도록 하는 뜻입니다. 프롬프트에 모든 내용을 붙이는 것은 작업 과정의 뒤쪽 개입입니다. 모델이 자체 문서 모음을 검색해 필요한 맥락을 찾도록 도구를 주면 스스로 발견할 수 있습니다.

관측성 데이터는 PromQL 같은 익숙한 도구로 수집·집계하고 CLI로 다루면 추론을 결정론적 작업으로 바꾸기 쉽습니다. 모델은 학습 데이터에서 자주 접한 도구를 잘 활용할 수 있습니다. 문서의 링크를 본문 흐름에서 떼어 관련 문단 근처에 두고, 링크가 올바른 위치에 있는지 테스트해 맥락 효율과 사람이 읽기 쉬운 문서를 함께 유지하는 사례도 들었습니다.

에이전트가 만든 코드나 Google 문서·스프레드시트 같은 최종 결과물을 검토하는 것이 중요합니다. 결과가 타당하지 않다면 어떤 입력과 실행 과정이 그런 결과를 만들었는지 알아낼 수 있어야 합니다.

## 긴 작업에서도 일관성을 유지하기

하네스 엔지니어링이 해결하려는 문제는 에이전트가 긴 시간 동안 일관된 작업을 할 수 있느냐는 것입니다. 조직의 일은 한 번에 완성되지 않고 반복적으로 발전합니다. 에이전트 결과를 조직이 생각하는 좋은 기준에 계속 맞춰야 합니다. 검토하기 쉬운 작은 PR은 쉽게 운영할 수 있고, 에이전트가 이를 검토하게 할 수도 있습니다. 작은 PR의 상태 공간을 줄이면 사람의 개입을 줄이면서 더 긴 작업을 맡길 수 있습니다.

작은 변경 하나가 괜찮다고 얼마나 확신할 수 있는지, 그런 변경을 이어 붙여 긴 작업에서도 괜찮은 결과를 얻을 수 있는지가 중요합니다. 가드레일이 충분하고 결과를 신뢰할 수 있으면 언어 전체 이전처럼 큰 작업도 가능해집니다.

팀원들의 전문성을 에이전트에 반영하면 다양한 분야의 역량을 한데 모을 수도 있습니다. 에이전트가 수행할 작업을 분류하고 필요한 전문 지식과 맥락을 동적으로 찾아 불러오는 것은 높은 자율성의 일부입니다. 사람이 세세한 코드와 프롬프트를 모두 지정하지 않으려면 에이전트가 어떤 지식을 활성화할지 판단해야 합니다.

## 하네스를 직접 만들 필요는 없다

Ryan은 자신이 하네스를 직접 만든 적은 없다고 말합니다. 하네스 엔지니어링이라는 표현이 모든 사람이 자체 하네스를 만들라는 뜻은 아닙니다. 최신 모델을 사용하고 높은 목표를 세우되, 가능한 일에 대한 기존 생각을 계속 갱신하라고 조언합니다.

에이전트가 일을 잘하지 못할 때 원인을 조사하고, 코드와 문서를 저렴하게 만들 수 있다는 점을 활용해 환경을 개선합니다. 도구를 더하고 문서를 풍부하게 만들며 에이전트가 적시에 문서를 찾도록 도와주면 사람의 직접 통제를 줄이면서 더 복잡한 일을 맡길 수 있습니다. 하네스가 제공하는 파일 읽기, Git, 임의 명령 실행 같은 도구와 맥락에 투자하면 최신 모델을 바꾸어 써도 가치가 남습니다. 반대로 에이전트가 좋아질수록 불필요한 제약이 될 정도로 환경을 과하게 구성하면 매몰 비용에 묶일 수 있습니다.

## Google Cloud 운영 에이전트

Ryan은 Google Cloud를 운영하는 에이전트를 만들고 있습니다. 모델은 현재 유용한 작업으로 끌어낼 수 있는 역량보다 더 뛰어나다는 “역량 과잉”이 있다고 보고, 실제 배포 영역을 넓혀 그 능력을 활용하려 합니다. Google Cloud는 매우 크고 복잡한 컴퓨터와 같으며, 성공적인 에이전트에는 컴퓨터가 필요합니다. 에이전트가 클라우드를 잘 운영하도록 만들고 고객도 이를 직접 활용하게 하는 것이 목표입니다.

그는 도구와 맥락이 모델과 하네스가 계속 발전해도 에이전트에 필요한 확장 가능한 인터페이스라고 강조합니다. 에이전트는 조직이 생각하는 좋은 결과에 맞춰 마지막 단계에서 조정될 맥락을 계속 필요로 합니다.

## 직접 만드는 하네스의 구성

이어지는 실습에서는 모델을 둘러싼 하네스가 무엇을 하는지 코드로 살펴봅니다. 모델 자체는 도구를 쓸 줄 알아도 실제 환경과 상호작용할 수단이 없습니다. 하네스는 모델의 의도를 실제 동작에 연결합니다. 작업별로 최선의 하네스는 다르며, 반복 횟수, 도구 종류와 사용 시점, 메모리의 중요도와 검색 시점을 결정해야 합니다.

선형 하네스는 도구로 파일을 살펴보고 추천을 출력한 뒤 끝납니다. 항상 같은 흐름을 거치므로 어느 정도 결정성이 필요한 작업에 적합합니다. 폐루프 하네스는 종료 조건까지 계속 반복합니다. 코드를 수정하고 테스트를 실행한 뒤 통과하지 못하면 실패 이유를 메모리에 넣고 다시 수정합니다. 다섯 번 반복 후 끝내는 식으로 반복 횟수를 제한할 수도 있습니다.

Google ADK 같은 도구를 쓰면 메모리 압축과 안전 장치 등 기능을 직접 하나씩 구현하지 않고도 더 유연한 하네스를 만들 수 있습니다. 실습에서는 파일 삭제, 데이터베이스 삭제, GitHub 푸시 같은 위험 명령을 차단하는 함수를 보여줍니다.

Antigravity, Claude Code, Cursor 같은 도구가 각자 특정 방식의 컴퓨터 사용, 메모리, 문제 해결에 맞춰져 있습니다. 어느 하나가 모든 문제에 최선인 것은 아닙니다. 모델을 편하게 쓰도록 만드는 핵심은 모델 그 자체뿐 아니라 모델 주변의 하네스 설계입니다.

## 고성능 에이전트 개발 스택: 모델, 하네스, 지식

영상 후반부에서는 코딩 에이전트의 개발 스택을 모델, 하네스, 지식의 세 계층으로 설명합니다. 에이전트는 연속된 반복 루프를 실행할 수 있으므로 한 작업을 끝내려면 디렉터리 검사, 함수 수정, 단위 테스트 등의 단계를 20~60회 수행할 수 있습니다. 이런 순차 호출이 많으면 속도와 비용이 누적됩니다. 그래서 가볍고 빠른 모델은 실시간 에이전트 루프를 실용적으로 만듭니다.

진행자는 자신의 이번 주 기본 모델로 Gemini 3.8 Flash를 꼽습니다. 두 번째 계층인 하네스에서는 Antigravity의 Boost 명령을 소개합니다. 단일 모델을 오케스트레이터로 바꾸고 전문 하위 에이전트를 병렬로 실행한 뒤 별도의 검증 단계를 수행합니다. 일상적 기능이나 UI 작업에는 기본 에이전트가 빠르고 효율적이므로 Boost는 복잡한 엔지니어링 문제에 쓰라고 권합니다.

세 번째는 지식 계층입니다. Google Skills 저장소는 Google Cloud, Firebase, Flutter, Maps 등 100개 넘는 스킬을 제공합니다. 스킬은 에이전트가 필요할 때 불러오는 분야별 지식입니다. MCP 서버나 무거운 플러그인과는 달리 정돈된 맥락을 제공해 에이전트가 추측하지 않도록 돕습니다. Claude Code, Codex, Google Antigravity 등 하네스에 종속되지 않고 사용할 수 있습니다.

빠른 모델로 반복 루프를 만들고, 복잡한 작업에는 조정된 에이전트 팀을 쓰며, Google 관련 작업에는 전문 지식을 제공하는 스킬을 사용할 수 있습니다.
