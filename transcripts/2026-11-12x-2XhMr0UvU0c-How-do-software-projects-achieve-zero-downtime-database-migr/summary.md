# 무중단 DB 마이그레이션: expand and contract

## 결론부터

발표자는 프로덕션 DB의 컬럼 이름을 바꾸는 한 줄 마이그레이션이 rolling deploy 중에 구버전·신버전 코드가 공존하기 때문에 다운타임을 만든다고 설명합니다. 해법으로 "expand(새 구조 추가) → migrate(데이터·트래픽 이전) → contract(기존 구조 삭제)"의 7단계를 제시하며, 각 단계를 따로 배포해 모든 순간에 구버전과 신버전이 모두 동작하게 하라고 결론짓습니다.

## 핵심 내용

- **문제 설정과 실패 원인 (0:00-2:12):** 구급차 배차 앱의 `address` 컬럼을 `pickup_address`로 바꾸는 사례입니다. Kubernetes가 pod 3개를 하나씩 교체하는 동안 구버전 pod가 사라진 컬럼을 요청해 500 에러가 나고(약 3분의 1 호출 실패), 마이그레이션을 배포 뒤로 미루면 반대로 신버전 pod가 실패한다고 말합니다. 점검 시간(maintenance window)은 이 앱에는 쓸 수 없다고 봅니다.
- **패턴과 1단계 expand (2:12-3:33):** 실행 중인 코드가 견딜 수 없는 변경을 하지 않고 작은 안전한 단계로 나눕니다. 1단계는 NOT NULL·default·index 없이 nullable 컬럼(`pickup_address`, `hospital_id`)만 추가하는 것이며, Postgres에서는 default 없는 nullable 컬럼 추가가 테이블 정의만 건드려 거의 즉시 끝난다고 설명합니다.
- **Dual write와 batch backfill (3:33-5:35):** 2단계는 코드 변경으로, 정정이 생길 때마다 한 문장으로 두 컬럼에 함께 쓰되 읽기는 기존 컬럼에서 합니다(trigger로 대체 가능). 3단계는 새 컬럼이 빈 행만 골라 작은 배치로 복사하며, 한 배치가 0행을 갱신하면 끝입니다. 이후 `CREATE INDEX CONCURRENTLY`로 인덱스를 만듭니다. 앱이 읽어 둔 옛 값으로 복사하면 그 사이의 정정을 덮어쓰는 경쟁 상태가 생기므로, `pickup_address = address`처럼 DB 안의 단일 UPDATE로 복사하라고 합니다.
- **읽기 전환과 대기 (5:35-6:28):** 복사 후 표본 비교로 검증하고, 4단계에서 읽기를 새 컬럼으로 옮깁니다. 쓰기는 양쪽에 유지해 롤백 안전망으로 삼고, 하루 또는 한 릴리스 주기를 기다립니다. 야간 리포트, 분석 대시보드, trigger, stored procedure 등 다른 소비자를 쿼리 로그와 코드 검색으로 찾아 옮긴 뒤에 진행합니다.
- **contract와 일반화 (6:28-8:26):** 6단계에서 앱이 기존 컬럼 쓰기를 중단하고, 7단계는 백업 후 컬럼을 삭제하는 유일한 되돌릴 수 없는 단계입니다. 이름 분할, 컬럼 타입 변경, 테이블 이전, API 필드 변경에도 같은 형태를 쓰며, 새 컬럼만 추가할 때는 한 단계로 충분하다고 말합니다.

## 배울 점과 적용 조건

- 이름 변경·타입 변경·분할·삭제처럼 실행 중인 코드가 의존하는 스키마 변경에는 "추가 → 이중 쓰기 → backfill → 읽기 전환 → 쓰기 중단 → 삭제"를 배포 단위로 쪼개 적용할 수 있습니다. 단순 컬럼 추가에는 과합니다.
- backfill은 멱등한 배치(대상 조건이 `새 컬럼 IS NULL`)와 DB 내부 단일 UPDATE로 짜면 재실행과 동시 쓰기에 안전하다는 점이 바로 쓸 수 있는 설계 포인트입니다.
- 비용은 단계마다 배포 한 번과 대기 시간, 이중 쓰기 기간의 코드 복잡도이며, 영상은 삭제 전 다른 소비자(리포트·대시보드·stored procedure) 확인이 필수 전제라고 강조합니다.

## 근거와 한계

- **영상의 근거:** 코드 시연이나 실측 수치는 없고, 애니메이션 카드와 가상의 배차 앱 시나리오(아샤의 주소 정정 사례)로 논리를 전개합니다. SQL은 화면에 나오지만 자막에는 대부분 담기지 않았습니다.
- **평가:** 단계 순서와 각 단계의 롤백 가능성은 논리적으로 일관되며, backfill 경쟁 상태 예시도 설득력이 있습니다. 다만 대용량 테이블의 lock·replication lag·배치 크기, 외래 키·제약 조건 추가 시점, ORM·마이그레이션 도구 사용법은 다루지 않아 실제 적용에는 보완이 필요합니다.
- **확인 범위:** 자막 기반 평가입니다. Postgres의 nullable 컬럼 추가가 즉시 끝난다는 설명과 `CONCURRENTLY` 동작은 영상 내 주장이며 외부 미검증입니다. 게시일은 defuddle이 가져오지 못해 알 수 없습니다.
