# summary.md 작성 규칙

영상 폴더의 `summary.md`를 쓸 때 이 형식을 그대로 씁니다. 매번 다르게 쓰지 않습니다.

## 프론트매터

필드는 아래 순서로 씁니다. `refs`만 선택 사항입니다. `watch`와 `reason`은 원문 전체를 읽고 아래 판정 기준에 따라 작성합니다.

```yaml
---
title: "컴파운드 엔지니어링의 시대입니다"
source: "https://www.youtube.com/watch?v=m8pBazNPvZE"
published: 2026-08-22
watch: "요약만"
reason: "개발 과정의 병목을 설명하지만, 생산성 향상 주장은 비교 실험보다 발표자의 경험에 의존한다."
refs:
  - compound-engineering-plugin
---
```

| 필드 | 규칙 |
|---|---|
| `title` | 채널 접두사(`[한영자막]`)를 뗀 제목 |
| `source` | `original.md` 프론트매터의 `source`를 그대로 |
| `published` | 게시일을 날짜만 표기. 게시일을 모르는 `x` 폴더는 `null`로 쓰며 수집일을 게시일로 취급하지 않습니다 |
| `watch` | `추천`, `요약만`, `건너뛰기`, `판단보류` 중 하나 |
| `reason` | 판정의 결정적 이유를 구체적인 한 문장으로. 얻을 내용과 한계를 짚습니다 |
| `refs` | `refs/` 아래 **폴더 이름만**. 참조가 없으면 필드를 통째로 생략 |

`refs`에 경로(`../../refs/...`)를 적지 않는 이유는 폴더를 옮겨도 안 깨지고 `refs/index.md`와 대조하기 쉬워서입니다.

## 본문

프론트매터 다음에 제목 한 줄, 그다음 내용입니다. 영상·원문·번역 링크를 헤더에 다시 적지 않습니다 — 프론트매터의 `source`와 같은 폴더의 파일들이 이미 그 역할을 합니다.

다음 순서를 따르며, 일반 요약은 1분 안팎에 읽을 분량을 목표로 합니다.

```markdown
## 결론부터

[무엇에 관한 영상이며 발표자가 어떤 결론을 내리는지 1~2문장.]

## 핵심 내용

- [핵심 주장과 이를 뒷받침하는 설명·사례. 최대 3개.]

## 배울 점과 적용 조건

- [구체적으로 배울 개념·방법·도구와 적용할 상황, 전제·비용·제약. 최대 3개.]

## 근거와 한계

- **영상의 근거:** [코드 시연, 실험 조건, 운영 사례, 인용 등 실제 제시한 근거. 없으면 없다고 명시.]
- **평가:** [그 근거가 결론을 어디까지 지지하는지와 빠진 비교·조건·반례.]
- **확인 범위:** [자막 기반 평가인지 외부 검증인지. 외부 확인 시 출처 링크.]
- **홍보성:** [협찬 고지·제품 유도 등 관찰된 사실과 기술 설명에 미치는 영향. 특별한 징후가 없으면 생략.]
```

## 시청 가치 판정과 1차 필터링

`original.md`의 자막 전체에서 주제, 결론, 구체적인 학습 내용, 제시한 근거, 홍보 요소를 확인한 뒤 판정합니다. 제목의 과장이나 채널 인상만으로 평가하지 않습니다. 위 프론트매터 예시는 형식 설명이며 실제 영상의 판정을 대신하지 않습니다.

| 판정 | 기준 |
|---|---|
| `추천` | 구체적인 코드·설계·실험·실패 사례·비교 등 배울 내용이 있고, 요약으로 놓치는 설명이나 시연을 볼 가치가 있음 |
| `요약만` | 핵심 동향이나 유용한 정보가 있으나 요약으로 충분함. 소개·목록·반복 설명 위주이거나 일부 주장에 근거가 부족함 |
| `건너뛰기` | 홍보·가입 유도가 중심이고 기술 정보가 빈약하거나, 일반론·과장·반복에 비해 구체적으로 얻을 내용이 거의 없음 |
| `판단보류` | 자막 누락, 시각 자료 의존 등으로 핵심 내용이나 학습 가치를 평가하기 어려움. 필요한 추가 자료를 밝힘 |

- 광고 여부와 학습 가치는 따로 봅니다. 협찬·제휴·자사 제품 소개가 있어도 구체적인 기술 설명은 평가합니다. 홍보 징후만으로 유료 광고라고 단정하지 않습니다.
- 기본 개념도 대상 독자와 설명의 구체성에 따라 가치가 있습니다. 사용자의 숙련도를 모르면 "초보자에게 유용하지만 경험자에게 새 내용은 적음"처럼 적용 대상을 씁니다.
- 근거 부족은 거짓이라는 뜻이 아닙니다. 근거 부족만으로 `판단보류` 처리하지 말고, 실제로 얻을 내용에 따라 판정합니다.
- `건너뛰기`는 긴 요약 대신 `결론부터` 아래에 주제와 발표자의 결론, 얻을 내용이 적은 이유, 근거·홍보성 판단을 총 3~5문장으로 씁니다. `판단보류`도 짧게 쓰되 확인한 내용과 판단에 필요한 자료를 명시합니다.
- 필터링은 판정과 요약 분량 조절로 수행합니다. 파일이나 재생목록 항목을 삭제하는 동작과 연결하지 않습니다.

## 근거 검토와 작성 규칙

- 발표자의 주장에는 주체를 드러냅니다. 작성자의 평가와 외부 확인 내용은 `근거와 한계`에서 구분합니다.
- 데모 한 번과 일반적인 성능 입증, 개인 경험과 재현 가능한 결과를 구분합니다. 수치에는 영상에서 밝힌 비교 대상·버전·조건을 함께 적고, 빠졌다면 한계로 씁니다.
- 도입 판단을 좌우하는 핵심 주장(성능 우위, 라이선스, 보안, 비용, 지원 여부 등)은 가능한 경우 공식 문서·저장소·논문 등 1차 자료로 확인합니다. 빠르게 변하는 정보는 영상 당시와 확인 시점의 차이를 밝힙니다.
- 외부 확인을 하지 못한 사항은 "영상 내 주장, 외부 미검증"으로 명시합니다. 추론상 그럴듯함을 사실 검증 완료로 표현하지 않습니다.
- 원문 밖의 배경 설명이나 조언은 작성자의 보충으로 표시합니다. 근거·수치·실패 사례를 만들어 넣지 않습니다.
- 타임스탬프는 넣지 않습니다. 외부 검증 출처 링크는 해당 평가 옆에 둡니다.
- 완료 전 첫 두 문장만 읽어도 영상의 주제와 결론을 알 수 있는지, 판정 이유가 본문의 근거와 일치하는지 확인합니다.
