# 코드 리뷰 (Code Review)


## 아티팩트 루트 (Artifact Root)

<!-- ce-docs-root:start -->
**아티팩트 경로를 구성하기 전에 CE 아티팩트 루트 `<root>`를 확인하세요.**

- `docs_root`는 `<repo-root>/.compound-engineering/config.yaml`에서만 **읽습니다** (`<repo-root>` = `git rev-parse --show-toplevel`). `config.local.yaml`에서는 읽지 않습니다. 설정되지 않은 경우 -> 이전과 동일하게 `<root>`는 `docs`입니다.
- 설정된 값을 **검증합니다**: 심볼릭 링크가 해석된 실제 경로가 리포지토리 내부에 유지되고 리포지토리 루트도 아니며 `.git/` 아래도 아닌 리포지토리 상대 디렉토리여야 합니다. 그렇지 않은 경우 `docs_root`와 해당 값을 명시하는 오류와 함께 중단합니다. 절대 `docs`로 대체(fallback)하지 마세요.
- `<root>`를 유일한 아티팩트 위치로 **사용합니다**: 없으면 생성하고, 각 경로를 이 스킬의 자체 하위 디렉토리가 포함된 `<root>/<subdir>`로 구성하며, `docs`를 함께 읽지 마세요.
<!-- ce-docs-root:end -->

## 실행 스파인 (Execution spine)

다음 단계를 순서대로 따르세요. 참조 문서는 세부 사항을 제공하지만 순서를 변경하지는 않습니다. 아래에 명시된 각 참조 문서는 해당 단계의 필수 읽기 자료입니다: 해당 단계의 작업을 수행하기 전에 로드하세요.

1. 먼저 `references/modes-and-output.md`를 읽으세요. 인수의 의미, 리뷰어가 디스패치되기 전에 실행을 중단시키는 인수 충돌, 빠른 리뷰 단락(quick-review short-circuit) 적용 여부, 이 호출이 반환하는 내용을 확정합니다.
2. **1단계 (Stage 1).** `references/scope.md`를 읽고 검토 대상 diff, 범위 모드 및 결정론적 범위 신호를 결정합니다.
3. **2단계 (Stage 2).** `references/intent-and-plan.md`를 읽고 모든 리뷰어가 수신할 의도 요약을 작성하며, 6단계에서 요구사항 검증에 사용할 계획을 찾습니다.
4. **3단계 (Stage 3).** `references/persona-catalog.md` 및 `references/select-and-route.md`를 읽은 다음 위험 기반 리뷰어 로스터를 선택하고, 적용 가능한 표준 경로를 찾고, 적대적(adversarial) 경로를 바인딩합니다.
5. **3d단계 (Stage 3d).** 로컬 검토 트리에 대해 적대적 경로가 선택된 경우, **로컬 페르소나 디스패치 전에** `references/cross-model-review.md`가 정의하는 승인된 교차 모델 작업을 시작하고 유지합니다. 이 스킬을 호출하는 것 자체가 수신자와 머신을 떠나는 코드에 대한 필수 공개를 한 후 구성되거나 허용 목록에 있는 피어 경로에 대한 권한 부여가 됩니다. 사용자에게 두 번 확인을 요청하지 마며, 사용자가 해당 권한 부여를 반복하지 않았다는 이유로 피어를 건너뛰지 마세요. 외부 검토에 대한 사용자의 명시적 금지는 이를 재정의하며, 실시간 옵트인 없이 `cross_model_review_mode: off`로 설정된 체크아웃도 마찬가지입니다. 둘 다 경로를 바인딩하기 전에 해결됩니다. 시작된 피어는 이 단계에서 로컬 적대적 페르소나를 대체하며, 범위 지정, 허용 목록 추가, 연결, 인증 또는 시작의 실제 실패만이 로컬 대체 항목을 로스터에 남깁니다. 이후 단계에서는 해당 참조에 명시된 조건에 따라 여전히 로컬 리뷰어를 복원할 수 있습니다.
6. **4단계 (Stage 4).** `references/dispatch-reviewers.md`를 읽으세요. 구체화된 로컬 로스터를 호스트의 활성 에이전트 한도에 맞춰 크기가 조정된 하나의 포그라운드 동시 배치로 디스패치하고, 호스트가 반환하는 방식에 따라 종합 전에 모든 리뷰어를 수집합니다: 동일 메시지 호출이 동시에 실행되는 하나의 블로킹 대기, 서브에이전트 원시 기능이 비동기식인 반복적인 비폴링 수집 대기, 둘 다 적용되지 않는 직렬 디스패치. 로컬 리뷰를 폴링되는 백그라운드 작업으로 분리하는 것은 금지됩니다. 교차 모델 피어가 유일하게 분리된 작업이며, 이 배치와 겹칠 수 있습니다.
7. **5 및 6단계 (Stages 5 and 6).** 리뷰어 반환 결과가 준비되면 `references/finish-review.md`를 읽으세요. 피어를 한 번 접어 넣고, 문서화된 발견 사항 메커니즘을 실행하며, 참조가 선택한 모든 유효성 검사기를 실행합니다. 그런 다음에만 보고서를 반환합니다. 원시 리뷰어 아티팩트에서 직접 종합하지 마세요. 다중 에이전트 경로에서는 이 스킬의 보고서만 출력하세요: 빠른 리뷰 단락에만 속하는 하네스 네이티브 발견 사항 또는 보고 도구를 함께 호출하지 마세요.

## 운영 원칙 (Operating principles)

- **기본적으로 보고 전용(Report-only)이며 푸시하지 않습니다.** 단순 `ce-code-review` 호출은 발견 사항을 생성할 뿐 적용하지 않습니다. 적용 단계로 진입하려면 `apply:local` 또는 이 리뷰의 발견 사항을 적용하거나 수정하라는 호출 프롬프트의 명시적 사용자 요청이 필요합니다. 지원 중단된 `mode:autofix` 토큰은 둘 다 아닙니다. `mode:agent`는 나중에 발견 사항을 적용하는 워크플로우 내에 중첩되어 있더라도 트리를 변경하지 않습니다. 어떤 모드에서도 푸시하거나 PR을 열거나 티켓을 제출하지 마세요.
- **블로킹 프롬프트 금지.** `AskUserQuestion`, `request_user_input`, `ask_user` 또는 기타 블로킹 질문 도구를 사용하지 마세요. 명시적 토큰, git 상태, PR 메타데이터 및 대화로부터 의도, 계획, 범위를 추론합니다. 불확실한 부분은 커버리지 또는 판정에 기록하고 멈추어 묻지 마세요.
- **명시적 변경만 허용.** `gh pr checkout`, `git checkout`, `git switch` 또는 유사한 브랜치 전환 명령을 실행하지 마세요. PR 번호, URL 또는 브랜치 이름을 전달하는 것은 **리뷰 범위**를 선택하는 것이지 작업 트리를 변경할 수 있는 권한이 아닙니다. 커밋되지 않은 작업은 이를 보유한 체크아웃에서만 검토할 수 있으므로 기능 브랜치에서 이를 검토하려면 해당 브랜치를 유지(또는 직접 체크아웃)하고 `base:`를 전달하거나 대상을 지정하지 마세요.
- **메커니즘이 아닌 결과를 보고하세요.** 사용자에게 보여주는 내용은 검토에 관한 것입니다: 검토 대상, 포함된 커버리지 및 각 조건부 렌즈에 대한 한 줄 이유, 독립적인 교차 모델 패스, 그리고 발견 사항입니다. 내부 라벨, 디스패치 장부 관리, 설정 설명 등이 사용자 대면 텍스트에서 제외되는 이 스킬의 배관(plumbing) 대신 사용자가 인식할 수 있는 항목(PR 번호, 리뷰어의 우려 사항, 피어 모델 등)을 명시하세요. 영수증이 증명하는 것 이상으로 피어에 대해 주장하지 마세요. 이는 문구가 아니라 표출할 내용과 억제할 내용을 규율합니다. 자신의 어조를 사용하세요.

## 작업 가시성 (Task Visibility)

다중 에이전트 경로의 경우 리뷰 범위가 결정되면 가능한 경우 플랫폼의 작업 추적 기능을 사용하여 실행 스파인에서 파생된 짧은 사용자 대면 뷰를 표시합니다. 개별 페르소나, 설정 메커니즘 또는 도구 호출이 아닌 검토 결과를 추적합니다. 게이트가 실행될 때만 조건부 작업을 추가하고 의미 있는 전환 시 뷰를 업데이트합니다. 작업 추적 기능을 사용할 수 없는 경우 채팅에서 작업 목록을 시뮬레이션하지 않고 정상적인 진행 및 최종 보고서를 계속 진행합니다.
