정확한 동작을 보존하면서 명확성, 재사용성, 품질, 효율성을 위해 최근 변경된 코드를 단순화합니다. 간결한 코드보다 읽기 쉽고 명시적인 코드를 우선시하세요 — 줄 수를 줄이는 것이 목표가 아닙니다.


## 1단계: 범위(Scope) 식별

다음 순서로 단순화 범위를 결정합니다:

1. **사용자가 지정한 범위**가 가장 우선합니다. 이를 임의로 넓히지 마세요.
2. **그렇지 않고 git 환경인 경우**, 현재 브랜치와 베이스 브랜치를 비교하여 사용합니다. 사용할 수 있는 베이스가 없으면 스테이징된 변경사항과 스테이징되지 않은 변경사항(`git diff HEAD`)을 사용합니다.
3. **git 외부이거나 diff가 없는 경우**, 사용자가 지정한 파일이나 대화 앞부분에서 편집된 파일을 사용합니다.

위의 방법 중 어느 것으로도 비어있지 않은 범위를 얻지 못하면 추측하지 말고 중단하여 사용자에게 무엇을 단순화할지 물어보세요. 플랫폼의 블로킹 질문 도구를 사용합니다: Claude Code의 `AskUserQuestion`(스키마가 로드되지 않은 경우 먼저 `select:AskUserQuestion`으로 `ToolSearch` 호출), Codex의 `request_user_input`, Antigravity CLI(`agy`)의 `ask_question`, Pi의 `ask_user`(`pi-ask-user` 확장 필요). 하네스에 블로킹 도구가 없거나 호출 오류가 발생하는 경우(예: Codex 편집 모드)에만 호스트의 사용자 표시 채팅 화면에 번호가 매겨진 옵션으로 대체하세요 — 스키마 로드가 필요하다는 이유로 대체해서는 안 됩니다. 질문을 묵묵히 건너뛰지 마세요.

**사전 점검(Preflight).** 범위에 실질적인 사람이 작성한 코드가 없고 문서, 생성된 파일 또는 벤더링된 파일, 종속성/락파일 또는 기계적인 변경만 있는 경우 단순화할 항목이 없다고 보고하고 리뷰어 없이 중단합니다. 혼합된 범위의 경우 코드만 유지합니다. 이는 종류 게이트(kind gate)이며 크기 게이트가 아닙니다: 명시적인 작은 범위도 계속 실행되며, 크기나 비용 임계값은 호출자가 소유합니다.

플랫폼의 작업 추적 기능을 사용할 수 있는 경우 리뷰어당 하나의 작업을 생성하지 않고 검토, 적용 및 검증 결과를 표시합니다. 그렇지 않으면 채팅에서 작업 목록을 시뮬레이션하지 않고 계속 진행합니다.

## 2단계: 3개의 리뷰 에이전트를 병렬로 실행

사용 가능한 경우 플랫폼의 서브에이전트 원시 기능(Claude Code의 `Agent`/`Task`, Codex의 `spawn_agent`)을 통해 세 가지 범용 서브에이전트(코드 재사용, 코드 품질, 효율성 리뷰어)를 디스패치합니다. 그렇지 않은 경우 리뷰를 인라인 또는 직렬로 실행합니다. 각 리뷰어에 대해 이 스킬의 디렉토리에서 프롬프트 에셋을 읽고 완전한 컨텍스트를 가질 수 있도록 결정된 범위(전체 diff 또는 파일 세트)와 함께 **전체 파일 내용**을 서브에이전트의 프롬프트로 전달합니다:

- `references/personas/code-reuse-reviewer.md`
- `references/personas/code-quality-reviewer.md`
- `references/personas/efficiency-reviewer.md`

이 루브릭을 기억에 의존해 패러프레이징하지 마세요. 각 파일을 읽고 그대로 전달해야 합니다. 그렇지 않으면 리뷰어가 동작을 보존하도록 유지하는 게이팅 규칙을 잃게 됩니다.

**제한된 디스패치(Bounded dispatch).** 3명의 리뷰어를 대기열에 넣고 하네스가 한 번에 수락하는 수만큼만 시작합니다. 동시성/활성 에이전트 제한 오류는 리뷰어 실패가 아니라 배압(backpressure)으로 처리합니다(리뷰어를 대기열에 두고 슬롯이 비면 다시 시도). 호출 수정 후에도 지속되는 이유로 디스패치가 실패하면 동일한 프롬프트 에셋을 사용하여 상위 컨텍스트에서 해당 리뷰어의 패스를 인라인으로 실행하고 대체 사실을 한 줄로 공개합니다.

**모델 선택.** 현재 하네스가 알려진 오버라이드를 노출하는 경우 이 리뷰어들에게 플랫폼의 균형 잡힌 중간 티어 모델을 사용합니다. Claude Code에서는 Sonnet 클래스입니다. Codex에서는 활성 디스패치 원시 기능이 명시적 모델 또는 커스텀 에이전트 선택기를 노출할 때만 이 티어를 적용합니다. 작업 문구만으로는 다른 모델을 선택하지 않습니다. 그렇지 않은 경우 오버라이드를 생략하고 상위 모델을 상속합니다 — 실패하는 디스패치보다 상위 모델에서 정상 작동하는 패스가 낫습니다.

**권한 모드.** 디스패치 호출에서 `mode` 매개변수를 생략하여 사용자가 구성한 권한 설정이 적용되도록 합니다.

## 3단계: 문제 수정

서브에이전트가 반환했든 인라인으로 생성되었든 3개의 리뷰 결과가 모두 완료된 후에만 진행합니다. 가치 있는 발견 사항을 직접 적용합니다. 오탐(false positive) 및 낮은 가치의 발견 사항은 사용자에게 묻지 않고 건너뛴 것으로 기록합니다.

발견 사항을 평가하기 위해 필요한 경우 결정된 범위를 넘어 조사할 수 있지만, 해당 범위와 필요한 import/export 경계만 편집하세요. 사용자가 지정한 파일 또는 디렉토리 범위의 경우 해당 경계 또한 그 내부에 있어야 합니다. 변경 경계 외부를 편집해야 하는 수정 사항은 건너뜁니다.

각 수정 사항은 출력, 오류, 부수 효과 및 순서를 보존해야 합니다. 이를 확립할 수 없는 경우 건너뜁니다.

아직 배포되지 않은 현재 범위의 이전 반복에만 존재했던 인터페이스나 데이터 형태는 배포, 지속, 공개, 외부, 종속 브랜치 또는 결정된 범위 외부의 인-리포지토리 호출자가 없음을 확인한 후에는 보호되는 동작이 아닙니다. 필요한 모든 호출자 업데이트가 기존 변경 경계에 맞는 경우에만 해당 호환성 경로를 제거하고, 그렇지 않으면 보존하세요.

**안전 검사를 절대 단순화하여 없애지 마세요.** 신뢰 경계 유효성 검사, 데이터 손실 방지, 보안 검사 및 접근성 기능을 보존합니다. 이를 축소하거나 제거하는 모든 발견 사항은 건너뜁니다.

**호출자가 전달한 구조 핀(structure pins)을 준수하세요.** 구조 핀 제약 조건과 함께 전달된 계획 경로는 범위가 아니라 컨텍스트입니다. 의도적인 중복 또는 분리를 포함하여 `session-settled:` 주요 기술적 결정을 보존하세요.

## 4단계: 동작 보존 검증

프로젝트 전체의 타입 검사(typecheck)와 린트(lint)를 실행합니다. 영향 범위에 맞는 테스트를 실행합니다: 로컬 변경에 대한 범위 지정 테스트, 공유되거나 광범위한 변경에 대한 더 넓은 테스트, 러너가 테스트 범위를 지정할 수 없는 경우 전체 테스트 스위트.

검사 이름 및 관련 출력과 함께 실패를 보고합니다. 단순화로 인해 발생한 실패를 수정하거나 원인이 된 변경을 되돌리세요. 단언문(assertion)을 완화하거나 타입을 약화하거나 테스트를 건너뛰지 마세요.

테스트 스위트, 린트 또는 타입 검사가 구성되지 않은 경우 요약에 이를 명시적으로 언급하고 검증을 조용히 건너뛰지 마세요.

## 5단계: 요약

이미 견고했던 부분과 개선된 부분을 요약합니다. 재사용성, 품질, 효율성별로 적용된 개수, 건너뛴 개수, 검사 결과를 보고합니다. 변경된 내용이 없으면 그렇게 명시합니다. 순 제거 줄 수를 성공 지표로 사용하지 마세요.
